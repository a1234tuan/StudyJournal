## 1. 不可退让的目标

1. 日志仍为唯一正文真源；知识库只保存组织文字和日志 ID 引用。
2. 旧日志/标签/附件/复习/Coach/计划/语音事实不得因组织操作改变。
3. 浏览、展开、平移、缩放、查找不得产生正式云写入。
4. 并发修改不能以整图快照或旧整行静默覆盖新内容；无法安全合并就保留证据。
5. 移动后正式树始终无环；一个节点只有一个正式父级。
6. 本地事务、云端提交、确认后的本地应用分别有原子边界，不混称“已保存/已同步”。
7. 备份包含尚未上传的组织内容和冲突证据；恢复不自动把旧包当最新版本覆盖云库。
8. 能够在 Android 与 desktop 完成整理、检索、阅读、编辑、返回；导图不是唯一操作路径。
9. 自动阶段通过不等于用户验收、真机验收或生产发布通过。

## 2. 已选定的推荐决策

### D01. 功能与入口

保留现有主导航、分类和中央新建日志动作。入口为日志页次级“知识库”、更多 → 应用 → 知识库、日志详情“加入专题”及所属专题反链。默认大纲，导图是同一树的另一视图。首期包含专题、文字节点、多个日志引用、节点说明、引用备注、批量归类、待整理、组合搜索、回收站和待处理。

不实现 AI 分类/问答、RAG、语义向量、图谱关系线、段落锚点、自由白板、跨专题子树迁移或节点别名。为未来保留稳定身份和查询接口，不预建平台。

### D02. 单位置、引用身份及生命周期

取消 Placement。Node 具有不可变 workspaceId 和一个 position = {parentNodeId, orderKey} 原子单元；Reference 绑 nodeId + recordId，不复制正文。同一日志可在不同节点出现。

Reference 的 id 由 ref-v1 + SHA-256(canonical({nodeId, recordId})) 确定，同一库内同一对只有一个正式身份。不同备注保存为候选；delete 与未见的 add/edit 并发采用 remove-wins 可见性，重新加入必须显式 restore 同一 id 且保留旧备注/候选。完整交错规则见 D11/C2，不能创建新 ID 绕过删除。

分支删除只对分支根设置知识墓碑，后代保留并进入回收投影；不自动改父级。专题归档不同于删除。v1 不自动永久清理墓碑、历史和候选；提供占用提示及导出，不实施按日期盲删。

### D03. 编辑与文字格式

纯文本、多行、显式保存，不增加富文本/节点附件。标题最多 512 UTF-8 字节、说明 16 KiB、备注 4 KiB。空说明/备注合法，标题必填。本机恢复草稿保留原字段版本、按库隔离，不参与云/检索/正式备份。

本地提交短暂锁定目标字段，保留输入至结果确定；失败保留输入，草稿失败不得提示草稿已保存。退出未保存编辑有继续、保留草稿后离开、明确放弃。IME 组合期 Enter 不保存、不查找下一条。

### D04. 排序、结构与导图实现

orderKey 采用**可变长度分数排序串**，固定 Base62 字母表（0–9、A–Z、a–z）和编码比较，不使用 localeCompare；生成规范合法键的最短中间串，禁止会导致前缀间无可插入值的终止形式。基于实际邻居键而不是固定浮点精度计算。并发同间隙生成使用 commandId 派生的唯一段，完整键参与后续中间键计算；最终同值以稳定 ID 决定顺序。一个节点 parent/order 同时更新，禁止字段拆合并。

排序编码和字母表封装在纯 orderKey 模块，P0 必须以可执行性质测试验证：任意合法邻居间能生成可比较键、并发唯一段不破坏区间、前缀键正确、重复操作幂等。单键最多 4096 UTF-8 字节，超预算拒绝本次操作且保留原位置；不偷偷分批改整父级排序。首期不做后台全树重排。达到预算时展示可诊断信息和替代目标选择，P0 的热区插入测试必须证明正常夹具不会触达此保护。

导图选择纯 SVG 连线 + HTML 节点、左至右层级布局、虚拟根；布局在可替换纯函数内实现，不首期引入复杂白板/图谱依赖。坐标不进数据库事实。大纲/移动到提供所有功能的键盘/触屏替代。

### D05. 视觉与响应式

继承 reading/modern × light/dark/system，使用现有视觉 token，控件/卡片约 6px、容器约 8px 圆角。低饱和、细分隔、不做彩虹分支或大阴影。知识区及其 portal 采用局部 on-primary 前景映射修正深色浅底主按钮可读性，不扩大到全站样式维护。

默认手机文字 1rem，必要触区至少 44px，行高随换行/字号增长。可用内容宽度达到 840px 才并列详情，详情 300–340px、主区至少约 480px；否则覆盖详情/详情页。手机只读详情起始约可用视口 60%，长读和编辑转全高，不实现多级拖动吸附 sheet。

浏览态不拖节点，整理态把手启动；初始鼠标拖动阈值 6 CSS px、触屏 10 CSS px，双指立即取消单指点击候选。阈值可按手势测试在不改变模式边界的前提下调整，不能以扩大误触窗口换取通过。全局页面动效沿用现有 140/120ms 淡入出、180/150ms 进退及 reduced-motion 行为。

### D06. schema 与本地实体

当前 schema 24，知识库迁移使用 **schema 25**；开工先确认没有其他已完成工作占用 25，如已占用则使用下一个版本并记录，不覆盖既有迁移。只增表/索引，不重命名数据库、包标识、签名或数据目录。

计划新增以下十一个逻辑存储；最终类型定义和建表放同一小模块，避免散落：

- knowledgeLibraries：库身份、本机/账号绑定、恢复副本标记。
- knowledgeWorkspaces：专题事实。
- knowledgeNodes：单位置节点事实。
- knowledgeReferences：引用事实。
- knowledgeRevisions：不可变小单元版本及父版本。
- knowledgeConflicts：按 kind 区分不可变分歧/解决证据、可重建 candidateProjection 和固定大小 groupState（generation/setToken/count/currentRevisionId）；各 kind 身份带前缀，不将派生状态覆盖原始证据。
- knowledgeRemoteEntities：已确认远端镜像，不能直接当 UI 当前内容。
- knowledgeCommands：本机待上传/未知结果命令，稳定 ID 与请求 hash。
- knowledgeSyncState：库/账号上下文、连续游标、dataGeneration、知识 epoch、持久备份 dirtyGeneration。
- knowledgeDrafts：本机未正式保存的编辑恢复草稿。
- knowledgeBackupScopes：按 ownerScope 持久保存备份范围版本、目的地授权、dirty/已覆盖代际及运行会话状态；设备本地，不进入云与便携事实。

知识事实、协议与草稿行按 libraryId 分区；事实主键采用 [libraryId+id]，关联节点/日志的查询加库内复合索引。knowledgeBackupScopes 例外，按 ownerScope 分区，不能用当前选中库替代身份范围。根父级用类型中定义的保留哨兵值，不能依赖 IndexedDB 对 null 索引的行为。索引/画布缓存可以内存重建，首期不额外增加可误同步缓存表。

### D07. 命令、版本和局部合并

所有 UI 写操作经 repository/command 单入口。命令固定 commandId、context、dataGeneration、目标、expected 单元版本集合和明确 patch。本地事务内读当前行、验证、应用、写版本/命令/epoch/备份 dirty；失败整体回滚，无变化操作为 no-op。

revisionId = commandId + 单元标识；规范化内容以确定性 JSON 编码及 SHA-256 计算 hash（使用项目已有 @noble/hashes/sha256 的同步实现，不在 Dexie 事务里等待网络、计时器或异步 WebCrypto），对象键排序、数组保序，明确区分缺失/null/删除，不混入时间、视口、ledger。字符串不擅自改 Unicode 或换行后再假称原样保留。先校验类型再规范化，拒绝非法数值/未知版本。

同字段并发不同值保留当前已提交值与候选，不逐字合并；不同字段可合并，但还要统一检查删除/编辑关系与树。候选可多于两份。解决命令携带事务维护的固定大小 group generation/setToken、正式版本和本批选择的候选，语义校验完整集合未变但不发送全部候选列表；只消费所选批次。并发解决或新候选到达则拒绝陈旧解决并保留输入，详细协议见 D11/C3。已覆盖旧版本重传不复活冲突，旧版本派生的新修改仍要保留。

所有正式父级变更在当前完整专题验证，云端提交还绑定 head，不能用本机检查代替合并后的检查。破坏树的候选仍可保存，但不得物化为正式结构。

### D08. 独立知识云通道

选 /knowledgeUsers/{uid}/libraries/{cloudLibraryId}/… 独立顶层命名空间，不置于旧 /users 递归放行规则之下。v1 无知识 Storage 对象，不复用普通 assets/documents 根和 GC。普通实体映射、账本、游标、epoch 与删除推导不接纳知识实体。

云布局为 library head、entities、revisions、conflicts、immutable commits、receipts。每次有界命令以一致镜像准备结果，在事务里比较 head/相关版本与 receipt，同步写完整结果/证据/commit/receipt/new head。64 KiB 是单次序列化事务变更预算，20 是包括 head/证据等在内的写文档上限，均为本项目上限而非供应商额度说明；本地创建命令前就校验，禁止本机接受了一个永远无法同步的超限编辑。

可见大批量拆成独立命令，逐项展示成功/失败/待核对；单条语义原子操作不可拆。大量候选按 D11/C3 的组令牌与至多4项批次处理，未选候选原样保留；新令牌确认 unresolvedCount 为0时才显示该组全部解决，不能丢候选或发送无界heads数组以完成请求。

相同 commandId 的 receipt 校验原始不可变命令 hash；重试重新计算的合并结果可以变，但不能改变原始意图后仍冒用同一 ID。稳定 ID/时间在事务重试回调之外生成。事务失败不写部分结果，未知结果先查 receipt；不引入远端长锁、租约或跨批次事务协调器。

拉取固定 endHead，按连续提交序号读 immutable commit 的完整变更，不用“读取当前可变 entities”假冒过去某个 head 的一致快照。首期不 GC commit；首次从零连续重放，未来 checkpoint 单独设计。定向确认不推进连续 cursor。

本地同一事务完成 remote mirror、基线、特定命令确认、pending 重放/候选、working view 和 cursor。V1 确认时 V2 仍待传。账号/库/代际已变时晚回调拒绝；纯下载也遵守该合同。

### D09. 绑定、备份与恢复

首次绑定/第二设备发现统一按 D11/C1：每账号一个默认云库，固定 registry/default 事务注册；空设备自动发现拉取，已有非空未绑定库保留并显式另存专题，不按名称合并。已绑定 A 的库不随登录 B 上传；本地 libraryId 与云 cloudLibraryId 的映射独立。

完整备份提议 v7，使用外层 manifest.json + snapshot-v7.json，不保留旧根 data.json；新读取器可读旧 v1–v6。所有入口按 D11/C4 在正式写入前验证四态：缺知识段不改知识库；合法空在选中恢复知识范围后创建空detached副本；非空创建各自新副本；损坏/未来版本拒绝。任何知识恢复均不清空/替换已有库。知识版本/候选/墓碑与未上传内容可携带；账号凭据、ledger、receipt、锁、设备草稿不携带。

知识恢复为新的 detached 本机库，原云库不回滚，之后可留本机、切回原云库、显式重映射 ID 另存专题。恢复阶段抬高并持久化代际；日志和知识的选中恢复范围暂存完校验后在本地一次正式事务切换。取消/失败不可留下半份正式事实。旧在途云提交不能靠 abort 撤回，原库仍须核对 receipt。

自动备份按 D11/C5 覆盖当前ownerScope的全部本机知识库（含恢复副本），不包含其他账号/未认领guest库；配置、目的地及确认代际按身份隔离。采用持久 dirtyGeneration + 提交后调度 + 启动补偿，不能通过脏普通云 epoch 触发。普通日志仍是本机非账号分区集合，完整包必须明确告知，不能宣称账号日志隔离。旧版本读取新容器、同设备 DB 降级、原生流式入口必须实测失败关闭；不允许 catch 后删库重建。

### D10. 检索、导航及安全反馈

综合检索包括当前可用正式日志与组织文字；专题 Ctrl+F 只包括当前专题与其引用日志，可选正文/已接受 OCR。待整理排除删除日志和草稿，归档/隐藏/候选引用不算默认已整理。全局按日志去重，图内另报定位点数；完整扫描前不显示精确总数，不复用 200 条显示上限作全量。

来源栈统一进入现有 TabMemory/Web history，建议上限 32 层，超出仅丢最旧导航历史，不丢事实。Back 顺序为拖动 → 顶层编辑/确认/选择 → 模态详情 → 搜索 → 整理子态 → 来源栈 → 宿主返回；同次事件只消费一层。

本地保存、待同步、云结果未知和冲突分开呈现；暂缺原日志只做派生状态，不累计成冲突。所有 UI 错误经过 uiError。无 AI/付费请求。相同命令重试不换 ID，不用 spinner 掩盖失败。

### D11. 五个跨端边界的确定合同（本轮补充）

本节对 D02、D07–D09 和 R3 的相应概述作具体化；如旧措辞仍可产生不同解释，以本节为准。以下均为选定设计，不是假称已有实现或已通过新增测试。

#### C1. 同账号发现默认云库、首次绑定与离线双库汇入

**首期一个账号只有一个默认同步云库；本机可有多个未绑定库/恢复副本。** 专题是库内对象，“手机的数据结构”不等于为每个专题另建一个云库。云库生命周期不得由客户端登录时自动删除或替换。

1. 固定注册入口为 /knowledgeUsers/{uid}/registry/default，保存 protocolVersion、cloudLibraryId、registrationRevision。首次明确启用知识同步时，在一次事务内读取注册项：不存在才创建注册项、空云库 head 和注册 receipt；已存在就返回那个 cloudLibraryId。两台同时创建只能有一个胜者，失败方读回胜者，不能遗留第二个可用“默认库”。候选 UUID 和 requestId 在重试回调外生成。未登录、离线或权限错误不能被当成“注册项不存在”。
2. 第二台同账号设备在线进入知识库并启用知识同步时，先读注册项。没有本机组织事实/墓碑/候选/待上传命令的设备自动建立本地映射，拉取完整提交到固定 head 后显示该库；不要新建空云库。下载中显示“正在获取账号知识库”，失败显示重试，不能给用户一个看似丢数据的空库。已有库可立即只读浏览；仅发现/下载不产生云写入。
3. 未登录库用明确 guest 本机身份；登录不自动上传。云端无注册时，用户的“启用同步并连接此本机库”是一次明示绑定：先注册，再把本地事实转为稳定的首传命令，保留原实体 ID；原云 head 创建和本地全部内容上传不是同一事务，UI 显示首传进度，另一设备可见部分已提交专题，不假称整库已完整上传。
4. 云端已有默认库而当前设备已有**未绑定且非空**本机库时，先下载默认库并保留本机库，展示二者来源/数量。推荐动作是“把本机专题另存到账号知识库”；必须用户明确点击，登录不等于同意汇入。未绑定库不伪装成远端镜像，不能拿它的缺行推导云删除。
5. 另存按专题复制组织结构，不按同名专题/同名节点合并，不复制日志正文。创建一次持久 importSessionId，对 workspace/node/reference 的新 ID 映射在本地事务固定；Reference ID 用重映射后的 nodeId + 原 recordId 重新计算。导入可按小命令逐步成功，重试沿用相同 ID/commandId；原本机库不删除也不自动改成已同步镜像，显示“已另存到账号库”的来源关联即可。会话固定源库快照及其版本，导入按父专题/父节点先于子节点、引用的顺序分批提交；中途新编辑不混入已确认会话，另存进度明确标出已完成和未完成部分。
6. 两台都离线创建“数据结构”后连接：共同采用注册项指向的默认云库；第二份通过显式另存后成为另一专题，允许同名，UI 显示来源/创建时间区分。首期不自动去重不同身份的同名内容。已绑定到同一 cloudLibraryId 的两台离线编辑则走正常版本合并，不走复制导入。
7. recordId 只在原日志身份可信时沿用，不按标题匹配；云日志尚未到达则保留未知引用，日志由普通通道同步。身份冲突需显式处理，不修改原日志或悄悄上传另一账号日志。注册项已存在但云 head 缺失/不兼容视为异常，停止写入并给诊断，绝不自动新建替代库。

本地映射唯一约束为 {ownerUid, cloudLibraryId}，注册发现不生成重复镜像。切账号或绑定上下文变化时递增 contextGeneration，旧发现/导入回调不能映射到新账号。实体操作的稳定 scope 是云库身份；本地 libraryId 只是本机容器，不参与跨设备引用 identity hash。

#### C2. 引用唯一身份、删除优先与显式重新加入

正式引用身份为 ref-v1 + SHA-256(canonical({nodeId, recordId}))，完整身份还包含其所在 cloudLibraryId（未绑定时对应本机库）。ID 不含备注、时间、设备或本机 libraryId。数据库/云端同一库的这个引用 key 只有一条正式行，candidate/revision 是证据而非第二条引用。读取到同 hash 但元组不一致时拒绝并诊断，不能合并错误日志。

- 两端首次同时添加同一对：确定性同一 id，两次创建均以“未存在”基线表达。事务首个版本成正式值，相同字段值收敛，不同备注成为候选；界面只有一条引用，但“先看队列”“注意最短路”均可查看。引用位置顺序的并发也作为该引用的顺序候选，不制造新引用 ID。
- 已有 live 引用时“添加”是幂等 no-op，不清空原备注、不偷偷恢复旧备注；要改备注必须明确 editRemark。并发首次添加的“没有备注”是空创建基线，不压掉另一端非空备注；将已有备注改为空则是显式编辑，可与并发非空编辑产生候选。
- “移除引用”针对这个正式 id 的生命周期设置 tombstone，作用于整条引用的可见性，**不是只移除一份候选备注**。候选、原备注和历史仍保留在知识回收状态，原日志不删除。删除命令固定生命周期基线与自己已见的版本 frontier；本地相关版本在确认后变化则返回 stale、保留对话框上下文。
- 云上并发 delete 与 add/edit：选择 **remove-wins 可见性**。只有删除标记进入正式生命周期；未被删除操作看到的备注/顺序版本保留在隐藏候选，可在回收站查看。无论上传先后最终引用不自动复活。迟到的“首次添加/编辑”没有权限清除 tombstone，不被伪装成 restore。
- “重新加入”检查并提示“此前已移除，恢复此引用”，发显式 restoreReference，使用同一个 id、当前 tombstone revision 及 restore 所见的候选集合 token，目标节点必须有效。只清除生命周期删除状态，保留原正式备注与全部候选；如用户要换备注，恢复后再明确编辑。不得通过新 ID、清空备注或覆盖整行绕过删除历史。
- restore 必须因果上包含要解除的 tombstone；restore 与它未见的新删除并发时仍由删除保持隐藏，restore 意图可重试/比较，不能由时间戳决定谁赢。两个针对同一墓碑的等效 restore 在基线未有新删除时收敛为一次可见恢复，不重复创建。旧 add 在 restore 后迟到可以带来新备注候选，不能替换已恢复的备注。

分支/专题隐藏仍优先于引用自身 live，恢复引用不自动恢复被删祖先。UI 删除一个正式引用就隐藏该节点对该日志的链接，另一个节点的相同日志引用不受影响。

#### C3. 大量候选：固定大小集合令牌 + 有界部分解决

撤回“每次解决请求必须携带全部活跃 heads 列表”的线格式要求。**语义上仍检查完整集合是否变化，网络请求改用固定大小集合状态令牌；选择只解决部分候选是正式支持的行为。** 不要求用户一次读完十份才处理其中三份，也不能把未读候选当成已接受/已丢弃。

每个冲突组定义 groupId = 实体+单元，维护派生 ConflictGroupState：generation、setToken、unresolvedCount、currentRevisionId。该状态与相关候选投影更新、版本/解决证据、receipt/head 在同一云事务写入；本地在同一 apply 事务更新。setToken 是按已提交历史递增 generation 和有界本次增删摘要计算的 SHA-256 链令牌，不是客户端随手对当前可见分页 hash，也不声称它与提交顺序无关。

任一候选新增、消费、当前正式值变化均推进 generation/token；CAS 检查库 head、group generation/token 和 currentRevisionId。候选新增必须与组状态一起提交，不能存在候选行已写但 token 未变的窗口。候选原文/因果 revision 与解决记录不可变，活跃标志和计数是可重建投影；规则与测试验证这些相关写入和身份限制。为了避免无界索引列表，group 行只放固定字段，候选活跃状态在候选投影行保存。

解决流程：

1. UI 从固定 commitHead 的本地一致镜像分页读候选，默认每页 20 个摘要、原文按需展开，显示总数与正式值。候选多于两份时可选任意两份比较；分页前后 group token 变了就提示有新版本，不冒充同一集合。
2. 一次明确操作选择 S 个候选（最多 4，且实际编码小于 64 KiB/20 文档）；可“合并这些候选到当前版本”“采用其中一版并处理所选候选”或“保留当前版，处理所选候选”。操作文案明确只处理选中的 K 项，不是“所有冲突已解决”。
3. 请求包含 groupId、expected generation/token、expected currentRevisionId、selectedCandidateIds、各选中候选 expected revisionId、resultText/结构意图及 commandId。不发送未选候选 ID 列表，也不重复传所有旧正文。只读/写所选候选及固定组状态；result revision 的父节点为先前正式/累计版本 + 本批所选版本，大小有界。
4. 事务验证各 selected 仍 active、集合 token 未变、result 合法，然后写新累计正式 revision（或确认保留原正式值的有界解决 revision）、消费所选候选、更新 count/token、保存不可变解决证据。未选候选的正文、活跃状态和历史全部保留。
5. 例如 10 个未解决候选，合并选中的 3 个后剩余 7 个，界面显示“本批已处理 3 项，还有 7 项”。下一次在新 token 上继续，可将上一次合并结果作为正式基线。只有 unresolvedCount = 0 且该 token 仍当前，才能显示此组已解决；之后新分支到来可再次显示待处理。
6. 批次间出现第 11 个版本或另一设备已处理，旧 token 的下一批拒绝，保留用户合并输入/选择，重新比较。未知结果先查同 ID receipt；已成功批次不重放，未成功部分不借新 commandId 重做。不能自动把针对旧集合的“全部采用某版”授权扩大到新候选。
7. 完成后旧祖先重传根据因果版本与已消费候选投影判重，不能仅靠一个不断变长的 coveredIds 数组。通过有界解决 revision 的父链保留已处理因果关系；旧祖先派生的新 revision 仍是新的分歧，不静默忽略。

不可变正文只存一份并用 revisionId 引用，commit/receipt 记录引用和小元数据；重放所需的 immutable revision 必须同一事务存在，reader 按 commit 引用取齐后才能推进 cursor。测预算包括所有写文档，而不是只算用户输入。候选最多选择 4 是上限，不是每次强行满批；单个最大合法说明和一次删除/恢复也须有可提交路径，P0 必须测得证据。

此设计不引入长租约、锁住其他设备的“冲突处理会话”或清空未选候选。结构候选处理后仍检查全树；无效目标只能换有效位置/保留当前，不为完成计数而制造环。

#### C4. 空备份与 detached 恢复：绝不清空现有知识库

**v1 知识恢复永远不原位覆盖任一已有库。** 明确撤回“合法空集合需确认清空当前库”的旧表述。用户勾选的是从包恢复的范围，不是选中一个会被删除的现存知识库；如需清空已有库，应走另一个显式删除流程，不复用恢复按钮。

v7 的 knowledge 段是带 version 与 libraries 数组的 envelope；每个库含 archiveLibraryId、名称、便携事实/候选等。知识段的校验和和 manifest 范围描述必须匹配，不能把读取失败当合法空。

- 缺少 knowledge 段：这是未覆盖知识范围的旧包/日志包，不创建知识恢复副本，不改现有库或当前选中。
- knowledge 合法但 libraries=[]：预检显示“知识部分为空；将创建一个空的本机恢复副本，现有库和云端均保留”。只有用户选择恢复知识部分才创建一个空 detached 库；不选则不做知识写入。
- libraries 中明确列出的某库没有节点/专题：保留该空库的存在和名称，创建对应空副本；不能把“空库”与“无知识字段”混同。
- libraries 非空：每个被选择库生成一个新的 detached libraryId，内部 ID 按库边界还原/映射，跨库身份不混用；本机原库/云镜像/其他恢复副本全部保留。
- 损坏、缺必需数组、未知版本、manifest 与 payload 不一致：任何正式写入前拒绝，包括异常写成 null；不得转成 libraries=[] 后继续。

restoreSessionId 在用户确认后固定，{sessionId, archiveLibraryId} 对应稳定新库 ID，重试或崩溃恢复不能造多份副本。libraries=[] 使用固定 empty-envelope 源标识。用户另一次明确点击“再次恢复”才创建新 session，界面说明将增加副本。保存整个 restore session 的状态不携带旧云 ledger/绑定。

新副本归属**确认恢复时的本机身份 ownerScope**（C5）；提交前身份/代际变化则取消正式提交，暂存待清理，不把 A 时确认的包导入 B 的可见库。所有选择库与用户同时选择的普通日志恢复仍遵循一次本地正式事务；普通日志原有替换语义不受知识新增副本语义偷换，预检分别说明。单库恢复成功可选中新副本，多库恢复到副本列表；未选范围的库不变。

因此“云库 100 个节点 + 空知识备份”的唯一结果是：原 100 个节点保留，另有 0 节点恢复副本；点击普通知识同步也不能把这个副本当原云库发删除。

#### C5. 多本地库、账号切换与备份范围

**备份范围按身份而非当前正在看的 libraryId，也不按数据库里全部库。** 首期没有“后台打包本机所有账号知识库”的模式。

本地 library 除 sync binding 外，必须有不可混淆的 ownerScope：account(uid) 或 deviceGuest。恢复副本即便没有 cloudLibraryId，也有 ownerScope；绑定同步/解绑/退出登录不自动改 ownerScope。A 的库与 A 的恢复副本在切到 B 或退出登录后均不可枚举、查询、导出；UI 锁定不能只靠过滤，repository/备份入口也检查 ownerScope。

- 未登录：当前身份 deviceGuest，自动/默认手工完整备份仅包括 deviceGuest 的所有库。
- 登录 A：只包括 ownerScope=A 的**全部本机已保留知识库**，含云镜像、A 的恢复副本、归档/回收内容、未上传正式修改及冲突证据；不是只备当前选中的库。A 期间新建恢复副本自动纳入 A 范围并增加范围 dirty generation。
- 登录 B：同理只备 B；A 的库连标题、候选、库计数和附件引用衍生信息也不进入 B 知识载荷。未认领 guest 库不会因登录 B 自动加入；用户从 guest 明确另存/认领后才按目标身份处理。
- 登出：保留账号数据但不可见，不把 A 的绑定信息清掉后伪装为 guest；guest 范围只看原 guest 库。登录不自动认领/上传 guest 内容。

新默认备份按钮文案为“当前身份完整备份”，预检清楚列知识库数量和来源。选择部分库的手工导出标“知识库选定范围备份”，知识-only 包不声称携带原日志正文；只恢复知识库可保留暂缺引用。未上传修改必须包含，UI 未保存草稿按既有排除边界不包含；云端尚未拉取部分无法凭空备份，manifest 明确本机快照/已拉取水位与待同步情况（仅便携说明，不携带可恢复成 ledger 的运行游标）。

**现有普通日志不是按 Firebase 账号分区的事实库。** 不能承诺 B 导出的普通日志中一定没有曾在 A 使用时写下的日志。完整包预检必须同时说明：“日志部分是本机日志集合，不按云账号隔离；知识库部分仅当前身份”。这不是顺带重构普通日志所有权的授权，也不能把这种包简称为“B 账号所有数据”。切换身份后重新启用完整自动备份，需要确认这个范围；如用户不要带普通日志，使用明确的知识-only 手工备份，不能偷偷改完整包语义。

自动备份配置、dirty/lastSuccess、目的地授权按 ownerScope 独立持久化（新增 knowledgeBackupScopes 存储，见 D06 修订）。原有全局自动备份开关/目录不无条件继承到另一个账号；v7 升级后首次完整自动备份须确认范围与目的地；确认前暂停未绑定身份的旧自动调度并显式提示，不让旧全局目录在切账号后继续写。手动“仅日志兼容导出”仍可用，必须标明知识库未纳入，不静默降级自动完整备份。暂停或仅日志导出不能清掉知识 dirty；用户确认 v7 完整备份后才可标知识已备份。

每个 ownerScope 绑定独立目的地分区；允许同一父目录下不同 opaqueScopeId 子目录，但不能共用 latest 文件、仓库快照头、去重对象根或 GC 范围。已属于 A 的目标不能在 B 下无提示改成 B 最新备份。路径不含原始 uid/邮箱；这只是避免串写，不提供文件加密或阻止同一个 OS 用户主动读取旧 A 文件，首次设置须提示存放位置权限。

开始一次备份固定 BackupScopeToken = {ownerScope, scopeEpoch, membershipGeneration, selectedLibraryIds, capturedDirtyGenerations, destinationId}，先在一致只读事务捕获知识事实和便携快照，再到事务外写文件/原生资源；逐库扫描期间不能动态混入新账号/新库。数量多时内部持久快照可分块，但一次包的范围/版本必须固定，最后 manifest 标明内容与校验和。

切账号/退出/恢复提升 scopeEpoch，停止旧调度、清除展示缓存。旧任务已经准备好的 A 快照仅允许完成到旧授权的 A 隔离目的地或丢弃临时输出，**绝不重新读取 B 的“当前目录”或“当前快照”**；已发出的文件写入不能靠 abort 保证撤回。不创建 B 配置、不更新 B 的成功标记。A 的任务只有在核验旧 scope 快照与产物均完整时才记录 A 的 captured generations 已备份，否则保留 A dirty；B 需独立启用，A 待办待回 A 后续跑。

同一身份新库创建/库内容修改/范围变化发生在快照捕获之后，仍保持未覆盖代际 dirty；当前任务只确认 captured generations，不能把现在所有库都标为已备份。未绑定目录、只备日志、写入失败、账号切换都不能清掉对应知识 dirty。

各导出入口必须传明确 BackupScopeToken 或同等冻结上下文，不能继续无参遍历 db 中所有知识库；原生/目录/云恢复快照入口同样遵守范围。manifest 使用包内 archiveLibraryId 和不含原始账号凭据的范围说明，恢复时不信任包里的旧账号标签自动授予所有权，以当前确认身份创建 detached 副本。

### D12. 本轮五项补充的测试映射

以下21项均为**必须新增的验收场景，尚未执行**。各阶段退出条件包含本节标注给该阶段的全部用例，不是可选附录。每组先在纯规格/隔离数据库验证，再覆盖指定集成路径；失败按原 P0–P7 规则修复，阶段通过后直接推进，不需要另设用户中间确认。

- BIND-01（P0/P3）：两端同时首次注册，只有一个 default 指针/一个可用云库，失败方无孤立可用库；重试 receipt 幂等。
- BIND-02（P3/P4/P7）：第二台空设备发现同一库，获取首传中/完成/离线/失败状态正确；纯发现与拉取零云写入。
- BIND-03（P1/P3/P4）：两端都有同名本机专题，保留两源并显式另存；中断重试 ID 稳定，无正文复制/名称匹配合并/原库删除。
- BIND-04（P3）：发现期间切账号、注册存在但 head 缺失/版本不兼容，拒绝错误绑定且不新建替代库。
- REF-01（P0/P1/P3）：两端同 tuple 首次添加不同备注，正式引用恰好一条，两备注可找回；重复 live add 不清备注。
- REF-02（P0/P3）：delete 与 add/edit 的所有提交顺序最终 remove-wins，候选保留、正文不变；另一个节点引用不受影响。
- REF-03（P1/P3/P4）：restore 同 id 保留备注/候选；两个等效恢复幂等；新 delete 与旧 restore 交错仍隐藏，旧 add 不复活。
- REF-04（P1/P2）：本机 libraryId 改变/恢复副本和导入新节点后身份符合规则，跨库不串行；hash 与元组不符拒绝。
- GROUP-01（P0/P3）：10、100、1000 个候选分页，先处理 3 个其余原文/状态不变；请求/文档数不随总候选数线性增长，计数准确。
- GROUP-02（P0/P3/P4）：部分批次后新候选/另一解决者改变 token，旧下一批 stale 且保留输入；未读候选绝不被消费。
- GROUP-03（P3）：提交结果未知、云成功 local apply 失败、重启重放、不完整 commit revision 获取，receipt/cursor/group 状态不重计/跳号。
- GROUP-04（P0/P3）：最大说明 16 KiB、备注 4 KiB、最多4项和实际少于4项批次，含全部证据/head/receipt 写入仍满足64 KiB/20文档；无单个合法字段永不可解的状态。
- GROUP-05（P0/P2/P3）：多批解决后备份还原覆盖关系；旧祖先重传不复活，祖先派生新分支仍显示，计数为零只针对已确认 token。
- EMPTY-01（P2/P4/P7）：现有云库100节点，libraries=[] 创建0节点 detached副本；旧100节点、云head、旧ledger不变。
- EMPTY-02（P2）：缺段不创建；显式一个空库创建一个空副本；多库分别创建；损坏/null/未知版本写前拒绝。
- EMPTY-03（P2/P3）：同 restoreSession 重试不重复副本；确认后切账号或在途sync回调不得污染新副本；普通日志恢复语义单独校验。
- SCOPE-01（P1/P2/P4）：A云镜像+A恢复副本+B库+guest库共存，A默认包含前两者且不含B/guest任何知识内容；B、登出反向验证。
- SCOPE-02（P2/P3）：逐阶段注入账号切换：排队、读快照、资源读取、文件写入、核验、确认代际；目的地隔离，A结果不更新B，旧输出不写进B latest。
- SCOPE-03（P2）：同身份切当前库不缩小范围；捕获后新建副本/新编辑仍dirty；只日志备份不清知识dirty，升级未确认状态文案真实。
- SCOPE-04（P2/P4/P7）：B首次完整自动备份必须确认本机日志非账号分区和新目的地；不存在跨账号继承开关/覆盖latest/跨分区GC；全部ZIP/流式/仓库入口产物范围一致。
- SCOPE-05（P2）：manifest不含原始uid/凭据、包中旧账号标签不自动认领；partial手工包不标完整，当前身份所有本机库/未上传事实 round-trip 无丢失。

## 4. 所有阶段共同的执行规则

### 4.1 自动推进

进入阶段 → 完成任务 → 跑定向测试 → 补充触及的旧功能回归 → 修复发现的本阶段/本功能 bug → 重跑 → 写阶段证据 → 满足退出标准后自动进入下一阶段。不得用“代码已写完”代替测试退出条件。

不逐阶段请求确认，不每阶段推送一份验收报告。进度与失败细节写本机阶段记录；全部 P0–P7 通过后才汇总给用户最终验收。真实不可继续的外部阻塞不能伪装通过：先尝试不改变合同的本地替代，仍缺凭据、签名或安全执行环境则记录阻塞，不启动破坏性替代或静默跳关。

### 4.2 修复范围和不可绕过项

本功能造成的回归和相关可靠性缺陷立即修复；已存在且无关的缺陷复现、记录，不借机扩范围。已知测试抖动先隔离重跑，并保留第一次失败证据；重跑偶然绿不能直接销账，须判明环境抖动还是产品竞态。绝不删除断言、加大重试、跳过关键测试、放宽云规则或关闭 expected 检查来让阶段绿。

测试预算受并发影响：全量 Vitest、Vite build、Playwright 和 Emulator **串行运行**；Vitest 最多 2 worker，Playwright 1 worker 起步。禁止重演并发构建导致同步测试超时再误诊为产品 bug。

### 4.3 阶段证据格式

执行时新建 docs/knowledge-library-v1-implementation-status-2026-09-22.md（现在不创建假状态）。每阶段记录：状态、基线/变更文件、命令、结果/数量、最初失败及修复、关键截图/trace、环境、未运行项及原因、下一步。状态只用未开始/执行中/失败待修复/通过/外部阻塞，禁止把未运行写成通过。

“通过”要求该阶段所有阻断项为零、数据完整性断言通过、无新增 type/build 错误。恢复/同步发现丢失或错误账号写入，即使只有一例也阻断后续 UI 推进。

## 11. P6：导图、拖拽、响应式与无障碍

实现共享树的确定性布局、平移/缩放/聚焦/全图、标题与数量级别展示、只读详情、整理把手拖放、目标预览与非法原因。把大纲/导图选择与搜索上下文贯通。完成 840px 内容宽度响应、键盘/弹层/系统字号、安全区和 reduced-motion。

### 必测场景

浏览态单指/鼠标滑动不编辑；双指开始取消点击；拖把手只有松手合法目标提交一次；拖动期间目标被远端删除或形成环；后台/pointercancel/Escape 取消不写；提交失败不假成功；缩放/搜索/选中不触发全图重排；拖动中布局延后但提交校验不延后。

1440/1024/768/390/320 × 四种主题，长中文/英文/emoji、深树、200% 缩放和无 hover 输入。合成指针可测 DOM 事件边界，真实捏合/IME/Android Back 仍在 P7 原生隔离环境确认，不能用 JS dispatch 代替全部手势验收。

### 退出标准

所有导图操作都有大纲/移动到替代，页无横向溢出、重要按钮无遮挡、焦点可见且可回返；文字目标对比 4.5:1、必要轮廓/图形 3:1；无浏览导致正式写入。图与大纲显示同一版本和候选状态；帧率与大树预算达到第 13 节。禁止为视觉效果放宽底层数据约束。

## 12. P7：全量集成、隔离宿主验收与最终交付

### 任务与顺序

1. 干净重启后串行跑全部非 live Vitest → TypeScript/生产构建 → 全量受控 Playwright → Firebase Emulator → 受影响的 desktop/native 测试。
2. 用已安装能力和本机测试资源构建 APK/EXE，生成 SHA-256 与源码/环境/测试清单。版本号仅按现有打包规则推进，不改应用身份/签名，不自动发布。
3. desktop 使用独立 userData/profile；Android 优先独立 Emulator/受控测试设备，先载入测试 fixture，再测试升级/冷启动/退出/离线/恢复/系统 Back/IME/安全区/手势。禁止在用户真实库做竞争、清库或破坏性测试。
4. 将旧安装程序置于隔离环境，验证新完整备份拒绝与升级/降级保护；不能仅运行当前代码 mock 就写“旧端已通过”。
5. 两个隔离客户端使用 Emulator 后端重做端到端交错、只拉不改、离线双方编辑、冲突解决、恢复副本后再次同步；真实生产 Firebase 双设备验收留给最后经用户同意的受控步骤，不能暗连真实账户。
6. 更新用户教程、开发文档索引、范围/迁移/备份格式与排障说明，创建最终验收报告，写明自动化/模拟器/真实设备各自证据，不用单一“全部绿”掩盖范围。

### 退出标准

P0–P6 阻断项归零；完整非 live 套件、类型/构建、浏览器及 Emulator 通过；已声明的宿主/旧端测试有真实证据；没有新增数据可靠性缺陷、错误账号写入、不可恢复备份或未解释测试失败。APK/EXE 可追溯且 checksum 有记录。SJ-AUD-01 定向回归再次通过。

如果宿主或旧包环境在 P0 已标外部缺失，P7 不能写“通过”：可交付明确的自动化完成/外部验收阻塞报告，但必须标未完成，不把用户最终验收当作替 agent 漏测兜底。缺少签名、设备连接等也不得绕过安全边界。正常情况下只有这一阶段结束后向用户发一份统一验收邀请。

### 最终用户验收清单

- 测试日志加入两个专题，正文仍为同一份；修改日志后两处均更新，备注各自独立。
- Android/desktop 浏览、展开、缩放不误编辑；移动/搜索/打开日志/返回保持位置。
- 同字段双端修改保留候选、不同字段安全合并、交错移动不成环。
- 收藏/删除/恢复/资源标题及 OCR 相关 SJ-AUD-01 人工复验，最新正文/资源不丢。
- 独立恢复副本不回滚云库，旧包缺字段不清知识库，双通道状态准确。
- 用户确认视觉密度、阅读、IME 和常用操作符合预期。

不把用户确认前的构建称为正式发布；发布、生产规则部署及真实账号压力测试仍不自动执行。

## 13. 性能、测试命令与失败判定

### 13.1 可复现的性能预算

固定基准 fixture：500 篇正式日志，每篇约 2000 中文字符，1000 个节点、5000 条引用，含 20 层深分支与高扇出；另有候选、软删除、长标题/备注及 OCR 样本。记录电脑/Android Emulator 硬件、浏览器/运行时、构建模式，不能把 mock 数量当真实用户容量上限。

生产构建、本机数据已加载、无网络等待下：desktop 热搜索 p95 ≤500ms，Android 受控模拟器 ≤1000ms；首次索引 desktop ≤3s、Android ≤5s，期间界面可交互；首次进入大纲 desktop ≤1s、Android ≤2s。索引切片目标 ≤8ms，取消旧查询在 100ms 内生效。导图拖动稳定过程 p95 帧间隔 desktop ≤25ms、Android ≤40ms；不依赖一帧渲染千份详情。

预热 5 次、测量不少于 20 次，记录 p50/p95、长任务与样本，不用最好一次充数。宿主调度噪声须隔离重测；不能悄悄放宽阈值或减少 fixture。优先虚拟化、折叠、惰性正文、分片索引/布局；必要时 worker 属实现优化，不新增云/AI功能。上述是验收目标，不是已有测量。

### 13.3 失败归属与重跑

纯规则失败回 P0 规则层；事务丢失回 P1；恢复丢内容回 P2；未确认/重复/错账号提交回 P3；输入/导航丢状态回 P4/P5；导图只改投影不得掩盖底层结构失败。修复涉及上游时重跑该阶段及全部已完成下游的受影响回归，不只重跑最后报错的 UI。

构建资源警告可记录但不得忽略类型错误、未捕获异常或影响恢复的解析错误。Playwright 的已知环境超时保留 trace，在同条件/隔离条件比较后归因；不靠增加 retries 使缺陷消失。新增代码不允许只有 snapshot 测试无行为断言。

## 14. 完成定义与通知方式

开发完成 = 阶段证据齐全 + 数据/同步/备份和 UI 闭环通过 + 无未解释阻断项 + 构建可交付。它不等于用户验收完成，更不等于生产发布授权。

最终只发一次正常验收通知，内容为：实现范围与推荐取舍、安装包/校验值、自动化及宿主测试结果、确实未运行的外部事项、用户验收步骤。中间修 bug 和重跑不逐阶段打扰；不可安全继续的外部阻塞如必须通知，只报告必要阻塞，不伪称阶段验收邀请或“已全部完成”。
