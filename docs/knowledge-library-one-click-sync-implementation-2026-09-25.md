## 1. 交付状态

本次已实现本地开发与自动化验证范围的一键同步，并准备两端验收候选包。后续已获单独授权，于2026-09-25北京时间16:15部署生产 Firestore 规则并回读核验，修正线上缺失 knowledgeUsers 规则的问题；见 `docs/knowledge-library-production-rules-deployment-2026-09-25.md`。未读写真实用户内容、覆盖安装或完成用户真机验收，仍不能宣称已验证真实双端同步成功。改动未提交。

正常操作为：电脑保存知识内容 → 点击现有云同步按钮 → 手机点击同一按钮。无需选择来源、本机库、同步范围或手动复制到账号库。两端必须登录应用内同一个 Firebase 用户；Google Cloud 控制台的管理账号本身不是应用登录凭证。

## 2. 实现内容

### 同步入口与真实结果

- 首页及同步页继续使用全局入口，先同步普通日志，再处理知识库；冲突解决后的继续执行也走同一 coordinator。
- 知识阶段发现或注册唯一默认云库，接管普通未绑定来源，再拉取、发布和核对回执。空手机拉取默认库，不要求选来源。
- 日志冲突、预算确认、失败或结果未知时不继续知识阶段，并说明知识尚未同步。
- 成功、无变化、待同步、需确认、失败和未执行分开返回。知识失败或未解决候选不会显示整体成功。普通日志数量及上次时间明确标为普通日志，不冒充知识库进度。
- 权限拒绝、登录失效、网络、额度、超时、缺提交头、坏历史分别处理；请求超时不声称远端事务已取消，下次核对原命令回执。

主要模块：

- `src/services/cloudSyncCoordinator.ts`
- `src/features/knowledgeLibrary/oneClickSync.ts`、`syncResult.ts`、`runtime.ts`
- `src/components/CloudSyncButton.tsx`、`CloudSyncConflictDialog.tsx`

### 安全接管与默认编辑位置

- schema26 升至27，仅新增设备本地 `knowledgeSyncBindings`、`knowledgeLibraryMigrations`；升级不联网、不重写已有知识或日志。知识协议仍为1。
- 当前账号和未认领 guest 的普通未绑定库自动纳入。恢复副本、受保护内容、其他账号、另一云身份不擅自接管。
- 接管采用事务内来源冻结、固定来源摘要和 session、持久冻结步骤及命令回执；中断后继续原步骤，避免重复专题和命令。
- 90秒事务租约阻止同设备多窗口同时整理；账号/会话代际、运行 token 和租约失效后不再启动下一次提交或写入。已发送的请求仍可能到达云端，因此保留回执核对。
- 原库保持只读，既有草稿保留；本地整理完成后，后续创建、编辑、导航和反向链接指向明确的默认目标，不再继续编辑已接管旧库。
- 状态依次为本地整理、等待云确认、已确认；云端回执未证实完整前不标记迁移已确认。guest 认领同时更新备份范围 membership。
- 旧人工复制只有来源摘要及实际命令证据一致才复用；复制后来源被修改则停止并保全，不把新内容误判为已同步。已保存的 active 冻结任务可继续，不依赖源库仍存在。

主要模块：`defaultLibrary.ts`、`migration.ts`、`import.ts`、`repository.ts`、`sync.ts`、`src/db/database.ts`。

### 界面

- 删除旧的 `KnowledgeSyncSettings` 日常选库/复制界面，不再提供新建普通独立库入口。
- 保留恢复管理：可以查看原库、恢复副本及未提交草稿，复制草稿后回默认库保存。
- 已打开旧专题在接管后跳转其对应的新专题；明确进入恢复视图时不强制跳回默认库。
- 使用指南补充电脑保存并同步、手机同步的流程。普通日志云快照与独立知识备份的边界没有改变。

## 3. 方案差异及限制

1. 对未绑定来源统一使用安全冻结复制，不实现计划中可选的“空云时原地绑定”快捷路径。这样原内容始终可查，跨设备同一来源同一快照使用确定命令身份；代价是首次整理有额外本地存储和计算。已经正确绑定的库仍直接增量同步。
2. 同名但不同来源的专题不按标题合并；旧复制后出现的新分叉不静默覆盖。发生真实冲突仍需确认，这不同于日常要求用户选择同步来源。
3. 同步的是正式保存的内容。未保存草稿仍在本机，不能冒充已上传；原库的全部旧历史也不整体转写为云库历史。
4. 纯拉取不生成新的上传命令，但内容变化仍使本机备份需要更新；不将“纯拉取无 dirty”解释成不更新备份代际。
5. 100/500/1000步测试验证冻结步骤规模、前1—2步有界进度、中断续传及未处理尾部不被改写，不是1000步全程真实云上传吞吐验收。导入命令构建/回执验证的全量遍历以及大库性能仍需单独容量测试。
6. 升级已验证隔离 schema26 样本保真及重开；未在用户实际安装数据上做升级或故障注入。新增本地绑定/迁移凭证不进入可移植导出。
7. 不能降级旧安装包直接打开 schema27 数据；优先同 schema 前向修复。不得以清空 registry/head、删原库或整库覆盖回退已发布迁移。

## 5. P6 生产核查与用户验收

本阶段的生产规则核查、备份、部署和回读验证已在单独授权后完成。以下清单中真实账号内容操作、安装和双端验收仍未由代理执行，相关操作仍需授权。它不是“再设计一轮”或让用户选择知识库。

1. 确认两端普通数据、知识库和草稿已有可读备份；记录旧版及待处理状态，退出旧客户端，不卸载清数据。
2. 核对应用内两端 Firebase UID 一致、项目为预期的 `study-journal-408-9f31`、数据库一致及已部署规则版本；只记录必要诊断，不记录 token/密钥。不要把控制台 Google 登录当成客户端登录。
3. 若仍出现 permission-denied，核对实际生效的 `knowledgeUsers/{uid}` 访问规则与本地已通过 Emulator 的规则。仅在确认差异且获授权后部署必要规则，不开放全库权限、不顺带改 Storage/Functions。
4. 用本报告目录中的同一批候选包升级电脑和手机；首次验收不并行修改两端，不另开旧版本。
5. 电脑创建专题和节点、修改标题/备注、添加日志引用，保存后只点一次同步；手机只点一次同步，确认内容、引用正文和结构一致，无来源选择。
6. 电脑继续编辑已有专题并再同步，手机再同步；确认不产生重复专题。检查移动、删除、恢复；重复无变化同步不生成新提交。
7. 重启两端再做一次编辑同步，确认默认编辑位置保持。检查恢复管理可查看旧内容和草稿，但不会重复上传。
8. 网络中断后重试确认续传；任何一侧失败都不得显示整体成功。真实同字段冲突应保全双方并提示确认，而不是自动覆盖。
9. 记录真实规则版本、候选包 SHA256、两端版本及用户结论后，才能标记 P6 和最终需求验收完成。
