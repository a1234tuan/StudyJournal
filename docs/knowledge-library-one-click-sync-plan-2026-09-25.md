# 知识库一键同步：单用户电脑 / Android 分阶段开发方案

日期：2026-09-25。

状态：**已实施本地开发与自动化验证，P6生产规则已授权部署并核验，真实双端验收待完成。** 本文保留最初方案及门槛，不能把其中所有计划用例都视为已完成；实际范围、测试结果、容量测试限制、候选包和安全复制路径差异见 `docs/knowledge-library-one-click-sync-implementation-2026-09-25.md`。以下“当前/尚未/本轮”描述属于方案制定时的基线，实施现状以该记录为准。

## 1. 目标与范围

### 1.1 用户操作合同

1. 电脑编辑并保存知识库，点击现有“同步更改”，自动上传。
2. Android 在应用内登录同一 Google 账号，点击同步，自动拉取。
3. 无新增编辑、网络错误或未解决冲突时，两端专题、节点、层级、顺序、笔记、日志引用和引用备注一致。
4. 以后电脑继续编辑原来看到的内容，再同步；手机再次同步即可获取变化。不选择来源、不复制、不切换所谓账号库。

产品按“一个使用者、同一账号、两台设备”设计。电脑是常用编辑端，**不是无条件覆盖手机的主服务器**；手机离线编辑仍须保留。同步是双向对齐，不是每次整包覆盖或备份恢复。

本次不增加实时后台同步、多账号管理、多人协作、设备角色选择、AI 分类或其他知识库功能。保留普通日志协议及知识库独立协议，保留签名、包名、应用名和数据路径。

### 1.2 正常界面

- 一个“同步更改”入口，说明为“将已保存的日志和知识库同步到当前账号”。首页、侧栏、备份页复用同一流程。
- 不再要求选择“来源本机库”，移除正常流程中的“知识库同步范围”和“复制到账号库”。
- 默认知识库页始终打开参与同步的日常工作区；后续创建专题也进入这里。
- 旧保留来源、备份恢复副本和故障保全副本放在恢复管理中，正常同步不需要用户处理它们。

### 1.3 对旧设计的有限替代

实施时以本文替代 `knowledge-library-v1-final-implementation-plan-2026-09-22.md` 的 D11/C1 中“非空本机库必须手动选择复制、复制后继续保留独立编辑入口”的日常同步策略，以及相关 BIND-03 预期。

固定默认云库、鉴权、引用稳定 ID、删除优先、候选保全、有界事务、坏历史停止和独立备份恢复合同不变。**单用户不等于关闭权限检查。** 当前请求是制定方案，不等于授权立即开发、生产部署或安装。

## 2. 代码基线与待核实项

已从本地实现核实：

- `runtime.ts:synchronizeBoundKnowledge` 只同步已有 `cloudLibraryId` 的库；没有时调用不带来源的 `connect()`，普通本机库被跳过。
- `sync.ts:connect(localLibraryId?)` 已具备默认库注册、发现、部分原地绑定及返回 `importSourceId` 的能力，但没有完成自动接管闭环。
- `import.ts` 已有冻结步骤和持久进度，适合复用；现有“复制”不负责切换后续编辑目标，也不能单独保证跨设备来源去重。
- `repository.ts:createTopic` 和 `KnowledgeLibraryPage.tsx` 存在默认取 `available[0]` 的行为；仅上传成功仍可能继续编辑旧库。
- `CloudSyncButton.tsx` 先知识同步、后普通日志同步；知识结果为字符串，整体成功图标主要由普通日志结果决定。
- `CloudSyncPanel.tsx` 待同步数来自普通日志，不代表知识已上传。
- 本地 `firestore.rules` 有 `knowledgeUsers/{uid}` 规则，配置项目是 `study-journal-408-9f31`；当前 schema26、知识协议1。

尚未核实：生产生效规则、实际客户端 UID/项目/数据库、两端安装版本、真实知识库数量和旧复制状态。截图证明出现权限拒绝，但不能据此断言唯一原因是“规则没有部署”。控制台管理账号与应用内 Firebase Auth 会话须分别检查。

## 3. 确定的技术选择

### D1. 一个默认云库，两份本机镜像

继续以 `knowledgeUsers/{uid}/registry/default` 唯一指向默认云库。两端本地容器 ID 可不同，`cloudLibraryId` 与实体身份、提交历史必须一致。

不为每台设备另建云库，不替换已有注册项，不混入普通日志实体集合，不采用 ZIP 覆盖。日志引用保持原 `recordId`，正文和附件仍走普通日志通道。

### D2. 自动接管普通旧库，不接管恢复副本

点击同步是纳入当前使用者普通本机知识内容的明确意图；仅登录/打开页面不上传旧库。

候选范围：当前 UID 所属普通未绑定库，以及未认领的普通 guest 库；排除其他 UID、已绑定另一云库、detached、restoreSession 来源、失败保全及 blocked 命令保护副本、已完成接管的来源。

- 一份普通库自动接管；多份普通库全部纳入，不任意选第一份，不按同名合并专题。
- “空库”必须没有事实、墓碑、候选、pending 和草稿，不只看可见节点数量。
- 已绑定正确默认云库直接走增量同步，不再次复制。
- 身份/绑定矛盾保留数据并报告，不强行改绑。
- 默认不再创建新的日常“仅本机独立库”，组织内容用专题；恢复管理保留特殊副本能力。

### D3. 接管后必须切换默认读写位置

完成本地接管后，浏览、创建、编辑、反向链接和旧导航都转向同步工作区。来源仅作只读保留，不自动删除，也不能仍显示成另一个普通可编辑入口。

源冻结必须在仓储事务中执行，不能只禁用按钮。旧页面上下文失效后不得继续写旧库，失败输入和本机草稿必须可找回。未保存内容不自动变成正式云内容。

### D4. 明确本地状态存储，不修改云协议

建议 schema26→27，新增两张设备本地表：

1. `knowledgeSyncBindings`：以 `ownerScope` 唯一记录本机默认工作区、云 ID、策略版本和绑定代际。
2. `knowledgeLibraryMigrations`：以 `[ownerScope+sourceLibraryId]` 唯一记录目标、源代际、冻结摘要、稳定 session、阶段及诊断。guest 来源须在事务内检查全体认领，防止重复归属。

大量冻结命令仍使用 schema26 的 `knowledgeImportSessions` / `knowledgeImportSteps`，不塞进一条迁移记录。新表不进入云、普通日志导出或可移植知识备份；恢复备份不能复活设备绑定或“已上传”凭证。

升级事务只建表，不联网、不迁移真实内容。若实施时 schema27 已被其他工作使用，采用下一版本并更新方案。更新 `knowledgeTables` 及所有相关事务范围。

### D5. 同一入口编排两个通道

建议新增 `src/services/cloudSyncCoordinator.ts`。正常顺序为：普通日志同步 → 默认知识库准备/接管 → 知识拉取和发布 → 回执确认 → 刷新视图。

- 日志先到达，减少手机无法打开新引用的时间；跨通道不是原子提交。
- 普通日志出现冲突、预算确认或结果未知，暂停后续知识写入，明确“知识库本次未同步”；解决后沿同一同步意图继续，不替用户决定覆盖。
- 日志成功、知识失败显示部分失败，不撤销日志成功，也不显示整体成功。
- 暂缺原日志的引用保留身份，显示“关联日志尚未到达”，不删除、不按标题重新关联。
- 按钮、冲突后继续及重试共享 coordinator，不能出现旁路。

### D6. 用结构化结果决定成功

知识结果包含 `status`、阶段、已确认上传/拉取命令数、pending/unknown/blocked 数、未解决冲突数、接管进度及错误类别。建议状态为 `success/no-change/pending/needs-attention/error/skipped`。

`pending=0` 不代表无冲突。只有两个通道明确完成且没有未知写入、未完成接管或待处理冲突，整体才显示成功。日志条数和知识命令数分别显示；云端未查询显示“待检查”，不能假报 0。近期状态与本轮结果不能混淆。

## 4. 首次接管算法与安全边界

### 4.1 云端无默认库

先选定可安全原地绑定的来源，再注册。只有可证明完整工作状态、历史、命令可按现有协议从空云端重放，才用原库身份注册；保持原实体 ID。guest 认领同时更新两侧备份 membership 和上下文代际。

不满足重放前提则注册新云 ID，走冻结导入，不能先注册不合格来源再强行补救。两端竞争时只采用注册事务的唯一胜出库，另一端自动导入自己的普通来源。

### 4.2 云端已有默认库

1. 发现注册项、验证 head 并严格拉取可信历史。失败不锁来源，不创建替代云库。
2. 分类来源，检查旧导入、保护状态、草稿与存储可用性。
3. 一个本地事务内复查来源，记录 `dataGeneration/dirtyGeneration/epoch` 和完整快照摘要，固定导入步骤、session 与只读接管标记，令旧写上下文失效。
4. 依照冻结步骤分批导入；故障后仍用同一会话，不从变化的来源重算另一批命令。
5. 本地步骤全部完成并确认内容/候选保全后，事务式设置默认工作区和只读来源映射，刷新及重定向页面。
6. 发布目标 pending；未知结果核对 receipt，不换命令 ID 重发。
7. 拉取确认后标记该批接管已获云确认；目标后来新增的编辑仍计入待同步。

步骤3—5是本地整理区间，用户不能编辑尚未齐全的目标导入分支；来源仍可阅读。**网络上传等待不锁死已经整理好的目标编辑。** 崩溃后页面明确显示未完成，下次同步自动继续。

### 4.3 持久状态机

`prepared → local-copying → local-ready → awaiting-cloud → confirmed`。

- 前两阶段冻结源并保留输入；`local-ready` 切换默认编辑目标；后两阶段网络失败不把用户退回原独立库。
- 错误附着于原阶段，不清 session、不删除冻结步骤。
- 多窗口、重复点击采用事务式执行权和代际校验；过期执行者不能确认或切换新一代流程。
- 未复制/未发布可事务式取消准备；部分复制或发布后只能续传/受控修复，不删云端重来。

### 4.4 幂等与历史复制

- 自动 session 由版本、UID、目标云 ID、来源 ID、规范化完整快照摘要确定并持久固定；生成器采用稳定排序。
- 两端完全相同来源及快照必须产生相同实体/命令 ID、顺序与 hash，通过 receipt 去重。须测试真实生成器，不能只断言 session 名相同。
- 不同来源或仅同名不去重；同源分叉不能沿用相同 command ID 写不同 hash。不能证明等价时保留分支并给一次性诊断，绝不静默舍弃内容。
- 历史 active 手动复制先续用原冻结会话；completed 只有来源摘要匹配且目标实体/命令证据可验证时才认领为已导入。
- 旧复制后来源又被编辑，不能仅按 sourceId 宣称已同步。无法证明如何合并时进入保全诊断，不盲目复制或覆盖；正常“电脑一份库、手机首次拉取”不应触发这个例外。

### 4.5 草稿、导航、备份

正式保存内容参与同步，设备草稿不自动上传。切换前通知活动编辑器保存或保全；旧上下文拒绝写入时保留输入。源草稿在恢复入口仍可达，重映射草稿必须校验实体及基线，不直接篡改 expectedRevision。

有可靠映射时保留所选专题/节点；无映射时回到默认专题列表，不打开另一条同名节点。接管更新必要的备份脏代际及 membership，保全来源和目标按现有身份备份合同可恢复。普通云快照恢复仍不清知识表。

## 5. 分阶段实施与完成门槛

### P1：权限诊断和真实结果

### P2：默认工作区与安全接管基础

工作：新增两张本地表和原子升级；建议新增 `defaultLibrary.ts`、`migration.ts`；实现分类、冻结、固定 session、续传、映射及状态推进。仓储事务阻止旧库继续写入，处理上下文、草稿、guest 认领和备份 membership。先证明安全，再隐藏旧 UI。

文件：`domain.ts`、`schema.ts`、`src/db/database.ts`、`repository.ts`、`import.ts`、新增模块及测试，扩展 `backup.test.ts`、`autoBackup.test.ts`、`importMigration.test.ts`。

完成：升级不改原内容；每个阶段中断重启可续；重复点击不复制；并发写入不落旧库；恢复/其他身份不被上传；草稿可找回，新状态行不装整份命令数组。

### P3：一键上传与手机拉取闭环

工作：知识阶段自动解析默认库、接管并增量同步；空手机只建本地镜像和拉取。消除 `available[0]`，绑定变更刷新视图，来源导航重定向。捕获账号/运行代际，失效后不开始下一条提交；进度与 watchdog 协同，不仅调大超时。停止等待不等于取消已发送的云事务，下次用 receipt 核对。

文件：`runtime.ts`、`sync.ts`、coordinator、默认库/接管模块、`repository.ts`、`KnowledgeLibraryPage.tsx`、`navigation.ts` 及相关调用点。

完成：电脑初传→手机拉取→电脑再改→手机再拉全部一致；移动、删除、恢复和引用通过；重复空同步无新云提交；纯拉取不产生无谓 dirty。

### P4：界面收敛

工作：移除日常选库和复制控件；已有未完成任务仍由接管服务续传。默认展示同步工作区，来源和恢复副本留在恢复管理。日志/知识结果分别显示；成功、部分失败、待处理用不同状态。保持“普通云快照不恢复知识库”的真实说明，更新受影响使用指南。

文件：`CloudSyncPanel.tsx`、`KnowledgeSyncSettings.tsx`（替换或删除无引用实现和测试）、`KnowledgeLibraryPage.tsx`、toast、样式、相关 e2e 和 `UsageGuidePage`。

完成：主流程不选库、不复制；1440px 桌面和390px窄屏可用；检查返回键、重复点击、切换目标及草稿；失败不打成功勾，特殊恢复内容仍可找回。

### P5：自动化与发布候选验收

工作：执行第6、7节；用隔离 schema26 样本验升级；覆盖100/500/1000步接管、耗时、请求数、分页和规则预算。复测普通同步、备份恢复、知识候选及本地隐私边界。更新实际实现文档及旧方案替代关系，不照抄历史测试总数。

完成：定向、全量、Emulator、UI、编译通过；偶发超时单独复跑并记录，不以历史 flake 豁免新错误。未部署、未安装、未真机验收必须明示。

### P6：授权后的生产配置与真实双端验收

前提：另行确认生产规则检查/部署、受控账号读写和设备安装的具体授权；批准本文不自动包含这些操作。

1. 验证两端完整备份可读，记录库、草稿、pending和版本；不卸载、不清数据。
2. 核对真实项目、数据库、应用 UID 和生效规则；保存旧规则版本，日志不记录 token/服务账号密钥。
3. 需要时仅部署已通过 Emulator 的 Firestore 规则到明确项目；不顺带部署 Storage/Functions/Hosting，不删除 registry/head。
4. 受控最小客户端请求验证权限，不能用管理员控制台访问替代，也不能把 Emulator 通过当生产通过。
5. 经授权从同一代码构建签名兼容的 EXE/APK，保留标识和路径；升级两端，迁移期间关闭旧客户端。
6. 电脑先保存、同步实际日常知识库，手机再点击同步；逐项核对专题、结构、笔记、引用和回收状态。
7. 再做电脑新增/修改/移动/删除→手机同步；重启两端复查，重复空同步不出现新副本。
8. 用隔离测试专题验证手机离线编辑、电脑并发编辑及冲突保全，不破坏真实笔记。

## 6. 必须实现的回归清单

### 主流程 FLOW

- FLOW-01：一份非空电脑本机库+空云，一次点击上传；原地绑定与冻结导入各有正向证明。
- FLOW-02：空手机发现、拉取；无第二默认库，云 head 不因纯拉取增加。
- FLOW-03：首次成功后电脑再次编辑，再次同步和重启仍使用正确目标。
- FLOW-04：树、顺序、笔记、引用备注、删除/恢复一致，不删除原日志。
- FLOW-05：两端无更改时重复同步，实体/命令/库数量不增长。
- FLOW-06：已有空账号库+非空本机库，自动同步真实内容，不停在空库。

### 接管 MIG

- MIG-01：多普通库全纳入，恢复/受保护/其他 UID 排除。
- MIG-02：每个阶段崩溃重开，沿同一冻结 session 继续。
- MIG-03：双窗口/重复点击只有一份接管；过期执行者不能写新流程。
- MIG-04：冻结前、中、后的交错编辑无丢失，失败输入/草稿可恢复。
- MIG-05：双端同源同快照真实生成命令 ID、顺序、hash 一致，receipt 消重。
- MIG-06：同名不同源与同源分叉不错误覆盖，不复用 ID 写不同 hash。
- MIG-07：历史 active/completed 复制正确处理，源有后续编辑不误判已同步。
- MIG-08：guest 认领、备份 scope、退出登录及晚回调不越界。
- MIG-09：升级失败回滚、重开幂等，新增绑定元数据不泄漏进可移植导出。
- MIG-10：坏历史/缺 head/身份矛盾停止，不替换默认库或清理来源。

### 网络与并发 NET

- NET-01：同时首传仅一个注册胜者，另一端安全汇入。
- NET-02：云已提交但丢响应，重启核对回执，不生成新 ID。
- NET-03：缺包不跳 cursor；超时/运行失效后晚回调不覆盖新状态。
- NET-04：两端不同节点编辑收敛，同字段冲突保全双方并提示处理。
- NET-05：纯拉取无新 dirty；日志先后到达不导致引用被删除。
- NET-06：100/500/1000步有界提交、规则预算、分页、进度、中断续传有效。

### 权限及 UI

- AUTH-01：当前 UID 全链路通过，未登录/其他 UID 被拒绝。
- AUTH-02：不完整事务、旧 head、不可变行重写、超预算被拒绝；普通日志规则不回归。
- UI-01：日志成功+知识失败为部分失败；pending、blocked、未解决候选分别统计。
- UI-02：普通冲突/预算阻断后知识未执行；解决后继续同一意图。
- UI-03：正常路径无选库/复制；恢复入口可达，窄屏和返回行为正确。
- UI-04：导航和创建不再依赖数组顺序，过期编辑提交保留输入。

## 8. 发布和回退边界

- 保留现行 `request.auth.uid` 所有权校验，不写死用户凭证，不以全开放规则解决错误。
- 规则回退恢复访问配置，不删除已同步数据；已发布导入不能靠清 head/删 registry/整库覆盖回滚。
- schema 升级后不默认允许旧安装包降级打开数据；优先发布同 schema 的前向修复/禁用自动接管版本。
- 旧客户端不理解新冻结标记，不宣称它能与新接管同时写同一数据库；迁移期间必须关闭旧版本。
- 原库保全不是永久垃圾清理授权，本次不自动删除来源。
- 未经单独授权不部署、不覆盖安装、不读写真实账号或批量上传真实内容。
