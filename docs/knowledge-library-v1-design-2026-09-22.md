## 1. 用户看到的 v1

### 1.1 大纲与导图

同一份专题结构提供两种视图：

- 大纲：默认阅读和整理视图，支持展开/折叠、稳定滚动、路径定位、批量选择和“移动到”。
- 导图：用于观察结构和分支移动，支持二维平移、放大/缩小、恢复 100%、聚焦分支、查看全图和搜索定位。

视图只是投影，不保存两套结构。导图的缩放、平移、选中、临时展开、视口和布局缓存是设备本地状态，不同步、不进入正式备份事实。

### 1.2 浏览态与整理态

工作区默认是浏览态：单击节点只选中并显示只读详情；点击明确的日志链接才打开日志；不使用双击或长按直接进入文字编辑；拖动画布只平移，不改变节点父级。

用户点击“整理”后进入整理态：显示节点拖动把手、移动到、编辑和删除入口；标题、说明、引用备注通过明确按钮进入编辑；节点拖动、画布平移和文本编辑互斥；拖动超过阈值后抑制点击；pointercancel、失焦、切后台或 Android Back 可取消未提交操作。

移动节点与建立语义关系是两种不同动作。v1 只做同专题内分支移动；“前置/对比/应用”等跨分支关系留给后续知识图谱层。

### 1.3 紧凑节点

导图使用紧凑圆角矩形节点，不把长批注或日志正文直接铺在画布上。默认显示一到两行标题、子节点数、日志引用数以及有说明/备注的状态标记。

完整说明、引用备注和日志列表进入 desktop 侧栏或 Android 底部详情/详情页。大纲按行显示，按需展开详情。不能用把字体缩到不可读的方式声称“全图可读”。

### 1.4 工作区内搜索

- desktop 在知识库工作区按 Ctrl+F；Android 使用显式搜索按钮。
- 默认搜索当前专题内的节点标题、节点说明、日志标题和引用备注；折叠分支也参与搜索。
- 可选“包含关联日志内容”，再搜索原日志正文和已有 OCR 文本。
- 显示匹配数量，支持上一项/下一项、Enter/Shift+Enter；命中时临时展开祖先并定位。
- 关闭搜索恢复搜索前的视口和临时展开；搜索状态属于设备本地 UI 状态。
- 日志编辑器、输入框和弹窗优先处理自己的快捷键，不能被导图层抢走。

## 2. v1 数据模型

### 2.1 不使用一张大导图 JSON

不能把整个专题序列化成一条大型 JSON 并作为一个同步实体。否则两端各自改不同节点也会形成整图冲突，一端移动节点会覆盖另一端新增节点，删除一处可能把另一端内容一起抹掉，旧客户端也可能把未知数据当成空数据发布。

v1 采用稳定 ID 的小实体。每个实体的字段范围要小，避免把互不相关的操作放进同一 payload。

### 2.2 推荐逻辑实体

实际 Dexie 表名和 schema 版本在实施前另行定稿。

#### KnowledgeWorkspace

表示一个专题入口：id、title、description、archivedAt、createdAt、updatedAt、schemaVersion。

专题删除首期实现为归档或软删除，不物理级联删除子节点和引用，避免跨端删除与离线新增互相抹除。

#### KnowledgeNode

表示可展示的节点内容，不直接表示屏幕位置：id、workspaceId、kind（section 或 text）、title、body、createdAt、updatedAt、deletedAt、contentRevision。

kind 创建后不可修改；标题和说明是节点内容，不把展开状态、颜色、图标或坐标写入同步实体。

#### KnowledgePlacement

表示一个节点在专题树中的一次展示位置：id、workspaceId、nodeId、parentPlacementId、orderKey、createdAt、updatedAt、deletedAt、conflictState。

节点身份与展示位置分开，既允许未来同一知识节点出现在多个分支，也允许双端同时移动时保留两个合法位置，避免一个位置静默覆盖另一个位置。

v1 默认把一个节点显示为一个位置；发生并发移动时，第二个位置作为“待处理重复位置”显示。

#### KnowledgeRecordReference

表示节点对现有日志的引用：id、workspaceId、placementId、recordId、orderKey、remark、createdAt、updatedAt、deletedAt、conflictState。

不复制 RecordBlock 标题、正文或资源。引用缓存只能作为可重建的显示缓存，不能作为内容真源。

#### KnowledgeConflictItem

表示无法安全自动合并但已保留下来的待处理项：id、workspaceId、entityType、entityId、conflictKind、双方值或快照、createdAt、resolvedAt、resolution。

它不是新的学习事实，不进入日志正文、复习或 AI Coach。解决后可保留最小审计信息或软删除待处理项。

### 2.3 顺序与布局

子节点和引用不使用共享数组。每个 placement/reference 使用可排序的 orderKey：在两个元素之间插入时生成中间 key；key 空间过窄时只在该父级内重排；同一 key 冲突时用稳定 ID 作为确定性 tie-breaker；排序修复只更新受影响的子项。

导图坐标不写入云端。布局由 workspaceId、placementId、parentPlacementId、orderKey 确定性计算；缩放、平移和布局偏好留在设备本地。两端不会因为窗口大小不同产生布局冲突。

## 3. 写入语义与防误操作

### 3.1 所有组织操作是小而明确的命令

UI 不直接提交整棵树，而是提交以下原子操作之一：创建专题；创建节点和初始 placement；修改一个节点标题或说明；创建/修改/删除一个日志引用；移动一个 placement；调整一个 orderKey；归档/恢复专题、节点或引用；创建/解决冲突待处理项。

每个操作在本地 Dexie 事务中完成，更新相应实体和本地 mutation epoch 一次。普通浏览、搜索、平移、缩放和展开不写数据库，不触发云同步。

### 3.2 移动提交规则

整理态从拖动把手或“移动到”菜单开始；目标必须是合法专题/父 placement；禁止拖到自身或后代；提交前再次检查目标存在；一次事务写入新的 parent/order 并保留旧版本信息；撤销只反向当前仍匹配的那次移动，不能覆盖之后的远端修改。

## 4. 同步架构：知识库与普通同步解耦

### 4.1 最重要的兼容性决定

v1 不把知识库实体直接混入现有普通 CloudSyncExport.entities 集合，除非同时完成旧客户端保护。

当前普通同步基于本机快照、ledger、内容 hash、云端 revision 和删除墓碑推导变化；未知实体如果从旧客户端快照中缺席，可能被推导成删除墓碑。这对已上线但不认识知识库的旧 Android/desktop 客户端构成数据风险。

推荐采用独立 Knowledge Sync Channel：独立云端命名空间、独立 head revision、独立 ledger/operation 状态和独立锁；共享用户身份和鉴权，但不共享实体集合。

普通日志同步继续处理既有实体；知识库同步只处理 KnowledgeWorkspace、KnowledgeNode、KnowledgePlacement、KnowledgeRecordReference 和冲突项。

如果实施阶段必须复用现有服务，必须先实现 capability fence：云端标记 requiresKnowledgeLibraryV1 后，不支持该能力的旧客户端只能读取普通数据，不能发布会省略知识库的快照，也不能执行“以本机覆盖云端”。没有这道保护，不允许把知识实体加入现有集合。

### 4.2 两个 channel 的关系

- 普通 channel 负责 RecordBlock、标签、复习、每日计划、Coach 正式事实等既有实体。
- Knowledge channel 只保存组织关系和组织文字。
- 两者只通过 recordId 弱引用连接，不在同一个写事务中强绑定。
- 普通日志修改不会改写 KnowledgeReference；知识库修改也不会触发普通 block 的云 mutation。
- 日志软删除后，引用显示“日志已移入回收站”；恢复后自动恢复可打开状态。
- 日志永久删除后，引用变成失效引用/待处理项，不静默删除专题结构和备注。

这样，Android 修改知识结构、desktop 修改日志正文时，不会因为写入不同实体集合而形成一个巨大的跨域冲突。

### 4.3 复用可靠性机制，不复用整库替换语义

Knowledge channel 可以复用现有成熟机制：每实体内容 hash、deviceId、云端 head revision、ledger 中的共同 payload、operation journal、超时后的 uncertain/reconcile、写后重读核对、删除墓碑，以及锁内重读后提交。

但不能把知识库冲突处理成“local 或 cloud 二选一”的整库恢复。现有整库恢复只适用于用户明确选择的恢复/迁移操作，不应成为知识库的日常冲突 UX。

## 5. 冲突策略

### 5.1 不同实体或不同字段：自动合并

Android 修改节点 A、desktop 修改节点 B；一端修改标题、另一端修改说明；两端新增不同日志引用；两端移动不同节点；一端修改引用备注、另一端修改另一条引用顺序；一端改普通日志正文、另一端改引用备注：均自动合并。

合并依据实体 ID 和字段级三方比较；更新只写双方实际变化字段。引用正文不复制，所以日志正文与引用备注天然隔离。

### 5.2 同一字段同时编辑：保留双方，不阻塞整库

两端同时修改同一节点说明时，不使用最后写入者覆盖，也不自动拼接可能错误的文本。

处理方式：把双方版本写入 KnowledgeConflictItem；当前节点保留确定性主版本并标记待处理；另一版本可查看、复制或选择；用户选择本地、远端或手工合并后生成新的明确写入；冲突记录也进入 Knowledge channel。

同步状态显示“已同步，1 个知识库项目待处理”，不因为一个节点的文字冲突阻塞整个知识库。标题、说明、引用备注使用不同合并单元，减少冲突面。

### 5.3 同一 placement 同时移动：保留两个位置

两端离线把同一个展示位置移动到不同父级时，不采用 last-writer-wins。将双方结果物化为两个 placement，其中一个标为 duplicate-placement；节点内容、日志引用和备注仍只有一份，两个位置均指向同一 node。

导图默认显示主位置，另一位置显示“存在另一处位置”标记。冲突中心提供“保留此处”“保留两处”“合并为别名/引用”。保留两处是安全默认，因为重复可见、可修复；静默丢掉一处不可恢复。

### 5.4 删除与编辑并发：不级联抹除

删除节点/引用是墓碑，不立即物理清除。若另一端基于共同旧版本编辑，形成 delete-edit 冲突；编辑版本保留到冲突项或孤儿区域，删除方墓碑继续保留。用户可以恢复、保留删除，或把编辑内容放到新节点/引用。

专题首期只做软删除/归档。物理清理需确认没有未解决冲突和活动设备引用，并经显式永久删除流程执行。

### 5.5 父节点删除、子节点离线新增：进入孤儿区

不做数据库级联删除。父 placement 失效而子 placement 仍存在时，保留子节点及日志引用，标记 orphaned，在专题的“待处理结构”展示，可移动到新父节点或恢复父节点。

### 5.6 同一日志多处引用不是冲突

同一 recordId 在不同专题、不同节点被引用是合法状态，不做唯一约束。只有同一个 KnowledgeRecordReference.id 被两端同时修改，才按引用实体冲突规则处理。

## 6. 同步流程

1. 先核对上一次 Knowledge operation；结果不确定时只 reconcile，不启动新写入。
2. 读取本机 channel state、ledger 和当前实体快照，推导本机变化和墓碑。
3. 读取云端 head/revision 及增量变化。
4. 在内存中按实体策略合并：字段合并、移动双位置、delete-edit、孤儿保留。
5. 获取 Knowledge lock 后重新读取 head、ledger 和本机 mutation epoch。
6. 若等待锁期间本机发生变化，放弃本次提交并重新计算，不覆盖新改动。
7. 写入合并实体、冲突项和必要墓碑；每个写入带 expected hash/revision。
8. 写后重读云端确认；超时返回 uncertain，下一次先核对。
9. 云端确认后更新本机 ledger，保留仍未确认的本地 mutation。

日常同步不自动整库覆盖，不调用普通 local/cloud restore。整库替换只用于用户明确选择的恢复/迁移，并单独显示普通数据和知识库范围。

## 7. 旧客户端、升级与恢复

### 7.1 旧客户端保护是上线前置条件

知识库首次同步到云端后，必须保证旧版不会因快照缺少知识实体而生成知识删除墓碑。独立 Knowledge channel 是首选；如果做不到，服务端必须设置 capability fence：支持客户端声明 knowledge-library-v1；存在知识数据时旧客户端发布被拒绝并提示升级；旧客户端不得覆盖云端或清空未知知识数据。

不能只依靠前端版本号，因为 Android 与 desktop 可能安装不同版本。

### 7.2 备份与恢复

全量普通备份增加明确的 knowledgeLibrary 段，包含知识实体、墓碑和格式版本；不复制日志正文，只保存 recordId。

- 旧备份没有 knowledgeLibrary 字段：恢复普通数据时保留当前设备知识库，不清空。
- 新备份明确包含空段：才表示备份时知识库确实为空，并允许按恢复流程清除知识实体。
- 恢复前分别显示普通日志和知识库结构的范围。
- 单条日志传输默认不携带整座知识库；引用目标不存在时保留失效引用。
- 恢复后重建搜索和反向引用索引，不把索引作为不可信输入直接恢复。
- 不可信备份输入执行完整性、引用形状、无环和实体 ID 校验。

Knowledge channel 的 recovery snapshot 独立保存；普通云同步恢复点不能被误认为包含知识库。以云端为准恢复时，分别显示普通学习数据、知识库结构和本机未同步知识修改的处理方式。

## 8. 检索与扩展

全文/OCR/专题结构检索使用本地可重建索引。索引不进入云同步实体，不作为备份真源，也不参与冲突判断。

索引记录来源类型和稳定 ID、当前内容版本/hash、workspace/placement/reference 路径、命中来源和可生成的上下文片段。

v1 统一查询接口供全局搜索、专题/分支搜索、Ctrl+F 图内查找、添加日志和批量整理选择器复用。支持关键词、学科、标签、日期、收藏、资源类型和专题/分支范围。

未来知识图谱、混合检索、RAG 和个性化 AI 可以接入同一查询接口，但必须明确用户选择的范围、返回可回溯来源、分开检索证据与生成建议，且不能自动修改原日志、复习状态、Coach 任务或每日计划。

## 9. 实施顺序

### Phase A：数据与同步安全底座

1. 定稿实体契约、ID、墓碑、版本和引用校验。
2. 决定并实现独立 Knowledge channel 或 capability fence；没有这一步不进入 UI 开发。
3. 设计本地事务、ledger、operation、expected hash/revision 和重试核对。
4. 设计字段合并、移动双位置、delete-edit、孤儿和冲突中心。
5. 定义备份段、旧备份缺字段保护和恢复范围确认。

### Phase B：无导图依赖的大纲闭环

专题首页、待整理、全部日志查询；创建专题、节点、文字节点、日志引用和备注；大纲浏览、展开折叠、移动到、批量加入、冲突/孤儿入口；从日志进入专题、从专题进入日志并恢复上下文；Android 与 desktop 完成核心操作。

### Phase C：检索与导图投影

统一查询服务和可重建本地索引；Ctrl+F/Android 搜索；紧凑导图、缩放、平移、聚焦和只读浏览态；整理态拖动把手、移动预览、取消、撤销和手势验收。

### Phase D：验收

覆盖旧数据迁移、升级、旧备份恢复；两端离线并发新增/编辑/移动/删除；网络中断、写入后未确认、重复点击同步；普通日志与知识库同时修改；回收站、永久删除、失效引用、孤儿恢复；Android 手势、系统返回、输入法和桌面触控板；quota、operation reconcile、恢复点、备份完整性；既有测试、新增确定性测试和 Firebase Emulator 场景。

## 10. 关键验收场景

| 场景 | 预期 |
| --- | --- |
| A 改节点 A，B 改节点 B | 自动合并，无整库冲突 |
| A 改标题，B 改说明 | 字段合并，无冲突 |
| A、B 同时加不同日志引用 | 两条引用都保留 |
| A、B 同时移动同一 placement | 两个位置均保留，标记重复位置 |
| A 删除引用，B 修改备注 | 不静默丢备注，生成 delete-edit 待处理项 |
| A 删除父级，B 在其下新增子节点 | 子节点进入孤儿区，内容可恢复 |
| A 修改日志正文，B 修改引用备注 | 无冲突，双方都保留 |
| 同步期间本机继续编辑 | 本次提交放弃或重算，不覆盖新编辑 |
| 云端已写入但本机超时 | 标记 uncertain，下次先核对 |
| 旧客户端遇到知识库数据 | 独立 channel 下普通同步不受影响；能力栅栏下拒绝危险发布并提示升级 |
| 旧备份没有知识库段 | 恢复普通数据时不清空当前知识库 |

## 11. 必须避免的实现方式

- 不把整棵导图作为单个 JSON 实体。
- 不把坐标、缩放和折叠状态作为正式同步数据。
- 不把 RecordBlock 正文复制到节点或引用中。
- 不用最后写入者覆盖解决同一字段冲突。
- 不用删除节点级联删除子树、引用或原日志。
- 不让普通旧客户端发布一个缺少知识实体的完整快照。
- 不把普通同步的 local/cloud 整库二选一恢复当作日常冲突处理。
- 不让搜索索引成为云端真源。
- 不让知识库组织关系改变复习、AI Coach、每日计划或其他正式学习语义。

## 12. 实施前仍需确认

1. Knowledge channel 是独立 Firestore 集合/文档，还是现有协议的 capability fence；旧客户端安全问题解决前不得实现同步。
2. 冲突项保存双方快照还是独立版本实体，需要评估隐私和存储量。
3. 同一 node 的多 placement 是否在 v1 UI 直接作为别名支持，还是仅用于冲突恢复。
4. 专题、节点删除和日志永久删除后的清理周期。
5. 旧客户端遇到 Knowledge channel 后是否继续普通同步，取决于独立 channel 的验证结果。
6. Android 导图渲染、触控阈值和 desktop 触控板快捷键，需要原型和真机验收后冻结。

## 13. 结论

第一版不是一个可以随意画框的白板，而是：用稳定 ID 的专题、节点、展示位置和日志引用组成可重建的知识目录；用紧凑大纲/导图浏览；用统一检索找回内容；用独立 Knowledge channel 和保留双方的冲突策略保护多端数据。

上线顺序不是先做漂亮导图，而是先证明普通日志不会被知识库改写、旧客户端不会抹掉知识库、双端离线编辑不会静默丢内容、超时同步不会重复破坏数据、备份恢复不会清空未知字段。
