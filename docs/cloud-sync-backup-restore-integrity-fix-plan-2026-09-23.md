## §2 逐项修复设计

### 2.1 `#1` 存储 GC 可不可逆删除在用资源（P1，最优先）

**病灶**：

- `:424` `parseRemoteState` 把非数字 `headRevision` **静默归零**，无任何可观测信号；
- `:2061` `protectedActiveCount` 只做成本闸门计数（`:2064`），**与实读集不比对**；
- `:2067` `active` 来自容错读 + `:1111` `revision <= headRevision` 过滤 —— 与归零后的 head 共享同一个错误值；
- `:2074-2077` 判 `stale` → `:2081-2084` `deleteObject`，**删除侧零覆盖回归**。

**触发画像**：`collectSnapshotEntities`（`:1985-1992`）直读子文档、不过 head 过滤，但恢复快照**只在冲突解决 / legacy 迁移路径产生**（`:2197`/`:2261`/`:2957` 一线；`synchronizeCloudChanges` 正常同步**从不**产生快照）。⇒ **无冲突历史或快照陈旧的账号 `snapshots=[]`，保护集为空，state 异常即全删；有近期快照的账号 = 删除快照之后的增量**。

**第二条删除路径（`#1b`，此前未被识别）**：滞留文档（`revision > headRevision`）不只是一处「计数失配的来源」，它**本身就是一组受不到保护的引用**：

- `:2069` `referenced = [...active, ...snapshots]` —— 只含 `revision <= headRevision` 的文档；
- 而 `publish` 的顺序是 **`:1876` 先 `uploadAssets`（资产已进 Storage）→ `:1884` 才写实体元数据**；
- ⇒ 崩在 `:1884` ~ `:1900` 之间时，**资产在 Storage、引用它的实体文档在 head 之上** ⇒ 不进保护集 ⇒ 判 `stale` ⇒ **被删**。

这条路径**不需要畸形数据、也不需要 state 异常**，与 `#3b` 是同一个结构论证。

**修复（三判据，缺一不可）**：

| 判据 | 条件 | 动作 | 对应形状 |
|---|---|---|---|
| ① 状态不可信守卫 | **任一成立即跳过**：(a) state 被标记为不可信；(b) `protectedRemote.exists && protectedActiveCount > 0 && active.length === 0 && 无 head 之上文档` | 跳过删除 | 归零 |
| ② 同谓词计数自检 | 以 `where("revision", "<=", headRevision)` 重新计数，`≠ active.length` | 跳过本轮删除并告警 | 容错丢弃 |
| ③ 扩保护集 | 把 `revision > headRevision` 的文档**也纳入 `referenced`** | 不跳过，正常清理 | `#1b` 滞留文档 |

**判据 ① 的 state 不可信来源**：`:424` 的归零路径改为**可观测** —— 保留容错（**不抛错**：`parseRemoteState` 在每次同步都会调用，抛错会让整个同步不可用，属功能停摆），但把「本应是数字却不是」标记为不可信标志传入 GC，由 GC 在删除侧 fail-closed。

**为什么必须三条，而不是「计数不相等就跳过」一条**：

- 若只比较 `active.length !== protectedActiveCount`：两者谓词不同（`:2061` 无谓词 vs `:1111` 有谓词），**只要存在任何未确认写入的文档，该等式永久不成立** ⇒ 清理功能在这些账号上**永久停摆**。这违反 §0 纪律第 5 条。
- 判据 ② 与读取共用同一个 `headRevision`，因此当 head 是「数值合法但取值错误」时两侧一致、②**不会**报警；此时落在错误 head 之上的文档仍被排除在保护集外。**判据 ③ 是唯一覆盖该形状的判据**，而形状 `#1b` 是**已证可达**的常态故障态。
- 判据 ③ 使 ① 的 (b) 分支成为冗余（head 归零时补集即全集，保护集自然完整），但 (a)/(b) 仍保留：成本极低，且能在查询超时/失败时提供早退。

**实现要点**：

1. 判据 ③ 优先**复用 `getAllRemoteDocuments` 已读到的结果**，避免额外往返；若必须新增读取，使用现成的超时封装，且**超时后不得继续删除**（按 `deferred-cost` 处理）。
2. 判据 ③ 的口径取 **`revision > headRevision`（无界）**，不取 `(headRevision, nextRevision]` —— 前者更严，且不依赖 `nextRevision` 这个同样可能损坏的字段。
3. 判据 ② 的计数查询使用单字段范围过滤，无需复合索引。
4. 三条判据**只影响删除决策**，不影响其余同步流程。
5. 手动维护入口（界面上的强制清理）必须**同样**受三条判据保护。

**回归**：先修 §0 纪律第 4 条的桩；新增 `N2-1..N2-4` 四类用例（见 §3.2），全部先对未修代码证红。

**成本**：约 1 行自检 + 1 处集合扩展 + 桩修正 + 4 用例。

### 2.2 `#2` 附件 MIME 豁免改为对称（P1，最易命中）

**病灶**（`assetIntegrity.ts:86`）：

```ts
if (declaredMimeType && declaredMimeType !== UNKNOWN_MIME_TYPE && actualMimeType && declaredMimeType !== actualMimeType) {
  return { reason: "mime", declaredMimeType, actualMimeType };
}
```

豁免只看 declared 侧。上传侧写 `contentType: blob.type || "application/octet-stream"`（`:33`/`:37` 定义该兜底值）⇒ **字节与哈希完全匹配**的对象，只要两侧类型不对称，就判违例。唯一校验点在 `cloudSyncService.ts:1309`，增量 `applyRemote`（`:1399`）复用同一路径 ⇒ 单个资源可致**账号级永久同步失败**，且为**全路径统一**（非增量独有）。判定发生在落盘之前，**没有跳过入口**。

**修复**：改为对称豁免 —— 任一为通用兜底值即放行：

```ts
if (declaredMimeType && actualMimeType
  && declaredMimeType !== UNKNOWN_MIME_TYPE && actualMimeType !== UNKNOWN_MIME_TYPE
  && declaredMimeType !== actualMimeType) {
```

**判定语义**：通用兜底值的含义是「类型未知」，未知不构成矛盾；**两侧都是具体类型且互不相同**仍然是真实的元数据违约，必须继续拒绝。

**回归**：hash 相同、declared 为兜底 / actual 为真实类型（及镜像方向）必须通过；双向真实且不一致必须**仍失败**（防止过度放宽）。

**成本**：1 行。

### 2.3 `#3` + `#3b` 假 `complete` 宣告（P1，数据损坏；两条同批修）

**病灶**：`replaceCloudWithLocal`（local-wins 冲突分支）**不经过** `:2716` 的间隙守卫（那是全源码唯一调用点）：

- `:2225` 容错读 `getAllRemote` → 畸形文档与 `(headRevision, lock.revision]` 滞留文档被丢弃；
- `:2261` 用丢弃后的数组建「冲突前的云端版本」存档 → `:1949`/`:1960`/`:1962` 的 `entityCount` 就是过滤后长度，`complete: true` 直接打标；
- `:1973` 回读校验拿计数**与自己比** —— 自证循环，恒真。

**`#3b` 可达性（结构证明，无需畸形数据）**：`publish` 的实体批 `:1884-1892` 与 head 推进 `:1900` → `:1483` 是**两次独立写**，中间无事务绑定（`metadataCommitted` 于 `:1867`/`:1893` 正是为部分提交建模）。一次发布中断即在云端留下 `(headRevision, lock.revision]` 文档 → 下次 local-wins 存档必然漏掉它们 → 假 `complete` → 该存档可被恢复到本机并推进游标。

**修复原则（关键）**：**不要在 `:2225` 加 strict。** 云端已坏时 local-wins 正是用户的**逃生门**，加 strict 会把门也锁死。严格解析只适用于「云端→本机」的四条替换入口。

**修复**：保持容错读取，在创建存档前做**两道证明**：

| 证明 | 内容 | 目的 |
|---|---|---|
| ① 覆盖自洽 | 实读条数 == 同谓词权威计数（`getCountFromServer`，与读取同谓词 `revision <= headRevision`） | 排除容错解析丢弃 |
| ② 无未确认写入 | 不存在 `revision > headRevision` 的文档（可复用 `hasRemoteRevisionsBetween`，**注意其早退条件** `beforeRevision <= afterRevision + 1` ⇒ 直接复用需传入足够大的上界；或用等价计数实现） | 排除会漏进存档的滞留文档 |

- 两道全过 → 照常建 `complete: true` 存档（**零退化**）；
- 任一不过 → **跳过创建存档**，主操作（local-wins 覆盖）**继续**，界面出 warning；
- **绝不写 `complete: false`**：升级前的客户端在列出恢复点时只读标识、时间、标签与条数，**不读**完整性字段，因此该标记对它们无效 —— 存档照样被列出、照样可恢复。**唯一有效的做法是让不可信存档根本不进入快照集合。**

**回归**：常驻的 `F-A-1`/`F-A-2`（`it.fails`）转绿后改写为正向断言（§0 纪律第 3 条）；`CONTROL` 用例保持。

**成本**：≤3 行逻辑 + warning 透传。

### 2.4 `#4` 增量容错丢弃仍推进 complete 游标（P1；`#3` 宣告的供给方）

**病灶**：`getRemoteChanges` 在 `:2745` 容错解析后，`:2770-2776` / `:2780-2783` **无条件**推进 `lastPulledRevision` 与 `remoteDatasetCompleteThroughRevision`。「本机已持有截至 R 的完整云端数据集」这句宣告，可以建立在一条被静默丢弃的坏文档之上 —— 之后的任何 complete 存档都从这条被污染的游标取数。

**修复**：`getRemoteChanges` 回报 `droppedCount`；仅 `droppedCount === 0` 时才传 `completeThroughRevision`（**冻结完整性宣告**）。`lastPulledRevision` 的推进**不受影响**，增量兼容性保持。

**必须说明的设计后果**：冻结完整性宣告后，下一次同步会退回**完整校验路径**，而完整校验是 fail-closed 的 ⇒ 畸形的云端数据会在**破坏性入口被判拒**（用户被告知，而不是被静默丢弃）。这正是期望行为，且逃生通道是「以本机为准」（该路径按 §2.3 刻意保持容错）。**不得**为了「让同步总能通过」而放弃这条冻结。

**与 `#3` 的关系**：两者同属「完整性宣告」这一个病灶，`#4` 是供给方、`#3` 是承载与落地方，**必须同一提交批次、同批验收**。

**回归**：一条畸形增量文档 ⇒ `lastPulledRevision` 前进、`remoteDatasetCompleteThroughRevision` **不动**；全良构 ⇒ 两者同进。

**成本**：1–2 行。

### 2.5 `#5` 大文本合并基线 `{}` 被当真值（P2）

**病灶**：`cloudSyncModel.ts:286-288` 的 `withCloudPayloadDocument` 把 >750KB 的外联 `payload` 实体在账本里记成 `basePayload: {}`（`persistLedgersInTransaction:1736-1738`）；`{}` 是**真值** ⇒ 冲突合并时「本机无基线」被误判为「基线为空对象」，不走「无共同祖先 ⇒ 实体级冲突」，而走三方合并 ⇒ 双方全字段视为已改 ⇒ 分歧必判全采云端，远端已删字段可复活。可达性未实测（阈值长模板可达），机理已回源码确证。

**修复**：落账本时把空 `basePayload` 视为 `undefined`（`Object.keys(entity.payload).length ? entity.payload : undefined`，1 行），使外联大实体走「无基线」分支。

**回归**：>阈值 settings/template 冲突 ⇒ 不再「基线 = `{}` ⇒ 全采云端」；普通小实体合并行为**不变**。

### 2.6 `#6` 次级项（各自小提交）

- **`#6a`（P2）**：`:2703-2713` legacy zip 迁移在 strict 体外，直接进 `restoreCloudSyncSnapshotIfUnchanged`。容器自带的逐对象字节校验仍然生效，缺的是「该文档是否声明自身完整」的分类判定。**修复**：迁移入口前补一次完整性分类校验；对分类为「不可验证」的旧存档按 `legacy-unverified` 语义处理，**不阻断**（见 §5.1）。
- **`#6b`（P2）**：`(headRevision, lock.revision]` 未确认写入会卡在 `:2716` 抛 Error（非 `kind: "conflict"`），普通同步无法推进。逃生路径结构存在（冲突解决路径绕过守卫后经 publish 越过孤儿文档），但 UI 可达性未证。**修复**：错误文案改为**可操作指引**（明确「等待对端完成发布，或走一次冲突解决」），并在文案指向设备不可用时给出冲突解决入口；同时复核该守卫的适用范围是否应扩展到其它写入路径。是否降级为 `kind: "conflict"` **留待第 0 步预演观察后再定**。
- **`#6c`（P2/C）**：快照回收按墙钟 `createdAt` 排序（`:88` `SNAPSHOT_LIMIT = 3`；`:2056`/`:2122` `orderBy("createdAt","desc")`；`:2128` `expired = slice(3)`；`:1957` 取本机墙钟）⇒ 时钟偏斜设备新建的恢复点可被**立刻回收**。**修复**：排序键改用服务端时间或 Firestore `__name__` 单调序，使偏斜设备只可能被回收「最老」而非「最新」。
- **`#6d`（C）**：`:3011-3023` catch 回退 legacy zip。触发需**竞态**（`:2924` 判过后、`:2292` 重读前状态变化）+ 存在 legacy zip **双门控**；且 `restoreRemote` 的自身守卫（`:2293`）位于其严格校验（`:2298-2299`）**之前**，说明该 catch 的设计意图本就是 zip 回退。**修复**：**只加一行注释** —— 「此 catch 仅用于回退 legacy zip，不得吞掉 strict 校验拒绝」，并在第 0 步预演中顺带观察。

## §5 残余风险与未决项

1. **升级前生成的残缺存档无法追溯识别**。正常存档与残缺存档的父文档字段形态一致（条数即其残缺数组的长度），因此严格校验对其自洽。建议按 `legacy-unverified` 语义**允许恢复、不作追溯**；若改为一律禁止恢复，会同时废掉全部历史回滚点。
2. **`#1b` 的危害是否可自愈未实测**。本机仍持有这些对象的副本，下一次发布可能重新上传；因此后果可能是短暂的缺档，也可能对**另一台**设备造成下载失败。当前不单列缺陷，仅作为判据 ③ 的设计依据。**标 `[码]`/`[?]`。**
3. **「`headRevision` 数值合法但取值错误」的可达性未证明**。判据 ③ 对它是有效的，但该形状本身尚未获得判别性证据。
4. **`#5` 的阈值形状、`#6d` 的竞态形状**均未实测可达性。
5. **`#1` 的手动维护入口**会绕过自动模式的成本限制，实施前需确认它是否也受三条判据保护 —— 按本方案**应当同样受保护**。
