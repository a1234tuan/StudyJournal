## 1. 一句话核心意图

**把日志从「事后记录」升级为「意图的兑现凭证」**：早上用最轻的方式承诺（一行计划），执行时在同一个日志原语里兑现，事后靠「计划这一行」长期留痕，去做统计与 AI 反馈，同时不改变日志的任何既有能力。

不是要一个待办清单：计划刻意是退化的——只有 学科 + 标题 + 日期 + 完成/未完成，没有优先级、没有截止日、没有任务状态机。

## 2. 三条设计原则（推断）

1. **一扇门不够，但只有一个房间。** 计划不是新的内容类型，只是日志的第二个入口；计划里长出来的日志与自由日志**在数据上完全等价**（用户第 5 条）。
2. **承诺留痕，未兑现的过程不留痕。** 计划标题是承诺，必须活过第二天；「点进去但没写」那次尝试不留任何痕迹。
3. **AI 只反馈「意图 vs 兑现」，不碰正式学习状态。** 计划数据进驾驶舱属于元数据层分析，不是新的学习事实。

## 4. 确认后的最小数据形态

- `DailyPlan`：`date` / `subject` / `title` / `order` / `linkedRecordId?`。**完成状态由「是否存在未删除的日志记录」推导，不单独存 `status` 字段**——这样不存在「状态与事实不一致」的可能。
- `RecordBlock`：只增加一个反向引用（`planId?`），用于「来自计划」标识与归属查询。
- **不预生成空日志**（已确认）：创建计划只写 `DailyPlan` 一行；用户点进计划并保存时才创建 `RecordBlock`，同时回填 `linkedRecordId`。
- 由此产生的一个直接好处：**不需要 `isDraft` 草稿态字段**，也不必改动 6 处记录消费方的过滤逻辑（审计 F-6 因此不成立）。计划与日志之间是「0 或 1 条」的关系，不存在任何中间态。

## 5. 第 4c「AI 驾驶舱联动」的可行分层

现有驾驶舱的事实链是 `记录正文 → 决策块 → 反馈 → 解读 → 训练任务 → 结果事件 → 延迟验证`；上下文服务（`src/services/aiContextService.ts`）喂给模型的只有**日志正文与决策块**，没有任何 prompt 见过计划元数据。所以「计划数据进驾驶舱」需要分三层看：

| 层 | 内容 | 是否需要模型 | 是否可在 StudyJournal 内做 |
| --- | --- | --- | --- |
| L0 确定性统计 | 完成率、连续完成天数、学科分布、计划数 vs 完成数 | ❌ | ✅ 现在就能做，属于纯派生计算 |
| L1 派生洞察 | 「周末完成率高于工作日」「某学科完成率偏低」 | ❌（规则引擎） | ✅ 可以做，但必须标注为派生洞察，不是学习结论 |
| L2 模型反馈 | 让模型据计划完成度给出建议/追问 | ✅ | ⚠️ 需要新的版本化 prompt 与 AI 角色；且 `docs/新的方案.md:743-744` 规定 AI 不得决定任务优先级、正式掌握状态或延迟验证日期，输出只能是建议文本 |

**建议（2026-09-17 修订）**：L0 + L1 + **L2 全部留在 StudyJournal**。原文「L2 正是 `docs/exocortex-ai-cockpit-migration-and-enhancement-plan-2026-09-15.md:34` 列为 Exocortex 第一层的 `Goal / Constraint / Capacity`，应在新仓库做」**已作废**——用户于 2026-09-17 明确「暂时不对 Exocortex 做后续开发」，该功能级延期由 `docs/studyjournal-scope-unfreeze-2026-09-17.md` 撤销。L2 的模型输出仍受 `docs/新的方案.md:738-750` 约束：**只能是建议文本**，不得决定任务优先级、正式掌握状态或延迟验证日期。

## 7. 已确认决策（2026-09-16）

| # | 问题 | 决策 |
| --- | --- | --- |
| 1 | 落地位置 | **留在 StudyJournal**，做「计划 + 日志 + 统计」（L0 层）。**2026-09-17 修订**：AI 联动（L2）原定「留给 Exocortex 的 `Goal / Constraint / Capacity` 层」，现改为同样在本仓库开发，见 `docs/studyjournal-scope-unfreeze-2026-09-17.md` |
| 2 | 「完成」的判据 | **存在未删除的日志记录即完成**。次日结算只看记录是否存在，不解析正文 |
| 3 | 是否预生成日志 | **不预生成**。点开计划并保存时才创建日志；无草稿态，无空记录清理任务 |
| 4 | 计划标题落到日志哪个字段 | **落到 `RecordBlock.title`，正文留空**。编辑器里日志标题本就用户可编辑，写入后仍可自由修改 |
| 5 | `title` 长度上限 | **UI 限 40 字，数据层不校验**。用户约定：计划标题不宜过长，超长时拆成**同一学科下的多条计划**（数据结构本就允许，无需唯一约束） |

**由决策 2 + 3 派生的直接结果：**

- 「次日自动清理空日志」这条机制**不再需要**——因为不存在空日志。v2 §3.3 的定时清理任务、§6.3 的清理代码、§9.1 的「定时清理失败」风险项全部作废。
- 剩余需要定义的只有一种边界：**日志已创建、随后被用户清空或删除**。
  - 清空正文：记录仍存在 → 按决策 2 仍算「完成」。若希望算未完成，需要额外一条「内容为空即视为未完成」的规则（当前不采纳）。
  - 删除日志：走现有软删除（进回收站），`getRecordBlocks` 已按 `deletedAt` 过滤，因此该计划自动回到「未完成」。这就够了，不需要额外逻辑。

**由决策 1 派生的前置条件（已闭环）：**「留在 StudyJournal」与当时的冻结声明冲突，现已由用户显式解冻本仓库的这一块范围，见 `docs/studyjournal-scope-unfreeze-2026-09-16.md`（2026-09-17 又扩大过一次，见 `docs/studyjournal-scope-unfreeze-2026-09-17.md`）。**2026-09-17 修订**：原文以「该文档同时写明『后续可能整体搬到 Exocortex』」作为「计划功能模块可整体剥离」这条约束的动机，**该迁移预期现已撤销**；**约束本身保留**（只读 `dailyPlans` / `blocks` / `subjects`，不反向依赖其它模块），但动机改为**模块边界纪律**——契约显式、不污染既有语义、可整体摘除，与其去向无关。

## 8. 两个细节（均已确认，见 §7 决策 4 / 5）

- **计划文本落到日志的哪个字段** → `RecordBlock.title`（现有字段），正文留空。理由：若把计划文本预填进 `contentHtml`，它会立刻被当成学习内容进入决策块提取、AI 上下文与知识导出。**已确认。**
- **`title` 长度上限** → 40 字（UI 限制、数据层不校验）。`RecordBlock.title` 不设限。**已确认。**
- **「来自计划」标识的呈现**：按需求强度做成正式字段（`planId`）而不是纯 UI 提示，日志详情页据此显示归属。
