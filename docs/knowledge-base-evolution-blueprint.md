# StudyJournal → 个人知识库系统：演进蓝图

> 日期：2026-09-13
> 状态：**规划草案**，仅讨论，不改代码、不改 schema、不改产品边界文档。
> 定位：本文回答"从应试复习工具，如何逐步演进为具备长期可用性价值的个人知识库（含检索强化、知识网络、PKM）"。
> 前提：原有功能不删；新增能力不得破坏现有 FSRS 复习、AI 驾驶舱、云同步、备份边界。

---

## 0. 一句话结论

**这个项目不需要"另起炉灶"重构成知识库，它已经埋好了三块地基**：① 记录正文 + 决策块 = 可原子化的内容单元；② `knowledgePoints` / `knowledgeRelations` / `recordKnowledgePointLinks` = 现成的知识网络雏形（当前被冻结为"遗留只读"）；③ Dexie + 云同步 + 备份 + AI 上下文服务 = 现成的存储/检索/智能底座。

真正的演进不是"新增一堆功能"，而是**逐步激活并重定义三层能力**：检索（从线性扫描 → 语义索引）、知识网络（从遗留只读 → 一等公民）、PKM（从被动日志 → 主动知识管理）。三者的正确接法顺序是**检索先行、网络其次、PKM 最后**，且每一步都复用现有决策块与 AI 上下文服务，而不是新建平行的数据结构。

## 1. 现状盘点：项目已经有什么（决定怎么接）

### 1.1 已具备、可直接复用的资产

| 现有资产 | 代码依据 | 对未来知识库的意义 |
| --- | --- | --- |
| 记录正文 + 决策块 | `RecordBlock.contentHtml` + `DecisionBlock`（schema 17） | **内容原子**：决策块已是"带 UUID、版本、可追溯"的最小内容单元，天然是知识节点 |
| 知识网络三表 | `knowledgePoints` / `knowledgeRelations` / `recordKnowledgePointLinks`（schema 16 遗留，schema 19 冻结为只读） | **知识图谱雏形**：节点 + 关系 + 记录链接的模型已经存在，只是被判定为"遗留只读事实" |
| AI 结构化上下文 | `aiContextService.ts` 的 `AiContextChunk` / `appendRecord` / 分块 + OCR + 公式 + Mermaid 序列化 | **语义索引的输入源**：已能把任意记录解析为结构化 chunk |
| 全文检索 | `search.ts` 的 `searchAll` / `searchAllAsync`（线性扫描 + 内存缓存 + 无持久索引） | **待强化的短板**：I-1 已确认"全表线性扫描无索引" |
| 标签体系 | `recordTags.ts` + `tags` 表（`&name` 唯一、有 parent） | **轻量分类法**：已支持层级标签 |
| 存储底座 | Dexie schema 21 + 云同步（PROTOCOL_VERSION 2）+ 4 通道备份 | **数据安全网**：知识库数据可跨端、可备份、可恢复 |
| 双层 AI 中枢 | 深度模型（策略）+ 快速模型（执行）+ 本地确定性规则 | **知识自动抽取/关联的引擎**：已具备"结构化 JSON 输出 + 溯源 + 版本"的完整范式 |
| 语音复述 | `voiceRecall*` 三表 + `ASR→LLM→TTS` | 知识库的**输入/输出多模态**基础 |

### 1.2 明确存在的短板（决定要补什么）

| 短板 | 现状 | 对知识库的阻碍 |
| --- | --- | --- |
| 检索无索引 | 全文线性扫描，无倒排/语义索引，无持久缓存 | 数据量上千条后检索变慢；无法做语义召回 |
| 知识网络是"死"的 | 三表冻结为只读，无活跃写入路径，无图谱 UI | 用户无法主动构建/浏览知识关系 |
| 内容"原子"未形成图 | 决策块挂在记录下，块与块之间无跨记录关系 | 无法表达"这个概念在多条记录中出现" |
| 无语义召回 | AI 上下文靠规则选取 + token 预算裁剪，非语义检索 | "相关知识"只能靠人工选范围 |
| 搜索无聚合 | 结果按 entry/block 平铺，无"主题/概念"维度 | 用户找不到"关于 X 的所有内容" |

## 2. 演进总原则（最重要的 5 条）

1. **复用决策块作为知识节点，不新建平行的"笔记原子"**。决策块已经是内容原子的最优形态（UUID + 版本 + 可追溯 + 可同步），再建一套"卡片/块"会导致双重真相源——这正是项目 AGENTS.md 反复强调要避免的。

2. **知识网络必须从"事实"重建，不能是 AI 一次性生成的投影**。参照项目里"投影必须可从正式事实重建"的既有约束，图谱的节点/关系要么是用户确认的事实，要么是可重算的派生，不能依赖某次 AI 调用结果才能恢复。

3. **检索分两层：确定性倒排索引（本地）+ 可选语义向量（本地或远端）**。第一版先补确定性索引（解决 I-1 的性能问题），语义检索作为独立增强，不绑死任何 embedding 供应商。

4. **同步边界必须显式**。新增的知识库实体要明确"哪些进云同步、哪些仅本机、哪些进备份"，沿用现有的 `cloudSyncModel` 实体映射 + `sanitizeSettingsForExport` 脱敏范式，绝不能把 embedding 向量、模型原始响应混入正式同步体。

5. **逐步激活，不推倒重来**。从"检索强化"这个对现有功能 100% 兼容的改动起步，验证底座后再激活知识网络，最后才做 PKM 层。每阶段都有独立交付与回滚能力。

## 3. 三层演进蓝图

```
┌─────────────────────────────────────────────────────────────┐
│  L3  PKM 层：主动知识管理（输入→组织→回顾的主动闭环）          │
│       双向链接、每日笔记、收件箱、Progressive Summarization   │
├─────────────────────────────────────────────────────────────┤
│  L2  知识网络层：知识图谱（节点 + 关系 + 浏览 + 推理）          │
│       激活 knowledge* 三表、图谱视图、自动/手动关联           │
├─────────────────────────────────────────────────────────────┤
│  L1  检索强化层：语义检索 + 倒排索引（把已有内容真正"找到"）    │
│       倒排索引、语义召回、聚合视图、全文高亮                  │
└─────────────────────────────────────────────────────────────┘
           ↑ 每一层都建立在现有 Dexie + 云同步 + 决策块 + AI 上下文 之上
```

## 4. 接法：分阶段实施（每阶段独立交付、可回滚）

### 阶段 A — 检索强化（先做，兼容性 100%）

**目标**：解决 I-1（线性扫描无索引），并为语义召回铺路。

| 子项 | 内容 | 是否改 schema | 风险 |
| --- | --- | --- | --- |
| A1 倒排索引表 | 新增 `searchIndex` 表（token → recordId 列表），编辑/删除时增量更新；启动时全量重建 | 是（新增表，本地） | 低 |
| A2 中文分词 | 引入轻量分词（jieba 的 WASM 或 `Intl.Segmenter`），对中文做 n-gram + 词典分词 | 否 | 低 |
| A3 聚合检索视图 | 结果按"主题/学科/标签/概念"聚合，不再平铺 | 否（UI） | 低 |
| A4 语义召回（可选，延后） | 本地 embedding（如 `@xenova/transformers` 的 ONNX 小模型）或远端 embedding API，对决策块生成向量，做余弦召回 | 是（新增 `embedding` 表，本地） | 中（模型体积、跨端一致性） |

**关键决策**：
- A1 用"确定性倒排索引"先落地，**不依赖任何外部服务**，纯 Dexie 层可做，风险最低。
- A4 语义检索**必须**与主检索解耦：向量表仅本机、不进云同步、不进备份（同 `voiceRecall*` 的本地边界）；embedding 失效时回退倒排。
- 复用 `aiContextService` 的 `blockToText`/分块逻辑，避免重新解析正文。

**验收**：千条记录下搜索 < 100ms；中文子串与词语均能命中；编辑后索引即时更新；A4 关闭时检索仍可用。

---

### 阶段 B — 激活知识网络（其次，需产品决策）

**目标**：把冻结的 `knowledge*` 三表重新激活为一等公民，让用户能构建和浏览知识图谱。

| 子项 | 内容 | 是否改 schema | 风险 |
| --- | --- | --- | --- |
| B1 节点模型升级 | 从"遗留只读知识点"升级为**有生命周期的知识节点**：`concept`（概念）/`topic`（主题）/`source`（来源）。复用现有 `knowledgePoints` 表，加 `kind`/`lifecycle` 字段 | 是（加字段，迁移） | 中 |
| B2 决策块 → 知识节点映射 | 允许用户把决策块"声明为知识节点"，建立 `decisionBlock ↔ knowledgePoint` 关联。**不复制正文**，只存引用 | 是（新增关联表） | 中 |
| B3 关系类型化 | 扩展 `knowledgeRelations.type`：`is-a`（是一种）/`part-of`（属于）/`prerequisite`（前置）/`related`（相关）/`example-of`（例证） | 是（枚举扩展） | 低 |
| B4 图谱视图 | 力导向图（复用 `recharts` 或引入轻量 `d3-force`），支持点击节点跳转、过滤、聚焦 | 否（UI） | 低 |
| B5 自动关联（AI 辅助） | 深度模型从多条记录中抽取"候选概念与关系"，**必须经用户确认**才成为正式事实（沿用决策块的"AI 派生 vs 用户确认"范式） | 否（复用 AI 中枢） | 中 |

**关键决策**：
- B 阶段最大的坑是**把"AI 自动建图"当成默认**。项目已有清晰范式：AI 产出的是"候选/派生解释"，用户确认后才成为正式事实。图谱必须遵守同一规则，否则会污染云同步的正式数据。
- `knowledgeRelations` 的跨实体一致性（逆向审计 §6.3 已发现"关系指向非 active 知识点"的风险）需要在 B 阶段一并补上校验。
- 旧 `knowledgePoints` 数据（用户确认过的）作为**只读种子**保留，不自动升级为有生命周期的节点，由用户决定是否"激活"。

**验收**：用户能手动建节点、连关系、浏览图谱；AI 候选关联需确认后才入正式数据；图谱实体进入云同步/备份；旧知识点只读保留。

---

### 阶段 C — PKM 层（最后，最谨慎）

**目标**：补上"主动知识管理"能力，让工具从"记录 + 复习"升级为"输入 → 组织 → 回顾"的闭环。

| 子项 | 内容 | 是否改 schema | 风险 |
| --- | --- | --- | --- |
| C1 双向链接 | 记录正文支持 `[[引用]]` 语法，跳转、反链面板（谁引用了我） | 是（需解析 + 索引） | 中 |
| C2 收件箱/每日笔记 | 快速捕获入口 + 每日默认页，未整理的条目进入待处理队列 | 是（新增本地表或复用 entry） | 中 |
| C3 渐进式总结 | 决策块已经是"重点摘录"，扩展为"渐进总结"分层（原文→粗体→高亮→摘要→重述） | 否（复用决策块） | 低 |
| C4 回顾面板 | 基于 FSRS 的知识点级回顾 + 随机漫步 + "这条知识我多久没碰了" | 否（复用 recordReviews） | 低 |

**关键决策**：
- C 阶段**最容易失控**。PKM 的完整形态（Roam/Obsidian/Logseq 级别）是另一条产品线，绝不能一步到位。建议 C 只做"最小可用 PKM"：双向链接 + 收件箱 + 回顾，其余留白。
- 双向链接的 `[[...]]` 解析要复用现有的 Tiptap 编辑器与 `recordContent` 解析器，不能另写一套 Markdown 引擎（项目已经踩过"多重内容真相源"的坑）。

## 5. 数据模型演进（新增实体的边界）

所有新增实体必须回答三问：**进云同步吗？进备份吗？能被正式事实重建吗？**

| 新实体 | 用途 | 云同步 | 备份 | 可否重建 | 类比现有 |
| --- | --- | --- | --- | --- | --- |
| `searchIndex`（倒排） | 检索加速 | ❌ 仅本机 | ❌ | ✅ 从 records 全量重建 | 类似投影表 |
| `embedding`（向量） | 语义召回 | ❌ 仅本机 | ❌ | ✅ 重新 embedding | 类似 `voiceRecall*` |
| `knowledgeNode`（升级版知识点） | 知识节点 | ✅ | ✅ | 部分（用户事实不可重建） | 升级 `knowledgePoints` |
| `decisionBlockKnowledgeLink` | 块↔节点关联 | ✅ | ✅ | ❌（用户确认的事实） | 类似 `recordKnowledgePointLinks` |
| `knowledgeRelation`（类型化） | 节点关系 | ✅ | ✅ | ❌（用户事实） | 扩展 `knowledgeRelations` |
| `backlinkIndex` | 双向链接反查 | ❌ 仅本机 | ❌ | ✅ 从正文重解析 | 类似投影 |

**铁律**：`searchIndex`、`embedding`、`backlinkIndex` 一律是**可重算的派生数据**，不进云同步、不进备份，删除后可无损重建。真正进同步/备份的只有**用户确认的知识事实**（节点、关联、类型化关系）——这与项目"投影必须可从正式事实重建"的既有原则完全一致。

## 6. 与现有系统的接缝（必须小心的地方）

### 6.1 与云同步的接缝

- 新增同步实体必须走 `cloudSyncModel` 的实体映射 + 墓碑 + 冲突策略，不能另起同步通道。
- **禁止**把 embedding 向量、搜索索引、双向链接反查表混入同步体——它们是派生数据。
- 知识节点/关系的跨设备合并要复用现有的"实体级二选一 + 追加式事件"范式；节点关系要补跨实体一致性校验（逆向审计已发现该缺口）。

### 6.2 与 AI 驾驶舱的接缝

- 知识网络的"自动关联"应复用**现有的双层 AI 中枢**（深度模型抽候选、快速模型执行、本地规则校验），而不是新写一套 AI 调用。
- 知识节点可以成为 AI 分析的**来源范围**（"针对这个概念，我有哪些决策块"），这会自然增强现有 Review Coach 的上下文。

### 6.3 与复习（FSRS）的接缝

- 知识节点**不新增一套独立的间隔复习**。复习仍以记录级 FSRS 为准；知识节点只做"引用/聚合/回顾提示"，避免重演项目里"Coach 复习与主复习是两套东西"的教训（逆向审计 §1.4 已确认此接缝）。

### 6.4 与备份的接缝

- 知识库正式实体（节点/关系/关联）必须进 ZIP/流式/文件夹备份；派生数据（索引/向量/反链）不进。这需要扩展 `createSnapshot` 的事务表清单，并同步更新 `assertSnapshotIntegrity` 的校验范围——**注意逆向审计 R-1/R-2 的教训：完整性校验的"排除集合"与"校验集合"必须一致**，否则会重蹈"播客音频被排除却仍被校验"的覆辙。

## 7. 与现有产品边界文档的关系

当前产品边界在 `docs/新的方案.md`，其 §19 明确冻结了若干边界（如"AI 自由决定正式状态""任意代码执行"等）。本蓝图**不违反**这些冻结项，但新增的"知识库"是一个**新的产品维度**，不属于原边界文档覆盖范围。

**建议**：在正式动手前，先把本蓝图沉淀为一份 `docs/knowledge-base-evolution.md`（或并入新的方案.md），明确：
1. 知识库是"保留现有全部功能"前提下的**增量**，不是替代。
2. 知识节点的生命周期、类型、关系语义（对应 B 阶段）。
3. 派生数据 vs 正式事实的边界（对应 §5 的铁律）。

在未做产品确认前，**不应在代码层临时决定知识节点的正式语义**——这延续了项目一贯的"产品边界先行"纪律。

## 8. 风险与依赖（诚实清单）

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 双重真相源 | 新建"笔记原子"与决策块重复 | 复用决策块为唯一内容原子 |
| 语义检索的供应商绑定 | embedding 模型/API 变化 | 向量仅本机、可重建、可回退倒排 |
| 图谱数据污染 | AI 自动建图未确认就入正式数据 | 严格"候选→确认"两段式 |
| 跨实体一致性 | 关系指向不存在的节点 | 补不变量校验（逆向审计已发现） |
| 打包体积 | embedding 模型/分词 WASM 增大安装包 | 倒排索引先行，语义检索延后+按需加载 |
| 跨端一致性 | 向量/索引在不同设备行为不一 | 派生数据一律本机重建，不进同步 |
| 修复债务未清 | 逆向审计的 P0（R-3 等）尚未修 | **建议先清 P0 再启动 A 阶段** |

## 9. 建议的推进顺序（一句话版）

```
第 0 步：先清掉逆向审计确认的 P0（尤其 R-3 数据丢失、K-1 错误不可见）
第 1 步：阶段 A（倒排索引 + 分词 + 聚合检索）—— 纯增量，零风险，立即让"找内容"变好用
第 2 步：阶段 A4 语义召回（可选，验证价值后再做）
第 3 步：阶段 B（激活知识网络）—— 需产品决策 + 迁移，谨慎
第 4 步：阶段 C（最小 PKM）—— 双向链接 + 收件箱 + 回顾，最后做
```

**核心判断**：这个项目演变为个人知识库的**最大优势**是——它已经有一套严谨的"正式事实 / 派生数据 / 同步边界 / 可重算投影"工程纪律，这套纪律恰好是 PKM/知识图谱类产品最容易翻车的地方。所以"怎么接"的答案很清晰：**沿着既有纪律，把检索、网络、PKM 三层逐一"合规地"接进去，而不是推翻重来。**

## 10. 需要你决策的 4 个问题

在进入正式规划（细化到阶段任务）之前，有几个产品层面的选择需要你拍板：

1. **语义检索的定位**：是"必须有"（本地 embedding）还是"锦上添花"（可延后）？这决定阶段 A 的边界。
2. **知识节点的形态**：倾向于"决策块即节点"（轻量，复用现有），还是"独立知识节点 + 块引用"（更灵活，但多一层）？
