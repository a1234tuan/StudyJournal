## 1. 产品定位

本产品不是一个根据“最近几天有没有学习”和“有多少卡片逾期”给出泛化建议的仪表盘，而是一个围绕用户亲自标记的关键内容工作的 AI 复习助教。

它要完成的核心闭环是：

```text
用户编辑决策块
  -> 决策块随原日志进入间隔复习
  -> 用户针对具体决策块写下本次真实困惑或反思
  -> 快速模型把原始反馈整理成可供规划使用的派生理解
  -> 用户在首页手动发起深度分析
  -> 深度模型为具体决策块设计个性化复习会话
  -> 本地规则选择和调度正式任务
  -> 快速模型按计划逐轮出题、讲解和追问
  -> 用户作答并反馈真实结果
  -> 系统记录即时表现，并在未来进行延迟验证
  -> 历史效果反过来影响下一次教学策略
```

产品的第一目标是提高关键内容的理解质量和延迟记忆保持率。任务完成数、AI 调用次数、评论数量和“感觉良好”次数都不是最终目标，只是过程信号。

## 2. 核心产品原则

1. 用户必须参与关键认知动作。选择关键内容、写下困惑、实际作答和确认结果不能由 AI 代替。
2. 用户的原始反馈是事实，AI 对反馈的改写、分类和原因判断只是派生解释，不能覆盖原文。
3. 用户反馈的具体程度决定个性化质量。系统应帮助用户把模糊反馈变具体，但不能假装知道用户没有表达的内容。
4. 智能化的价值是减少搜集材料、选择训练方式、组织题目和安排后续验证的成本，而不是消除所有认知摩擦。
5. 高成本模型负责复杂教学决策，低成本模型负责高频执行；确定性状态迁移、数据校验、去重和任务调度由本地程序负责。
6. 一次任务完成不等于已经长期掌握。即时结果和延迟保持必须分开记录。
7. AI 生成内容必须可追溯到来源决策块。证据不足时应返回“上下文不足”，而不是补写事实。
8. 正式数据应能够跨设备恢复；Prompt、原始响应、重试过程和未展示草稿属于可再生的本地执行数据。

## 4. 决策块

### 4.1 定义与身份

决策块是用户明确认为值得复习、检验或迁移应用的一段内容。它可以包含普通文本、列表、公式、对照表、高亮块、折叠块、结构图、Mermaid 和已经完成 OCR 的图片。

决策块使用 Tiptap 自定义容器节点 `record-decision-block`，至少携带：

- `decisionBlockId`：稳定 UUID。
- `contentVersion`：内容变化时递增。
- `createdAt`、`updatedAt`。

正文的唯一来源仍是 `RecordBlock.contentHtml`。独立的 `DecisionBlock` 表只保存索引、版本、所属记录和删除状态，不再复制一份可编辑正文，避免双重真相源。

复制决策块时生成新 UUID，不继承旧反馈、任务或状态。修改原块时保留 UUID 并递增 `contentVersion`；所有基于旧版本且尚未完成的分析和任务立即过期。

删除决策块采用软删除。系统必须把被删除节点的可恢复 HTML 片段保存到 `DecisionBlockArchive`，否则“软删除”只保存一个墓碑而无法恢复正文。

### 4.2 创建和转换

用户可以在编辑器中：

- 选中已有内容并转换为决策块。
- 新建空决策块后输入内容。
- 把决策块转换回普通内容。
- 恢复软删除的决策块。

把已有日志内容转换为决策块时，`RecordBlock.id` 和现有 `RecordReviewState` 保持不变，不重置复习次数、难度、稳定性或下次复习日期。决策块只增加新的块级反馈能力。

如果决策块中包含未完成 OCR、OCR 失败或 OCR 超时的图片，保存不受影响；进入 AI 分析前必须显示具体图片数量和处理状态。

### 4.3 自动加入间隔复习

当前项目只有记录级 FSRS。新建日志首次保存且含决策块时，系统自动把整条日志加入间隔复习。编辑已有日志时，如果该日志原本不在复习队列，系统明确询问一次是否加入，不能静默改变用户原有复习计划。

## 5. 间隔复习中的块级反思

### 5.1 展示方式

复习仍以整条日志为一张卡片。卡片中的每个有效决策块旁显示一个块级反思入口：Desktop 放在块侧边，Android 和窄屏放在块下方。

每次复习开始时，输入框必须为空，不自动带入上一次评论。用户没有填写时不创建空反馈事件，也不能把“未填写”解释为已经掌握、没有问题或拒绝 AI 帮助。

卡片结束后，用户仍要完成现有记录级 FSRS 评级。该评级只改变整条日志的调度，不直接作为某个决策块的掌握结论。

### 5.2 块级反馈只保留评论

决策块级反馈只保留评论，不提供“困难 / 模糊 / 良好 / 轻松”等块级评分。记录级 FSRS 评级继续保留，只负责整条日志的间隔调度。

这一规则要求用户通过语言描述具体问题，避免块级主观分数和整卡 FSRS 分数同时出现。空评论不会产生块级状态信号，也不能被系统解释为正向结果。

### 5.3 评论进入 AI 队列

所有非空评论默认进入待分析队列。用户可以在提交前关闭“加入 AI 分析”；关闭后评论仍作为复习历史保存，但不进入 AI 队列。

快速模型可以把评论标注为“可能无需任务”，但不能替用户永久排除。是否保留在本次分析范围内，最终由用户决定。

### 5.4 评论历史

每次评论作为独立、不可变的反馈事件保留，当前输入始终为空。历史默认折叠，用户可以展开查看，也可以执行永久删除；永久删除通过墓碑同步到其他设备。

历史事件用于识别重复困难和评估干预效果，但不会预填到下一次输入框中干扰本次反思。

### 5.5 低成本 AI 整理评论

快速模型保留用户原文，并异步生成一份并列、可见、可编辑的结构化理解，例如困惑对象、卡住步骤、用户猜测的原因、希望训练的方式和仍缺失的信息。它不能覆盖原始评论。

用户确认或修改过的结构化理解作为用户确认数据发送；未确认版本仍可参与分析，但必须明确标记为 AI 推断，并和原始评论同时发送。

快速模型输出采用固定 JSON：

```json
{
  "actionability": "needs_training | reflection_only | unclear",
  "difficultyType": "concept | procedure | confusion | calculation | application | expression | other",
  "stuckAt": "string | null",
  "userHypothesis": "string | null",
  "preferredPractice": "string | null",
  "missingInformation": ["string"],
  "confidence": 0.0
}
```

置信度不足或必要背景缺失时输出 `unclear` / `insufficient-context`，不得补造背景。

### 5.6 多次未分析反馈

同一决策块积累多条待分析评论时，深度分析发送最新一条原文，并附带更早反馈的结构化趋势摘要和发生时间。所有原始事件仍保留，不因生成摘要而被覆盖或删除。

## 6. 首页待分析工作台

### 6.1 队列单位

待分析队列改为“决策块反馈版本”，不再以整条日志为最小单位。列表按日志分组，但每个决策块可以独立选择。

一个条目至少显示：

- 日志标题、学科和上次复习时间。
- 决策块预览与 `contentVersion`。
- 本次原始评论和 AI 结构化理解状态。
- OCR 缺失警告。
- 是否曾有失败任务、延迟验证或重复困难。
- 预计 token 与费用。

用户在首页手动点击“AI 分析”后，系统才调用深度模型。快速评论整理可以在复习提交后异步执行，失败不能阻塞下一张卡片。

### 6.2 默认选择

打开 AI 分析时，系统默认选择全部符合条件的决策块，并展示总量、自动拆分后的子批次数、预计 token/费用和 OCR 警告。用户进行一次最终确认后，系统自动依次处理全部子批次。

用户可以在确认前取消任意条目；未确认前不得发起深度模型调用。

### 6.3 选择、修改和删除的语义

分析列表只负责：取消本批次选择、排除或恢复本次反馈，以及补充一段仅属于本次分析的说明。

编辑源内容必须跳转日志编辑器，并在保存后递增 `contentVersion`。软删除源决策块也只能在日志编辑器完成。系统不创建一份只供 AI 使用的决策块正文副本。

### 6.4 批次拆分

一个深度模型子批次最多处理三个决策块，同时还必须满足模型上下文硬上限。若单个决策块已经超过预算，则不能强塞给模型；系统应提示用户缩小内容、完成 OCR 或拆分决策块。

自动拆分只是一种请求传输方式，不代表三个决策块必须合成一个学习任务。每个子批次都保存冻结输入引用、模型版本、Prompt 版本、预计与实际 token、状态和错误。

## 7. 双层 AI 中枢

### 7.1 职责边界

| 层级 | 负责 | 明确不负责 |
| --- | --- | --- |
| 本地确定性规则 | 数据有效性、版本检查、队列去重、批次拆分、任务排序、唯一当前任务、状态迁移、过期、同步合并 | 理解开放文本、设计教学内容、判断开放题语义 |
| 深度模型 | 识别真正卡点、选择训练策略、设计难度和递进路径、决定何时讲解/举例/检查前置知识，输出 `SessionBlueprint` | 直接修改掌握状态、直接激活任务、执行任意代码 |
| 快速模型 | 整理评论、按 Blueprint 逐轮生成题目/讲解/追问、进行题目质量复核和回答语义评估 | 改变目标决策块、擅自改 Blueprint、决定正式状态 |

“深度模型生成个性化任务”在数据上解释为：深度模型生成任务的教学蓝图，而不是一次性写完全部题目。后续每轮内容由快速模型在蓝图约束内生成。这样既把复杂决策交给高成本模型，又避免为用户尚未走到的分支提前生成大量内容。

### 7.2 Session Blueprint

每个 Blueprint 只针对一个主决策块版本，至少包含：

- `decisionBlockId`、`contentVersion`、来源记录。
- 原始评论引用和 AI 结构化理解引用。
- 问题假设及其置信度；证据不足时明确标记。
- 本次会话目标和完成判据。
- 首轮题型、难度、预期关键点。
- 回答正确、部分正确、错误、跳过时的下一步策略。
- 可使用的讲解、例题、前置知识检查和变式范围。
- 禁止越界的知识范围。
- 每一步对应的来源证据。
- 允许的最大轮数、重试和费用保护规则。

深度模型可在同一批次中为三个决策块分别生成 Blueprint，但本地程序必须逐个校验。若输出引用了不存在的块、旧版本、未提供的来源或不支持的任务能力，则该候选失败关闭，不创建正式任务。

### 7.3 主决策块与辅助决策块

一个正式任务只有一个主决策块。任务可以引用用户已确认相关的辅助决策块，用于辨析、比较或迁移训练，但任务结果只更新主目标；辅助决策块不会因同场出现而被标记为已掌握。

### 7.4 Prompt 管理

所有 Prompt 必须短、约束清晰、要求结构化 JSON 输出，并包含：

- 输入字段白名单。
- 输出 JSON Schema。
- `insufficient-context` 分支。
- 不得补造来源事实的约束。
- 模型角色边界。
- Prompt 版本和策略版本。

正式开发前，每个角色的系统 Prompt、输入样例、反例、JSON Schema 和失败输出都需要单独提交用户复核。Prompt 原文和 Provider 原始响应默认只保存在本机诊断缓存，不作为同步后的真相源。

## 8. 个性化任务和自适应会话

### 8.1 第一类正式任务：自适应测验

第一类正式任务仍是自适应测验，但“测验”不是固定题数的试卷。它是一场围绕单个主决策块的多轮复习会话。

Blueprint 可以选择以下轮次策略：

- 概念问答：默认主形态。
- 计算题：适用于存在可验证计算过程的内容。
- 易混辨析：要求比较边界、条件和反例。
- 概念填空：只在少量关键词决定正确性时使用。
- 原知识点变式：适用于用户基本理解但缺乏信心或迁移能力不足。
- 最小 Chunk 训练组：适用于问题可以拆成连续小步骤且用户在中间环节卡住。
- 前置知识检查、讲解和例题：作为会话内部辅助步骤，不单独创建任务。

用户明确选择“继续”才进入下一轮。AI 不能仅凭一次回答自行宣告用户已经掌握，也不能无限追加轮次。

### 8.2 分析前后如何展示来源

测验默认闭卷。作答前只显示来源日志标题和题目，不显示可能包含答案的完整决策块。用户可以主动请求提示，每次提示及其层级都要记录。

提交答案后，系统展示相关决策块片段、答案依据和差异解释，使用户能够核查 AI 是否偏离原文。

### 8.3 AI 题目质量与幻觉

多轮交互和重新生成只能补救用户已经发现的问题，不能替代出题前的基本质量控制。客观题、计算题和唯一答案题在展示前自动经过快速模型的独立质检；开放题进行本地结构校验和来源约束校验。所有题目仍提供手动“题目有问题”入口。

质检属于快速层的独立角色，可以配置其他低成本模型，但第一版不强制新增第三套 Provider。

自动质检只检查严重问题：是否无解、关键条件缺失、明显偏离来源、唯一答案实际不唯一、计算或标准答案矛盾。它不得因为措辞风格或非关键细节反复挑刺。失败后最多自动重生成一次，再失败则暂停该轮并请用户处理，不能形成无限调用。

### 8.4 可视化交互程序

Gemini Canvas 式可视化能够帮助理解函数、几何、算法和动态过程，但“让模型生成任意 HTML/JavaScript 并在 Desktop/Android WebView 中运行”会新增代码执行、安全隔离、离线资源、跨端一致性、可访问性和长期兼容问题。它不是 Mermaid 图的简单升级。

第一版不把可视化交互程序作为正式任务类型。Blueprint 可以记录“适合可视化”的建议，供后续统计真实需求，但不能生成或运行可执行内容。

只有在测验闭环被验证有效且积累足够可视化需求后，才单独评估白名单 `InteractiveArtifactSpec`。任意模型生成的 HTML/JavaScript 不进入本轮实施范围。

## 9. 任务列表与调度

### 9.1 当前任务和等待任务

全局最多存在一个当前或进行中任务，其余正式任务处于等待、延期或历史状态。用户可以明确切换任务，系统不能静默替换仍然有效的当前任务。

### 9.2 等待队列的完整规则

本地调度器负责：

1. 当前任务完成、延期、放弃或因 `contentVersion` 失效后，重新计算等待队列。
2. 同一决策块同一版本最多保留一个未完成正式任务；新 Blueprint 不得无声覆盖已开始任务。
3. 决策块版本变化时，旧任务立即过期并说明原因。
4. 等待时间会提高同级任务的排序，避免长期饥饿。
5. 到期的延迟验证具有高优先级，但不得连续占满所有任务机会；重复失败的新困难项也必须获得机会。
6. 用户选择“这次没时间”时只是延期当前任务，不形成“未掌握”学习结果。
7. 用户切换任务时，原任务回到等待或延期状态，历史执行进度不被伪装成完成。

优先级不是一个让 AI 随意输出的总分。第一版由本地规则按“已到期延迟验证、重复困难、首次困难、普通巩固、等待时长”分层排序；深度模型只能在同一目标内部选择教学策略。

## 10. 用户执行、结果和重新规划

### 10.1 必须分开的四类结果

系统必须分别保存：

| 数据 | 含义 | 示例 |
| --- | --- | --- |
| 主观自评 | 用户此刻的理解或信心 | 已掌握、仍模糊、未掌握 |
| 即时作答结果 | 本轮答案相对判据的表现 | 正确、部分正确、错误、无法可靠判定 |
| 执行处置 | 用户对任务本身的操作 | 完成、延期、放弃、报告题目问题 |
| 延迟保持结果 | 经过时间后能否再次提取或应用 | 保持、衰退、未完成验证 |

`DecisionBlockState` 是根据这些事实计算出的当前投影，不是用户点击一次按钮后写死的事实。这样“没时间”“题目有错”“答案错误但用户感觉不错”不会被压成同一种未掌握状态。

### 10.2 结束会话时的反馈档位

完成有效作答后，用户提交“已掌握 / 仍需巩固 / 未掌握”三档主观结果。“仍需巩固”用于表达最常见的半掌握状态，并触发变式训练或更短间隔的延迟验证。

当最后一轮答案明显错误而用户选择“已掌握”时，系统展示冲突并要求二次确认。用户确认后保留其自评，但即时答案仍记录为错误；两个事实都不能互相覆盖。

### 10.3 未掌握、没时间和任务删除

“这次没时间做”不是未掌握原因，因为它没有产生学习证据。“题目错误”也不是未掌握。只有用户实际参与后仍无法理解，才形成未掌握结果。

任务未正常结束时分成三条路径：

- 没时间：延期原任务，不生成学习结果。
- 实际学习后仍不会：记录用户原因和即时表现，自动进入下一次重新规划。
- 题目错误或严重偏题：任务标记为无效并触发质检，不更新掌握状态。

### 10.4 保留失败任务历史

未掌握后，旧任务结束为“未达成”，保留 Blueprint、已展示轮次、回答和结果，并创建新的规划请求。普通界面折叠这段历史，用户仍可执行永久删除。

重新规划必须创建新任务，不能覆盖旧任务对象，以便系统识别已经失败的教学策略并避免机械重复。

## 11. 延迟验证

一次会话中的“已掌握”只能形成即时改善，不能直接证明记忆已经留存。每个即时掌握结果都创建独立的延迟验证计划，至少包含：

- `verificationEligibleAt`：最早允许验证时间。
- `verificationDueAt`：期望验证时间。
- `lastVerifiedAt`。
- `verificationOutcome`：保持、衰退或未完成。
- 生成该计划的策略版本。

延迟验证使用新的提取题或变式题，不重复展示原答案。其结果与原记录的 FSRS 调度并存：FSRS 决定整条日志何时出现，块级验证决定某个关键内容何时需要被再次检验。

延迟验证时间由本地确定性策略根据即时表现、提示使用和历史保持情况计算。深度模型只能建议验证题型和训练形式，不能任意指定日期。

块级验证时间不必与整条日志的下一次 FSRS 日期相同；二者同时到期时可以在同一次复习会话中合并展示，但必须分别记录结果。

## 12. 效果学习与“智能”的来源

系统不以任务清除率作为智能依据，而是以不同教学干预在当前用户身上的实际效果作为下一次规划输入。

`InterventionEffectSummary` 从正式事件重新计算，至少按问题类型、题型和辅助策略统计：

- 从明确暴露问题到即时已掌握的次数和比例。
- 延迟验证的样本数、保持率和衰退率。
- 达到即时掌握前的轮数和提示使用情况。
- 讲解、例题、变式、Chunk 训练和前置检查后的结果。
- 延期、退出、题目无效、重新规划和永久删除次数。
- 样本时间范围、最近性、置信度、模型版本和 Prompt/策略版本。

样本不足时必须明确输出“证据不足”，不能因为一次成功就宣称某种方法最适合用户。聚合摘要只帮助深度模型选择“怎么教”，不能凭空创建没有当前决策块和当前反馈的任务。

## 14. 旧数据迁移

### 14.1 开发基线

新系统仍应从 `baseline/pre-learning-coach` 对应的稳定基线建立独立 v2 分支，不把当前旧驾驶舱的 Snapshot/Diagnosis/Task 编排继续扩展。开始前必须完整归档当前脏工作区、已验证修复、测试和发布产物，禁止直接 reset、clean 或覆盖。

发布升级必须同时支持：

1. schema 11：从未安装当前驾驶舱的数据库。
2. schema 12-16：已经产生旧 Coach、KnowledgePoint 和 AI 测验数据的数据库。

### 14.2 现有记录级评论

当前 `RecordReviewLog.evaluationText` 只知道记录 ID，不知道评论针对哪个决策块。自动复制到该记录所有决策块会制造错误事实。

旧记录级评论原样保留在“旧版整条日志评价”历史中，不自动映射到任何决策块。用户可以在查看历史时手动关联；只有手动确认后，系统才创建新的块级关联事实。

### 14.3 现有 KnowledgePoint 正式数据

当前 `KnowledgePoint`、`RecordKnowledgePointLink` 和用户确认的 `KnowledgeRelation` 不是纯缓存。它们包含用户确认过的知识组织事实，不能与旧 Snapshot、Diagnosis 和 AI 候选一起直接丢弃。

用户确认过的知识点、链接和关系完整迁移，并作为“旧版知识关联”只读保留，可查看、导出和以后手动关联决策块。第一版不让这些记录级知识关系直接参与新任务优先级；未确认的 AI 候选不迁移。

旧 Snapshot、Diagnosis、未采纳 AI candidate、运行中间状态和可重算投影不迁移。旧 AI 测验中已经由用户确认的回答与结果应转成带“legacy”来源的正式历史事件，但不能自动升级为某个决策块已经掌握。

## 15. 同步、备份和隐私

schema 19 已覆盖新 Coach 正式对象的云同步；schema 20 仅增加不参与同步的 `reviewAnnotationDrafts`，schema 21 再增加 `voiceRecallSessions`、`voiceRecallTurns`、`voiceRecallLocalHistory` 三张 local-only 表。正式同步协议继续采用逐实体哈希、revision ledger、不可变复习事件和删除墓碑进行增量收敛，并采用以下边界：

同步：

- 决策块正文身份、版本、删除墓碑和可恢复归档。
- 原始反馈事件及用户对 AI 理解的修正。
- 当前有效的分析请求、最终摘要、正式 Blueprint 和任务。
- 已展示/已作答轮次、主观自评、即时结果和延迟验证结果。
- 用户的选择、排除、延期、切换和删除决定。

仅本机：

- API 密钥。
- 完整 Prompt、Provider 原始响应和流式片段。
- 重试过程、运行锁、费用估算缓存。
- 未展示题目草稿和未采纳候选的完整生成内容。
- 知识播客记录、音频和本机备份目录。

决策块正文冲突按内容版本和更新时间处理；反馈、结果、任务操作和删除都采用不可变事件或墓碑合并。跨设备同时编辑同一决策块时不得静默拼接 HTML，应产生可恢复冲突副本。

完整备份必须覆盖所有正式数据和用户确认的旧 KnowledgePoint 数据。恢复测试需要证明：没有任何 AI 中间缓存时，仍能重建当前任务、等待队列、历史反馈和延迟验证。

## 16. 失败与费用保护

1. 快速评论处理失败不阻塞复习；条目保留待重试状态。
2. 深度分析由用户手动触发，调用前显示预计 token、费用、子批次数和 OCR 警告。
3. 每个调用角色都有本地最大重试次数、超时、并发数和熔断规则，不能无限调用。
4. 单个决策块超过硬上下文上限时失败关闭，不自动截掉关键内容后继续。
5. JSON Schema 校验失败、来源引用失效或 `contentVersion` 不一致时不创建正式任务。
6. Provider 切换、模型版本和 Prompt 版本进入审计字段，效果统计不能把不同策略无条件混为一组。
7. 应用退到后台时暂停远程队列；恢复前台后幂等续跑，不重复创建任务。

## 17. 分阶段实施

### 17.1 实施纪律

1. 不在当前脏工作区上直接切换基线、reset、clean 或开始重构。
2. 每个阶段必须交付可运行的纵向能力和对应自动化测试，不能先铺完所有表再集中补行为。
3. 新数据库版本统一使用高于现有 schema 16 的版本号，使 schema 11 和 schema 12-16 都沿同一升级路径进入新系统。
4. 正式事实先于投影和 UI。任何状态都必须说明由哪些事实重算，不能依赖一次 AI 响应或缓存才能恢复。
5. 新旧驾驶舱不长期双写。迁移完成前保留旧表只读，迁移验收通过后再停止旧入口和旧服务。
6. 每阶段依次执行定向单元/组件测试、`npm run test`、`npm run build`；涉及交互后再运行对应 Playwright，涉及原生壳后再构建 Desktop/Android。
7. 真实 Provider 只用于阶段末受控验收；日常测试使用确定性 mock，避免费用和模型波动影响回归结果。

### 阶段 3：块级评论与待分析队列

## 18. 验收标准

### 产品闭环

- 用户可把已有内容转换为决策块且不改变原记录复习进度。
- 用户能在一次真实复习中针对具体块留下新评论，旧评论不会预填干扰。
- AI 派生解释永远不覆盖用户原文，并可见、可纠正。
- 一次点击可自动拆分并完成多个深度分析子批次。
- 每个正式任务能追溯到决策块版本、反馈、Blueprint 和来源证据。
- 用户能完成多轮个性化训练，而不是只收到一段分析摘要。
- 没时间、题目错误、未掌握和已掌握形成不同事实。
- 即时掌握会进入延迟验证，系统能报告保持或衰退，而不是只报告任务完成。

### 数据正确性

- 修改决策块后，旧版本未完成任务不能继续写入新状态。
- 删除后可以恢复决策块正文，而不只是恢复一个空壳 ID。
- 同一反馈、批次、题目或结果在重试和多设备合并时不会重复创建。
- 清空本地 AI 缓存后仍能恢复正式任务、作答历史和验证计划。
- schema 11 和 schema 16 升级不丢日志、FSRS、资源、计时、旧评论或用户确认的 KnowledgePoint 数据。

### AI 质量

- 上下文不足时可以稳定返回不可处理，而不是幻觉补全。
- 客观题和计算题不会在明显无解、缺条件或答案矛盾时直接展示。
- 作答前不会无意显示标准答案，提示使用被记录。
- 高成本模型只负责策略，快速模型不能越权改变目标或正式状态。
- 所有 Prompt、输出 Schema、模型和策略都有版本，可用测试样例回放。

## 19. 已冻结的产品边界

以下内容不进入第一版：

- 任意 HTML/JavaScript 可视化程序和新的正式可视化任务类型。
- 由 AI 自由决定任务优先级、正式掌握状态或延迟验证日期。
- 多个同时进行中的任务。
- 把空评论、没时间、题目错误或任务删除解释为学习结果。
- 自动把旧记录级评论或旧 KnowledgePoint 映射成决策块掌握事实。
- 用 AI 改写结果覆盖用户原始评论。
- 为了兼容旧系统继续扩展 Snapshot/Diagnosis/旧 Task 内核。

第一版实施期间，只要需求会突破上述边界、改变正式数据含义或新增正式任务类型，就必须先修改本文并重新进行产品确认，不能在代码层临时决定。
