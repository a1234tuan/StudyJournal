## 1. 用户会怎样使用

### 1.1 主流程

1. 从日志页的“知识库”入口或“更多 → 知识库”进入；不新增底部导航主标签，不挤压既有入口。
2. 新建专题，如“数据结构”，创建“树”“图”等节点；也可从日志详情“加入专题”，批量加入已有或新建节点。
3. 在“待整理”查看尚未进入任何有效、未归档专题的日志；也可切换成“尚未加入当前专题”。学科、标签、日期、收藏、资源类型用于筛选。
4. 专题默认大纲，可切换导图。节点能有标题、说明、多条日志引用及子节点，也能是纯文字节点。
5. 选中节点看详情，点击具体日志链接进入原日志浏览；编辑仍走原日志编辑器与正式保存保护。
6. 返回专题时恢复路径、选择、展开、搜索和视口。日志详情的“所属专题”显示反向引用，可跳到另一位置。
7. 点击现有同步入口后，分别看到“日志”和“知识库”的状态；有冲突则进入“待处理”，不是提示同步成功后悄悄丢弃另一端。

同一日志可被多个不同节点引用，正文始终只有一份。v1 **不支持同一节点/子树的多位置别名**；需要多处组织时新增节点并引用同一日志，各处说明与备注独立。

### 1.2 浏览、整理、输入三种互斥状态

- 默认浏览：单击节点只选中；画布拖动只平移；双击、长按不直接修改文字或结构。
- 显式“整理”：显示拖动把手、移动到、编辑和删除。从把手开始拖动，超过阈值后抑制点击；松手仅提交一次，目标不明确则取消。触屏有等价的“移动到”操作。
- 显式“编辑”：输入框接管触摸、选区、快捷键和 IME；拖拽失效。Android Back、切后台、pointercancel 或失焦不隐式保存结构操作。
- 导图支持双指缩放、二维平移、缩放按钮、100%、聚焦分支、查看全图；desktop 支持拖动画布及明确的缩放手势，不抢输入区滚动。
- 使用紧凑圆角矩形，标题最多两行，附引用数/子节点数/备注标记。长文字在 desktop 侧栏、Android 底部详情或详情页阅读，不把全文卡片堆到画布上。
- “全图”展示结构概貌，不保证一千个节点同屏文字全可读。依靠折叠、分支聚焦和搜索，而不是无限缩小字号。

### 1.3 编辑合同

v1 节点说明和引用备注为**纯文本、多行、显式保存**；不增加独立富文本编辑器、附件、图片上传或 Markdown 执行规则。标题单行。初始工程预算：标题 UTF-8 512 字节，说明 16 KiB，单条备注 4 KiB；界面提前给出剩余量，不静默截断。预算须在实现前用中文/emoji 验证，不是当前产品已有上限。

编辑打开时固定目标字段版本。保存必须在写事务内比较该版本；其他独立字段改变不阻止保存，本字段或目标生命周期变化则提示重新比较，保留本机输入。失败、离线、取消、切后台不丢输入；本机恢复草稿保留原基线，按账号/库/实体隔离，不参与检索、云同步和正式备份。成功提交后清理对应草稿。

IME 组合输入期间 Enter 不保存、不跳搜索结果。连续点击保存复用命令 ID，不能重复创建引用。离开未保存输入时明确选择保留草稿、放弃或继续编辑；远端删除后不自动复活节点，可把草稿复制到新的文字节点。

## 2. 关键取舍与实体模型

### 2.1 单位置树，日志多引用

取消 v1 的 KnowledgePlacement 实体。每个节点只有一个正式父级，引用直接归节点；移动节点不复制节点、引用、说明或子树。

- **KnowledgeLibrary**：本地知识库身份、账号绑定与同步命名空间；首次本机创建未绑定。不是第二份日志数据库。
- **KnowledgeWorkspace**：专题；稳定 id、libraryId、标题、说明、归档及软删除状态。
- **KnowledgeNode**：稳定 id、workspaceId、标题、说明、生命周期，以及一个结构单元 position = { parentNodeId 或根, orderKey }。workspaceId 在 v1 不可修改，跨专题子树移动后置。
- **KnowledgeRecordReference**：稳定 id、workspaceId、nodeId、recordId、备注、顺序与生命周期。nodeId/recordId 在创建后不变；改变归属用明确的移除/新建。单节点同一日志只显示一条有效引用；并发重复加入保留不同备注为候选，不能静默择一覆盖。
- **KnowledgeRevision / ConflictEvidence**：小单元的不可变版本及未采纳内容/结构意图；用于共同基线、候选比较、幂等确认与冲突处理。UI 的“有冲突”由候选推导，不另存可随意覆盖的 conflictState。

本节是逻辑模型，不预设 Dexie 表名和最终 schema 版本。正式实体不得混入画布坐标、搜索缓存、缩放、临时展开、远端游标、租约或设备凭据。

### 2.2 合并单元与身份

节点标题、节点说明分别是文字单元；parentNodeId 与 orderKey 是**不可拆分的结构单元**；引用备注、引用顺序各自为单元；生命周期独立但与删除/编辑交叉校验。专题标题与说明同理。稳定身份及所属库/专题不可被普通 patch 修改。

同一字段不做逐字自动合并。不同字段可合并，不等于不同节点移动永远能合并。删除与编辑必须结合双方的实体版本向量/单元版本集合判断，不能仅比较 deletedAt。

orderKey 同值按稳定节点 ID 排序。重排也属结构写入，有基线和命令边界；不能一次保存整专题来重排。v1 不承诺无限拖拽不维护排序键；实现前须确定有界重排算法，达到键长预算时先提示整理而非无限增长。

### 2.3 树必须始终可遍历

每专题是无环森林，多根由虚拟根展示。正式父级只能是同专题中存在的节点；自引用、成环、跨专题父级和不存在父级不能进入正式树。软删除/归档祖先造成的不可见节点进入恢复投影，不被物理删除。

本地命令提交时验证；远端合并后再次对完整受影响专题验证。特别覆盖 P→Q 与 Q→P 各自在离线端合法、合并成环的反例。正式树保留已提交合法结构；后来无法接受的移动保存为候选意图，不复制子树、不自动猜父级。无法满足约束的候选不必被伪装成一棵合法树。

索引、渲染和备份检查还要有 visited 集合与缺失父级兜底。损坏或未知版本数据放入“结构待修复”，不能死循环、无限递归或悄悄丢节点。

## 3. 本地命令与并发合同

### 3.1 一个事务完成一次真实修改

repository 是知识库唯一正式写入口。命令含稳定 commandId、账号/库上下文、dataGeneration、目标单元、expected 版本、明确 patch；不允许把旧 UI 对象整行 put 回去。

同一 Dexie 写事务内完成：读取当前行 → 验证身份/基线/生命周期/树约束 → 应用 patch → 写不可变版本、待上传命令、知识库 mutation 标记及持久化备份 dirty 标记。任何一步失败全部回滚；无变化操作不制造版本、epoch 或备份任务。

撤销是检查当前基线的新命令，不是回写历史整图。删除、恢复、重复加入也走相同入口。OCR 结果只触发关联日志检索失效，不改写知识节点或冒充知识库编辑。

### 3.2 版本与冲突的可执行语义

每次被修改的小单元有不可变 revisionId（commandId + 单元身份）、父版本 ID 集合、规范化内容与 hash。hash 不包含 updatedAt、本机视口或协议游标；规范化需区分“缺字段”“空值”“删除”，对象键序确定。时间戳只展示，不决定胜负。

- 基于已知版本修改，且当前 head 仍是该版本：采用新值。
- 不同单元修改：逐单元比较；随后统一检查生命周期与树约束。
- 同单元并发且内容相同：合并因果父版本，不生成内容冲突。
- 同单元并发且不同：保留已提交正式值和新的候选值；双方版本都持久化，不能用后到时间淘汰先到内容。
- 找不到可信共同基线：不猜三方合并，进入“基线不足”候选，提示比较或重新同步。

冲突证据 ID 由库、实体、单元和分歧 revisionId 的排序集合确定；新增第三个分支生成新的证据，原证据不改写，UI 按实体/单元聚合。解决命令列出自己看过的**全部活跃候选 heads**及选定/手工合并内容；事务 CAS 检查集合未变。出现新分支或另一设备已处理则拒绝陈旧解决，保留输入并刷新，不能覆盖先前处理结果。

解决形成有多个父版本的新 revision，并记录 covered revisionIds；重传已覆盖祖先不复活旧冲突。旧设备基于祖先产生的全新修改是新分支，仍须呈现，不能因为祖先已解决就丢弃。同一解决命令重试无副作用。

v1 不实现通用 CRDT、文本协同或任意多位置别名。只要求相同已提交历史最终收敛，不声称不同服务端提交顺序必得相同“默认保留位置”。版本、墓碑和冲突历史首期不自动 GC；必须可查看占用、导出，不能无限增长而不提示。

## 4. 云同步：独立通道，不混入普通日志账本

### 4.1 隔离决定

R2 唯一方案是独立 Knowledge channel；移除“先混入普通实体列表再靠 capability flag”的备选。现有客户端无法遵守后来新增的前端开关；现有普通账本缺行推导删除也不适合承载未知知识类型。

- 独立 Firestore 顶层命名空间，建议 /knowledgeUsers/{uid}/libraries/{libraryId}/…；**不放在当前 /users/{uid}/… 的递归放行规则下**。认证仍复用，但新命名空间必须有单独规则及协议校验。
- 独立本地 remote mirror、ledger、pending commands、cursor、epoch、恢复代际和状态；不得调用普通同步的删除推导或普通 epoch 表示知识库变化。
- v1 只存有界纯文本与结构，**不创建 Knowledge Storage 对象**。未来超大内容必须另立 Storage 根与 GC；不能借用普通 documents/assets 根。
- 自动备份 dirty 与普通云 mutation 分开；知识库事务写持久 dirtyGeneration，提交后通知备份调度，启动时补偿未调度的 dirty。恢复暂停期间也不能丢掉变脏事实。
- 普通同步旧行为不整体重写。入口仅编排两个结果；“日志成功、知识库失败/待处理”必须分别呈现，不能合成“全部完成”。

### 4.2 首期用有界原子命令，不自造跨批次事务

云端每个库一个提交序号 head。客户端用某个 head 的一致镜像准备合并结果并验证结构，再在事务内读取并比较 head、涉及单元版本、幂等 receipt；不匹配则重新拉取/计算。事务内一并提交实体变更、不可变版本、冲突证据、完整 commit 记录/receipt 与新 head。

这把“结构检查时看见的图”与“实际提交的图”绑定，避免图在事务外验证后已变。云端序列化的是**小命令**，不是上传整库 JSON；不维持长时远端锁，不需要首期另建租约、跨批次 staging 或分布式事务协调器。库级串行会有重试与吞吐代价，对本期单用户少设备规模先接受，不包装成无限扩展协议。

初始预算：一个命令序列化变更不超过 64 KiB、事务总写文档不超过 20（含版本/证据/head/receipt），最终以 SDK 与安全规则测试为准，**不是声称供应商实际限额就是这些数值**。超限在本地提交前阻止；批量加入拆成可见的独立小命令，显示逐项成功/失败，不承诺整个大批次原子。一个冲突解决不可拆半提交；极端候选数量必须先以有界逐个确认收敛，不能丢候选以压缩请求。

稳定 commandId 的 receipt 绑定完整命令 hash。重复请求同 ID 同 hash 返回原结果；同 ID 不同 hash 拒绝。离线只进本地 pending；重连后重算云合并。事务回调允许重试，不得生成新的 ID 或产生事务外副作用。未知结果先查指定 receipt，再决定重试，禁止重新分配 ID。

安全规则必须验证 UID、库归属、协议版本、不可变记录和 head/receipt 的合法关联；应用层树合法性仍需受支持客户端共同遵守。恶意持有同账号凭据的自编客户端不在“防双端误覆盖”保证内。规则的表达能力、读取预算和事务大小必须通过 Emulator；不能把文件里写了 expected 当成服务端已经 CAS。

### 4.3 拉取与本地确认也是协议的一半

本地分三层：已确认 remote mirror、尚未确认的本地命令、两者推导的 working view。上传 V1 时又保存 V2，V2 必须留在 pending，V1 的确认不能把整个当前对象标记为已同步。

拉取先固定云端 endHead，按连续提交序号获取完整 commit；收到的变更暂存，不以半个命令更新工作视图。应用时在**同一 Dexie 事务**内校验 uid/libraryId/dataGeneration，写 remote mirror、ledger 基线、确认特定 commandId、重放仍在 pending 的命令、更新 working view/冲突证据及连续 pull cursor。重放无法安全应用时保留本地版本为候选。失败则全部回滚，纯下载路径同样执行。

按 receipt 确认某次上传只更新该命令的确认信息，不越过未读提交推进 pull cursor；确认后也不能丢弃尚未进入连续远端镜像的本地可见结果。断电后凭 pending、receipt 和 cursor 重做；epoch 只是变化提示，不是行级 CAS 或确认列表。

同一账号多窗口可能重试同一命令；以稳定 ID、事务和 head 比较保障幂等，不依赖只有一个窗口活着。退避重试有上限，持续失败保留本地可用并给诊断，不无限忙循环。

## 5. 典型双端场景

- 一端改节点说明，另一端改同节点标题：独立单元合并；任一端同时删除则进入删除/编辑判定。
- 两端改同一说明：正式内容保留一个已提交版本，另一份可逐字查看、复制或合并；不能只保留冲突计数。
- 两端移动同一节点：一个正式位置加候选目标，子树始终只有一份；用户可以采用另一位置或保留当前，不能自动变成两个子树。
- 两端移动不同节点：合并后仍无环、父级有效才接受；成环意图进入待处理，导图继续可打开。
- 删除祖先与另一端编辑后代：删除不物理删后代，新内容进入可发现的“待恢复分支”；不在空白画布里永久隐藏。
- 上传已云端成功但本机超时：复用命令 ID 查询/重试；不能二次创建。上传期间继续编辑：仅确认已上传版本。
- 普通日志晚于知识引用到达：显示“原日志暂不可用，等待日志同步”，不是永久断链；后续自动刷新，不制造知识冲突。
- 恢复与在途同步相遇：数据代际隔离旧回调；云上已发生的提交不能靠本机取消请求撤回，按第 7 节处理。

## 6. 删除、归档与日志引用状态

### 6.1 专题与节点

专题归档是可逆的组织状态，不是删除；默认检索和待整理统计排除归档专题，可显式包含。专题软删除进入知识库回收站，不级联抹掉节点、引用或原日志。

节点删除默认为“此分支移入知识库回收站”：只对分支根写墓碑，后代因祖先状态不可见，仍完整保留。界面先显示影响的节点/引用数。v1 不提供含糊的“只删这个位置但保留别名”；移除引用只删引用，不影响原日志。移动子节点脱离被删祖先须为显式恢复/移动命令，不能由普通编辑偷偷完成。

并发移动已移出分支的节点不再受该祖先墓碑隐藏，但保留删除/移动分歧提示；还在隐藏分支内的新修改可从回收站和待处理定位。恢复使用当前父级；父级已删除/失效时要求选择有效位置或专题根，不盲目还原旧对象。候选位置再次应用时重新验证环与生命周期。

首期无自动永久清空知识墓碑/历史；不以“过了 30 天”替代所有设备已确认的证明。若未来做压缩/清理，需单独设计设备水位、离线过期策略与备份恢复兼容。

### 6.2 日志引用解析

引用状态是对普通日志数据的投影，不回写成知识库事实：正常可打开；日志回收站可查看/按既有入口恢复；本机未知则等待/手动同步；有可信删除证据才称“已永久删除”；损坏或权限不足单独提示。

不能从“查不到 ID”直接推定永久删除，不能由知识通道自动恢复日志。一次完整知识提交应用后再判断结构孤儿；跨通道尚未到达的 recordId 不是结构损坏。恢复原日志后引用重新可用。

## 7. 备份、恢复与旧版本兼容

### 7.1 四态解析与完整性

所有导出/导入路径明确处理 knowledge：缺字段 = 旧包未覆盖知识库，保留本机知识库；合法空集合 = 包里明确为空，只有用户选择该恢复范围并确认清空才替换；合法非空 = 校验后恢复；损坏或未来不支持版本 = 写入前拒绝，不降级为空。

便携备份含专题、节点、引用、墓碑、候选原文和解决关系，以及解释这些关系必要的不可变版本。pending 本机编辑的内容也不能遗漏；输出为恢复后的事实/候选，不携带原账号待上传命令。排除 UID 凭据、云 ledger、cursor、receipt、锁、设备运行状态和可重建索引。新库恢复时重建协议基线，不能冒充已经与云端确认。

覆盖普通 ZIP、Android 原生流式、目录/仓库、自动备份及相应恢复入口；普通云恢复快照的原格式保持日志范围，UI 不把它称作包含知识库的完整恢复。云端知识版本保留不是独立离线备份的替代品。按引用恢复不新造日志副本；备份引用缺少日志事实须展示未知目标，不假造正文。

### 7.2 新完整包必须让旧读取器失败关闭

仅把 manifest.version 从 6 改成 7 不足：当前普通 ZIP 与原生仓库路径检查版本，但 Android 流式入口显式重建字段，入口处没有同等版本拒绝。不能假设“新增字段旧端会透传”。

选定新完整包采用新的外层 manifest 与版本化主载荷入口，例如 manifest.json + snapshot-v7.json，**不再提供根 data.json**。新读取器先检验容器、能力和校验和，再进入 staging；受支持旧读取器应在缺少旧必需入口或版本不兼容时、任何恢复写入前失败。原生仓库等不同容器分别做等价门禁，不能只改 ZIP。具体文件名为待工程验证的编码合同，v7 为提议版本号。

可显式导出“仅日志的兼容包”，但必须提示不含知识库且不是完整备份；自动完整备份不能降级为兼容包。新客户端仍读旧 v1–v6 日志包并遵守缺字段保留语义。若任何已发布旧读取器仍能静默部分恢复新包，完整备份兼容门槛未通过，不能宣称已解决。

### 7.3 恢复后不自动覆盖云端

恢复预检显示包含范围、数量、候选、缺日志引用及云端关系。先暂停两个通道的新任务、提高并持久化 dataGeneration，等待/隔离本地写队列；导入内容与资源暂存，全部校验后，用户选择的日志和知识库表、备份 dirty 及新代际在一次本地事务提交。取消/失败不留下半份正式数据。大资源 staging 与现有恢复能力需专项验证，不声称一句事务就解决内存/磁盘问题。

知识库采用保守的**恢复副本**语义：云上 V10 不变，备份 V3 恢复为新的 detached 本地 libraryId，与云同步断开；原绑定库保留为可切回的库，不把其旧 ledger 复制给恢复库。旧在途操作只可能属于原库/旧代际，回调不得写入恢复库；撤销网络请求不保证云端未提交，后续原库必须核对 receipt。

恢复后可以：继续只在本机使用；切回云端库并先拉取；或明确“将恢复专题另存到当前账号云库”，为专题/节点/引用生成新 ID 并重映射内部关系，按有界导入命令同步，原日志 recordId 仅在身份一致时沿用。发现目标日志缺失/不匹配时阻止自动绑定，交由用户确认。v1 **不提供一键把整个云库回滚到备份**，避免 V3 被当成最新修改覆盖 V10。

恢复副本可能与云库重复，这是可见、可切换、可删除前备份的安全成本，不是自动合并结果。恢复普通日志后，原云知识库引用也可能暂时失效，预检必须说明；不能承诺两个独立通道有跨云原子事务。

### 7.4 两类旧版本问题分开验收

另一台旧设备：继续用普通日志，不读取/发布知识实体、不清理其存储；新命名空间和规则确保不是仅靠 UI 开关隔离。

同设备降级：新 schema 打开过数据库后，不支持安装旧应用直接读取，禁止自动降 schema、删库重建或重置。发布说明要求降级前备份、独立导出及明确恢复步骤；用真实旧 APK/EXE 验证拒绝行为。备份兼容不等于 IndexedDB 降级兼容。

## 8. 检索合同

全局知识检索与专题 Ctrl+F 共用查询服务但结果语义不同。只搜索已保存日志、节点说明、引用备注和可用的已接受 OCR 正文；草稿、OCR 运行过程/失败消息不检索，失败的本机 OCR 重试不抹掉已接受文本。

- 全局：按 recordId 聚合日志内容结果，展示命中片段和全部有效引用位置；组织文字结果按节点/引用身份展示，不冒充日志。显示“日志 N 条、组织项 M 项”。
- 图内：覆盖折叠分支，按稳定树序返回定位点；同一日志可有多个位置，明确“日志 N 条 / 位置 M 处”，不按文本出现次数冒充节点数。默认标题/说明/备注，可选关联正文与 OCR。
- 学科/标签/日期/收藏/资源类型是日志过滤条件。开启后默认只返回满足过滤的日志引用；纯文字节点不被虚构学科，可用“另含组织文字”开关明确纳入。专题/分支过滤对所有结果有效。
- 当前专题未整理与全库未整理分开；有效引用要求专题未删除/归档、节点及祖先可见、引用未删除。候选和回收站不算已整理，另有显式检索入口。
- 默认不搜删除、归档和冲突候选；可按分类包含并清晰标注，不能将候选当成正式内容跳转。
- 不复用 SearchPage 的 200 条展示限制作为全集/精确计数。查询可分页、异步取消，精确总数需完整计算完成；尚在扫描时显示“已找到…，继续检索”，不可伪报最终总数。

节点移动使整支的路径/范围索引失效；标题、备注、引用、日志保存/恢复/删除、OCR 接受更新均使相关索引失效。索引是可重建投影，不是事实；结果携带库代际、来源 ID 与版本。异步结果仅在当前 queryGeneration/dataGeneration 匹配时进入 UI，打开前复核对象仍存在且可见。

Ctrl+F 不抢编辑器、输入框及弹窗快捷键；Enter/Shift+Enter 跳转，临时展开祖先。退出搜索撤回搜索自己造成的展开/视口变化，保留期间用户主动展开操作；若用户已手动移动视口则不强制跳回旧点。

## 9. 导航、登录退出与运行状态

返回上下文包含 libraryId/workspaceId/nodeId/referenceId、视图类型、选中、搜索和本机视口，以设备本地有界来源栈保存。专题 A → 日志 → 专题 B → 日志应逐层返回，不只存一个 returnNodeId。原位置删除时回到最近有效祖先/专题入口并解释原因。

Android Back/Escape 优先：取消拖拽 → 关闭弹层/处理未保存编辑 → 退出搜索 → 消费来源栈 → 既有页面返回。必须接入现有 TabMemory、Web history 的序列化/白名单与 Android Back 处理，不另造平行路由系统；未知旧 history 状态安全退回知识库首页。

知识库本地数据按 libraryId 隔离，账号绑定显式记录：本机未绑定库首次启用同步询问是否绑定；绑定 A 的库绝不因登录 B 自动上传。切账号前停止旧队列、提高上下文代际，当前视图切到 B 的库/空库；A 的内容保留但锁定不展示，退出后可明确选择保留或删除本机副本。设备本身未加密不等于离线内容已具备强安全隔离，不在此承诺数据库加密。

所有请求及回调携带 uid/libraryId/dataGeneration；旧账号回调在本地事务写入前拒绝。不要依赖 React 卸载或 fetch abort 保障正确性。普通日志目前的账号行为不顺带重写，也不能因此把所有本地日志默认复制到新账号知识云库；知识绑定确认须提醒引用的日志是否已在该账号同步可用。

## 10. 最小改造面与未来扩展

新增独立 knowledge repository/command、merge/sync、query、outline/map projection 与 UI 模块；仅在必要接口接入现有数据库迁移、初始化/清空、备份、登录/同步面板、日志加入/反链、导航和搜索失效通知。不整体重写 storageAdapter、useAppData、普通云协议或现有日志编辑器。

数据库升级必须是增量添加与显式迁移，保留既有数据路径、品牌、签名和包标识。备份调度增加独立 dirty 来源，不让知识库写入冒充 ordinary cloud mutation。原日志编辑继续使用已修复的 expected-row 保存规则。

为未来保留稳定 ID、来源版本、类型化查询结果和独立投影适配器。知识图谱以新的语义边/概念层扩展，不把树父级强行当知识关系；RAG 以检索结果及来源为接口；AI 需要独立范围、隐私、费用及写入授权。首期不预建向量库、插件平台、AI 自动分类、段落锚点、关系连线或多位置子树。

## 11. 实施顺序与验收门槛

以下是将来获准后的计划，不是本轮开工指令：

1. 先冻结逻辑模型、版本/冲突规范、备份容器与旧版本拒绝矩阵。做纯内存交错规格测试和只读 mock 大纲/导图交互验证；无需等全部云代码完成才能试布局。
2. 实现事务式本地 repository、迁移/恢复 staging 与备份完整闭环，再接大纲、显式编辑、日志引用及检索。
3. 实现独立云规则、原子命令、连续拉取/本地 apply、账号和恢复代际隔离；通过多数据库 harness 与 Emulator 故障注入。
4. 接入导图平移缩放/整理交互，完成 desktop 与窄屏 Playwright；经授权后再做实际 Android/desktop 双端验收。

必须覆盖：两端同字段/不同字段/不同节点成环；删除与后代编辑/移动；第三设备新增冲突；两设备同时解决；已覆盖祖先重放与祖先派生新修改；重复命令/超时未知提交；云成功本机失败；V1 上传期间 V2 保存；纯下载 apply 失败；分页缺口；切账号/退出/恢复期间晚回调；四态备份及各入口；真实旧包/旧程序拒绝；普通 GC 不触及知识数据；知识-only 写入触发自动备份但不脏普通同步；一端只浏览不产生云写入。

交互验收包括触屏平移不编辑、拖动不点击、IME、长标题、长备注、分支折叠、Ctrl+F 全集与计数、返回多层来源、保存失败输入保留、失效目标可恢复。

容量目标为 500 条日志、1000 个节点、数千引用的测试夹具，不是现有性能测量或硬容量限制。实施前确定目标 Android 设备、加载/搜索/帧率与内存阈值，再测量；未达到时优先分页、虚拟化和折叠，不删数据降负载。

### 11.1 冻结前需确认的产品取舍

用户需确认：单正式位置、不自动复制并发移动子树；纯文本批注；恢复副本而非云库回滚；独立知识同步状态；新完整备份与旧程序不互读。其余合同不得在编码时偷偷改回旧稿行为。

### 11.2 仍需工程验证，不虚报完成

有界排序键与重排、规范化编码/版本 DAG 终止性、事务与规则预算、全通道备份失败关闭、恢复 staging 的资源边界、真实旧客户端兼容均未实现或验证。冻结前应把它们拆成可执行规格与验收用例；规则或容器验证推翻当前假设时，先回到设计评审，不通过扩大普通同步改造来绕过。

本轮只完成设计审查与修订；内存反例只证明旧稿几处逻辑不成立，不是新协议的正确性证明。SJ-AUD-01 既有 1708 项测试和 Emulator 结果不能作为本稿的实现验收证据。
