## 0. 审查范围与结论

材料：用户提供的 D:/DeskTop/设计方案审查报告.md；本仓库初稿 knowledge-library-v1-design-2026-09-22.md；main@b6c36da 上的当前工作区（包含尚未提交的 SJ-AUD-01 修复）。报告引用的是另一个目录里的初稿，不能直接照搬其行号或假设其工作区与当前相同。

**结论：报告指出的核心模型矛盾与同步缺口成立，值得在冻结前解决；但它不是 17 个已发生的产品 bug 清单，也不要求照单实现一整套分布式平台。** 修订稿是 knowledge-library-v1-design-r2-2026-09-22.md。本轮仅改文档，既有修复与测试文件保持不变。

独立核验方式：阅读初稿及报告；用 CodeGraph 定位并读取同步、备份、导航和搜索实现；补看明确文件的相关范围；用不写入项目的内存断言核对位置归属、合并成环、结构字段撕裂和 V1/V2 确认反例。后两项断言仅是合同示例，不是现有产品缺陷复现，也不是新同步协议证明。

本报告路径均相对仓库根，行号为本轮核验时的定位点。新增设计名称表示提议，不表示模块已经存在。

## 1. 多位置与引用归属：成立，必须改模型

初稿 §2.2 的引用绑 placementId，子树绑 parentPlacementId；§5.3 却要求新增位置共享引用和子树。共享 nodeId 不会让另一个 placement 自动取得原引用与孩子。内存检查也直接得到第二位置的引用/孩子为空。

采纳报告“首期不要因冲突引入完整别名”的方向，但进一步简化：R2 §2 取消 Placement，一个节点一个正式位置，引用绑 nodeId；另一移动目标仅保存为候选。保留同一日志多节点引用，不承诺节点别名。真正别名系统不是本期必要投入。

## 2. 合并后的环：成立，不能只验证单端

P、Q 为根，各端分别执行 P→Q 与 Q→P 都合法，合并后却成环。初稿的本地后代检查不能消除此反例。检查整棵受影响树与保留失败移动意图是正确要求。

R2 §2.3、§4.2 将准备时的图绑定云 head CAS，合并后再验证；不合法结构不进正式树。候选可以是暂不可执行的意图，不需要为候选再建“合法影子树”。

## 3. 父级与顺序原子化：成立，修正表述

初稿虽说一次本地事务更新 parent/order，却未禁止云端按字段拆开合并。移动与同级排序可拼出任一用户都未选择的组合。

R2 §2.2 定义 position 为一个合并单元；同值稳定排序保留，但并发移动不能独立挑 parent 与 order。无需为此升级为通用序列 CRDT。

## 4. 冲突自身的生命周期：成立，但不另造协作平台

初稿 ConflictItem 只有双方快照与 resolvedAt，不足以描述第三台设备、并发解决、旧候选重传。单个 conflictState 也容易与证据脱节。

R2 §3.2 使用不可变小版本、确定性证据身份、候选集合基线检查和覆盖关系；候选状态从证据推导。解决是新命令，陈旧解决拒绝且保留输入。v1 不做自动文本融合或完整多人实时协作。

## 5. 共同基线与三方合并：成立，现有通用支持不能假定

源码 cloudSyncService.ts:1633、1681 只给 settings/template 保存 basePayload；cloudSyncModel.ts:553 的 mergeCloudSyncSmallEntity 也不是任意知识实体合并器。

R2 §3.2 为知识单元明确 revision、父版本、规范化 hash 和缺基线行为；不复用“已有三方合并”四个字跳过协议设计。现有普通同步保持原边界。

## 6. 云确认后的本地 apply：成立，是关键缺口

上传 V1 时再编辑 V2，云确认只能确认 V1；将当前整行当已同步会漏传 V2。epoch 不能说明具体哪次命令已提交。现有普通同步的 ledger/cursor 处理不构成未来知识通道自动安全的证据。

R2 §4.3 分 remote mirror/pending/working view；实体、基线、命令确认、重放与连续 cursor 同事务提交，纯下载同样适用。定向查 receipt 不跳过拉取缺口。这是必须补齐的正确性合同，不是可延后优化。

## 7. CAS、幂等和部分提交：问题成立，所列设施不是全要建

报告要求 expected 真正进入事务、命令有稳定 ID、未知提交可确认，合理。但分批 staging、租约 fencing、长操作锁只在选用相应协议后才是必需；不能因报告列了这些术语就全部实现。

R2 §4.2 选有界原子小命令，一次事务包含变更/证据/receipt/head。大批量由多个独立小命令组成，明确部分成功；不把单个语义原子操作拆散。首期无需远端租约或自建跨批次事务协调器；仍需验证规则和事务预算。

## 8. 独立通道的完整隔离：成立，可用缩小范围来解决

cloudSyncService.ts:1875 的普通 Storage GC 按现有 entities/快照保留集清理普通 assets/documents 根；把新对象塞进同根但不进保留集有风险。autoBackupService.ts:156 是另一套 dirty 调度，不能以普通云 epoch 代替。

R2 §4.1 独立 Firestore 顶层根、本地 ledger/cursor/epoch，首期根本不写 Knowledge Storage；另接持久备份 dirty。这样既满足隔离，也避免为了纯文字首期引入新对象存储和 GC。

## 9. 旧端 capability 保护：成立，但误删有前提

firestore.rules:4 与 storage.rules:4 当前仅按用户身份递归放行，没有知识协议版本门禁。一个新前端开关约束不了已发布旧客户端。

cloudSyncService.ts:638 的 deriveLocalCloudChanges 从 ledger 中存在而 export 缺失的行推导删除，因此风险取决于旧端是否取得/处理到相应账本项。**不是任何旧端看见未知字段都会必然删云数据**，也不是现有普通同步已发生误删的证据。

R2 取消混通道后备路径，在不受旧递归规则覆盖的新顶层命名空间加专用规则；不能在旧广泛放行下面仅叠一条更严格的规则就声称已限制。规则行为需 Emulator 验收。

## 10. 跨通道暂缺与孤儿：成立，状态要分层

独立通道无法保证日志和引用同时到达，查无 recordId 不等于永久删除。知识提交尚未完整应用时也不应做不可逆修复。

R2 §6.2 将正常/回收站/暂不可用/有证据永久删除分开；引用状态是派生显示，不作为同步冲突写回。正式结构只在完整 commit 后验证，短暂的跨通道缺日志不制造永久待处理项。

## 11. 删除、归档、恢复入口与墓碑：成立，但设备水位系统后置

初稿有“软删除不级联”的原则，却没有说不可见后代在哪里找、如何恢复、删除祖先时远端编辑怎么办。保留数据库行但无入口仍可能造成实际不可恢复体验。

R2 §6.1 定义分支根墓碑、回收站/待恢复分支、显式选择恢复位置与移除引用语义。首期不自动 GC，因此暂不建设全设备水位协议；不能一边省略水位一边按时间永久清理。这是用限制破坏性能力换取首期可靠性。

## 12. 备份四态与所有路径：成立，不能只追加字段

backup.ts:126 的 zipToSnapshot、streamingBackupService.ts:168 的原生导入、nativeRepositoryBackupService.ts:163 的 normalizeSnapshot 都显式重建 payload；添加类型定义不会自动透传新数据。已有 dailyPlans 的缺字段保留语义可作参考，但不能替代 knowledge 完整性合同。

R2 §7.1 明确缺字段/合法空/非空/损坏或未知版本，包含孤儿/候选和解释它们的必要版本，不携带运行 ledger/锁。备份导出需覆盖尚未上传的本机内容，不能只备云端镜像。

## 13. 恢复后的再次同步：成立，首期不做自动云回滚

恢复锁 restoreLockService.ts:7、32 是进程内状态，不是持久数据代际。旧包 V3 恢复后如何面对云 V10，原方案未决定；“暂停同步”也不能撤销已发到服务器的请求。

R2 §7.3 使用 staging + 本地选中范围原子替换、代际隔离、detached 恢复副本；云库保留，之后显式另存新 ID 或切回云库。无需因此给普通日志与知识通道引入跨云分布式事务，但恢复体验变化必须由用户确认。

## 14. 新备份与数据库降级：成立，且报告建议还不够

database.ts:353 当前 schema 24；backup.ts:157 与 nativeRepositoryBackupService.ts:163 校验 v1–v6。但 streamingBackupService.ts:168 的入口没有同等外层版本校验，而是读取 data.json 后直接组装载荷。

因此，**仅升备份版本号不能据此证明所有旧端会拒绝**。R2 §7.2 选新容器入口且不提供旧必需 data.json，逐通道验证写前拒绝；§7.4 将另一台旧设备与同设备安装旧程序分开验收。这里比原报告更保守，不把未经测试的桥接发布或版本号当既成保护。

## 15. 检索计数与索引失效：成立，部分是产品选择

SearchPage.tsx:19 的结果限制为 200；:53 请求上限+1，:73 截断。它适合当前页面显示，不适合作为图内完整命中计数。Tab/视口无关索引、保存态与草稿、路径失效、日志去重与位置数都需明确。

R2 §8 明确两种结果口径、纯文字节点过滤、归档/候选范围、OCR 可用正文、query/dataGeneration 和打开前复核。不要求首期为数百条记录预建向量检索或分布式索引，先共享查询合同即可。

## 16. 编辑器行为：成立，低成本明确即可

标题/说明/备注是新写入口，不能只说“可编辑”而遗漏保存、失败、IME、离开和陈旧基线。报告的关注与 SJ-AUD-01 证明的事务边界问题方向一致，但不是说知识库已出现相同 bug。

R2 §1.3、§3.1 选纯文本显式保存、字段 expected、保留本机草稿、稳定命令 ID。不增加节点附件或富文本编辑器，避免扩大资源生命周期与 OCR 所有权。

## 17. 导航、部分成功和账号隔离：成立，拒绝顺带重写全应用

tabNavigation.ts:106 的 TabMemory 与 webNavigationHistory.ts:42 的枚举/恢复合同需要扩展；不能只在组件里加一个 returnNodeId。cloudSyncService.ts:585 的 localState 在换 UID 时清旧普通账本，不等于新增知识库已按账号隔离。

R2 §9 明确来源栈、Back 优先级、账号绑定库及回调代际；§4.1 独立显示两个通道结果。普通日志的账户模型不借机整体重构，跨账号日志可用性通过明确绑定确认和未知引用提示处理。

## 18. 对总体建议的采纳与修正

- “当前仍需先解除知识库范围冻结”：对当前工作区已过时。scope-unfreeze-2026-09-22 已记录范围解冻；后续暂停是等待 SJ-AUD-01 验收与设计冻结、开工授权。不能混淆范围授权与实施许可。
- “先让用户看到交互样机”：方向合理，可与协议验证并行，但本轮没有授权实施/样机，故只列将来计划。
- “500 日志、1000 节点、数千引用”：可作验收夹具，不是现有性能数据、硬上限或真机验收结果。
- “加强测试”：采纳交错、恢复、旧端与故障注入；不拿先前 SJ-AUD-01 的绿测替代新功能验收，也不为纯文档变更重跑整套业务测试后宣称协议正确。

## 19. 冻结建议

不按原稿直接冻结。先评审 R2 中明显影响用户体验的五项取舍：单位置树、纯文本批注、独立通道状态、恢复副本、新完整包不兼容旧程序。它们在首期降低隐式合并和误覆盖风险，但均有可见成本。

随后把规范化/版本算法、有界排序、云规则事务预算、新容器各路径失败关闭和恢复资源边界补成可执行规格。尚未验证的工程假设保持公开，不把“写进设计文档”叫作“可靠性已经完成”。用户确认冻结及明确开工前，不修改知识库业务代码或部署。
