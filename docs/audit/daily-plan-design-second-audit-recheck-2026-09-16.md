## 0. 结论先行

**审计 B 与审计 A 的失败方式完全不同，而且它的失败更根本。**

- **审计 A** 是"读错了代码"：用不可靠的工具得出了 4 条事实错误（例如断言 `createRecordBlock` 不存在）。

## 2. 最危险的一处：它为「无草稿消除竞态」背书（把 P0 级缺陷判成 ✅）

**审计 B 的原话**（§四 4.2）：

> **理由**（设计文档已明确）：
> - `RecordEditorPage.tsx:642-659` 的 `flushDraft()` 是异步的，不阻塞返回
> - 判据包含"无草稿"后，**回收器天然等待草稿写入完成**
> - 无需改动编辑器语义

并在一开始就给整条设计打了 ✅：「✅ **判空逻辑设计** - 六项判据完整，考虑了草稿竞态」、「✅ **回收器设计** - 触发时机、幂等性、竞态处理正确」。

**「回收器天然等待草稿写入完成」这句话是错的，而且反了方向。**

源码事实（我已在审计 A 的复核中逐条验证，此处给最简链条）：

1. `RecordEditorPage.back()`（:642-659）**同步**执行 `onBack()`（:658），之后才在不被 await 的异步块里 `await flushDraft()`（:648-651）。:653 的注释是刻意的：`// Returning must not depend on a recorder or storage operation completing.`
2. 卸载清理（:461-468）同样 `void flushDraft()`，不 await。
3. `flushDraft`（:269-311）在 :278 有守卫「**无改动则直接 return**」→ 没输入就不写草稿、**输入了才写**。
4. `permanentlyDeleteBlock`（`storageAdapter.ts:1619-1644`）在事务里会 `db.recordDrafts.delete(blockId)`（:1631）。

**回收器不会"等待"它——回收器读到的"没有草稿"恰恰是"还没写完"的假象。** 真正发生的是：

```
用户输入 → 立刻返回
  → onBack() 同步 → 导航变更 → 回收器触发（由导航驱动）
  → 回收器直读 Dexie：正文还是空的、recordDrafts 还没有行
  → 判定 isEmpty = true → 物理删除
  → flushDraft 此刻才落盘（记录已不存在）→ 用户输入丢失
```

**所以这条不是"天然的竞态消除"，而是"用一个不稳定的观察结果去做不可逆的删除决定"。** 审计 A 至少把它列为问题（虽然修法不对）；审计 B **主动论证它是对的**，这比不发现更糟——它会让实现者跳过这条风险。

**为什么它值得单列**：这是设计里**唯一**会静默删除用户已输入内容的路径，也是本次两轮复核中我判定必须最先修的一条（修订 R-1）。

## 3. 第二危险的一处：它给「反向墓碑」打了 ✅

**审计 B 的原话**（§十一 风险表）：

> | 恢复旧备份后同步的反向墓碑 | 中 | 计划不新增该路径；P5 复测 | ✅ **明确不做特殊处理** |

**「计划不新增该路径」是错的——它会自动进入该路径，而且是全量删除。**

`src/services/cloudSyncService.ts:2057-2059`：

```ts
const tombstones = allRemote.entities
  .filter((entity) => !localKeys.has(entity.key) && !entity.deleted
    && entity.entityType !== "review-state" && entity.entityType !== "review-day-stat")
  .map((entity) => ({ ...entity, contentHash: `deleted:${entity.contentHash}`, payload: {}, deleted: true }));
```

这是一份**写死的排除清单**。新实体类型 `daily-plan` **不在其中** → 它会走"远端存在、本地没有 ⇒ 生成墓碑 ⇒ 删除"这条默认路径。叠加**恢复一份本功能上线前的旧备份**（其 `payload` 里没有 `dailyPlans` → 本机计划为空）→ 同步一次，**其他设备上的全部计划被删**。

配套的第二条同类风险它也完全没提：给 `restoreStreamableSnapshot`（:2325，清表清单 ≈:2366）加 `db.dailyPlans.clear()` 会在恢复**旧**备份时清空本机计划。修法是区分「字段缺失（`undefined`，视为旧快照，跳过清空）」与「空数组（正常清空）」——这需要设计明确表态，而审计 B 只说"特别注意显式清表清单"，把它当作一个机械的补漏项。

**它把设计里唯一被标为"既有极高风险"的路径，判成了 ✅。**

## 4. 它把真缺陷列为「设计亮点」

审计 B（§九 边界与异常矩阵审计）：

> **设计亮点**：
> - **边界 20**：并发兑现检查 `linkedRecordId`，避免重复创建

审计 A 在这一点上是对的（列为问题），审计 B 打成了亮点。事实：

- 设计 §6.7 自己的时序是「点计划条目 → `today.recordId = r1` → `createRecordBlock` + `linkPlanRecord` + `markCloudSyncMutation`」。要拿到 `r1` 必须先 `await createRecordBlock`，而它内部串了 `listBlocks` + `getSettings` + `saveBlock` + `refresh` + `markAutoBackupDirty`（`useAppData.ts:818-845`）——**导航在整个 IndexedDB 往返之后才发生，列表在这段窗口内一直可点**。
- "先查 `linkedRecordId`"是一次**读**，两次点击都可能读到 `undefined`。正确做法是页内 in-flight `Set<EntityId>`（确定性、无时长猜测），而不是靠读一次状态。

**"读一次就够"的假设，和 §2 的"读一次就够"是同一个错误模式：把一个不稳定的观察结果当作充分条件。**

## 5. 它的"修复示例"含有 API 层面的错误

审计 B §8.1 给出接线代码：

```typescript
const openDailyPlan = () => {
  setTabMemory({
    ...tabMemory,
    today: { ...tabMemory.today, planOpen: true, planView: "today" },
  });
};
```

**`setTabMemory` 确实存在**（`App.tsx:253` 的 `useState` setter）——所以这段代码能编过。但它**绕过了这仓库唯一的导航提交入口** `commitNavigation`（:297-341），而后者做四件 `setTabMemory` 不做的事：

1. **web 历史 push/replace**（:306-330）→ 不做就没有浏览器历史条目，网页版 Back 直接失效（而 §6.5 整节就是为了这个）
2. **`setNavigationMotion(motion)`**（:334）→ 不做就没有 §6.7 承诺的 `forward` 过渡动画
3. **`navigationStateRef.current = next`**（:333）→ **不做会让 ref 变成陈旧值**，而 `popCurrentTabDepth`（:466）、安卓返回键（:763）、状态机全部读这个 ref
4. `setActiveTab` / `setActiveAiSessionId`（:335、:337）

`setTabMemory` 的真实角色是 `commitNavigation` 内部的一行（:336），属私有实现细节。另外它传的对象形状也不对：`setTabMemory` 期望 `TabMemory` 切片，而它把整个状态对象和解构混在一起。

**这是审计 B 唯一一处给出可执行代码的地方，而这段代码会同时破坏 §6.5 与 §6.7。** 这也说明它没有读 `commitNavigation`——而"新页面如何进入导航状态机"正是本次设计最需要外部审视的部分。

## 6. 它自相矛盾的一处（引用与结论冲突）

审计 B §四 4.2 的结构是：

1. **第 151-152 行**：引用设计原文——「标题不参与判空（关键）：计划记录的标题在被创建时就被写成了计划标题（§5.1），所以标题天然非空。」
2. **第 159-163 行**：构造失败链——
   > 1. 计划标题未写入记录 `title`
   > 2. 用户点进去不写就返回
   > 3. 判空时 `title` 为自动生成的"数学记录块1"（**不是空**）
   > 4. 误认为"非空"而不回收 → 产生垃圾日志

它刚刚引用了"判据只认正文/资源/公式/标签/决策块/复习状态/草稿，`title` 一律忽略"，紧接着就构造了一个**"title 非空 ⇒ 判为非空"**的失败链。**这条链只有在它引用的那句话不成立时才可能发生。** 它引用来当风险说明的那条设计，恰恰是消解它自己所描述风险的那条设计。

（顺带：它漏掉了这条设计**真正**的风险，而且方向相反——`title` 被写入计划标题之后，**不能让 `title` 参与判空**，否则"点进去不写就返回"会留下一条只有标题的记录并被计为**已完成**。这个错误方向我已经在设计的 §4.2 里显式加固过。）

## 11. 最终裁定

**审计 B：不通过。**

- **框架错误**：把"设计文档"当"实施报告"，10 项"严重阻塞"实为"设计要求尚未执行"；同时给设计打 5/5，内部不一致。
- **方向错误（最严重）**：在设计里**三处会造成不可逆数据丢失或行为破坏**的问题上打了 ✅（`flushDraft` 竞态、反向墓碑、并发双击），其中前两处是本次两轮复核中排在最前面必须修的两条。**一次把红牌当绿牌的审计，比一次没有发现的审计更有害**——它会让实现者跳过风险。
- **技术错误**：修复示例绕过 `commitNavigation`（会同时破坏浏览器历史与过渡动画、并让 `navigationStateRef` 陈旧）；§4.2 的失败链与它自己引用的设计原文互相矛盾；重复了"3 个索引"的笔误；把一行别名列成独立必改点。
- **可保留的贡献**：行号准确度高（20+ 处抽查基本精确）；对 §2.4 的判断优于审计 A 且正确；指出 `buildTabPageKey` 缺文件位置；提出签名扩展与判空测试的先后依赖。这些已并入 §10 的 S-1…S-6。

**对两份审计关系的结论**：它们在 7 个争议点上各错一半、**没有一处是两份都判对的**。**结论是这两份审计都不具备"可直接照做"的效力**，只能当线索用；真正的依据只能是源码。

**对设计文档的净结果（两轮复核合计）**：设计的方向、数据模型、导航复用策略、同步分层纪律、测试规划**均成立**；需要修订的是 **R-1…R-12（12 条，来自审计 A 复核 + 我的独立核对）与 S-1…S-6（6 条，来自本轮）**，共 **18 条**。其中 **R-1（竞态与用户输入丢失）、R-8④（破坏性清空 `linkedRecordId`）、R-9/R-10（备份与同步的删除放大路径）、R-2（空记录误判为已完成）** 必须在进入 P2 与 P5 之前定稿——它们的失败形态不可逆，无法靠事后测试补救。
