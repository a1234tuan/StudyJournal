# 云同步黑盒验收场景（2026-09-21）

## 这份清单的定位

**22 组黑盒使用场景**，用于在不看代码、不依赖任何一次具体修改实现的前提下，验收"两端（手机 ↔ 电脑）使用过程中不会丢内容、不会互相覆盖、不需要人工兜底"。

**关键约束：期望只写成"用户可观测的结果"**，不引用任何函数名、表名、字段名、日志编号。因此本清单与具体改法无关：同一组场景在**任何**正确实现下都必须成立；若某组不成立，说明该实现有缺陷，而不是"用例写错了"。

三条判定纪律：

1. **优先断言"不得出现"**（不得覆盖、不得复活、不得丢失、不得误报冲突、不得静默无反应），而不是断言具体数字或内部状态。数字只在"零变化"这一处使用。
2. **收敛判据**：每组的最后一步都要求再做**两轮无操作同步**，两端必须零变化。任何"看似同步完成、实际每轮都在互写"的实现都会在这里暴露。
3. **提示必须配恢复路径**：任何"已暂停 / 请核对 / 冲突"类的用户可见提示，都必须同时存在一条让用户能继续工作的路径（重试、放弃本机改动、以某端为准等）。只有提示、没有出口 = 判定为不可接受。

**前置条件（不满足则部分期望不成立，必须先核对）**：两端运行的是**同一修复版**（版本号/构建时间一致）。两端版本不同时，本清单只能用于"混用版本"专项验收，不能作为修复版验收。

## 观测手段（全部为外部可观测量，不依赖实现细节）

| 手段 | 能看到什么 | 适用 |
|---|---|---|
| 两端界面逐项比对 | 标题、正文、标签、收藏、回收站列表、统计数字 | 全部用例 |
| 同步结果提示 | 已同步 / 无变化 / 需要核对 / 冲突 / 暂停写入 等文案 | 15–22 |
| **明文备份导出**（应用自动备份的快照文件） | 两端各自的"事实状态"全量明文，可逐键比对 | 全部用例（最强调定口径） |
| Firebase Emulator 控制台 | 远端文档被写过几次、内容是什么、是否存在无人认领的写入 | 15–18、20 |
| 浏览器/桌面的网络面板 | "无变化同步"是否仍在发写请求 | 4、8、14 |
| 应用内回收站 / 统计页 | 派生结果是否与主视图一致 | 5–8、11 |

> 真机双端是唯一能覆盖"后台被杀、弱网、多进程并发"的环境；浏览器模拟只能作为前置排查，不能作为验收证据。

## 一、基础收敛（BB-01 ~ BB-04）

### BB-01 单向编辑往返
- **前置**：两端数据一致，各自同步一次确认"无变化"。
- **操作**：A 新建一条记录并写正文 → A 同步 → B 同步 → B 打开该记录 → B 再同步 → A 再同步。
- **期望**：B 看到的内容与 A 完全一致（含正文、标签、日期、收藏）；随后 A、B 各再同步 **两轮**，两端均为"无变化"，回收站、统计页数字不变。
- **隐蔽点**：只有"编辑 → 接收"这一段被验证过，很容易漏掉"接收端反向把收到的内容当成新改动的上传"。**必须交换方向再跑一遍**（B 编辑 → A 接收），两个方向的不变量是对称的。
- **反例信号**：第二轮同步仍显示"已同步 N 项"；或 B 收到后在 A 端又被覆盖回旧内容。
- **判定手段**：两端界面 + 端备份快照明文比对。

### BB-02 两端各自编辑不同记录
- **前置**：A、B 各有一条独立记录。
- **操作**：A 改自己的记录并同步 → B 在**未同步**的情况下改自己的记录 → B 同步 → A 同步 → 两端再各同步两轮。
- **期望**：两端的**两条**记录最终都保留各自的最新内容，且都出现在两端；无冲突提示；无重复条目。
- **隐蔽点**：B 是在"落后一个修订"的状态下本地编辑的。若实现把"落后"误判为"冲突"或"需要暂停"，用户会看到莫名其妙的冲突提示；若实现把 B 的本地改动丢掉，则表现为"编辑没保存"。
- **反例信号**：出现冲突提示；B 的记录内容消失或回退；某一端出现同一记录的两个版本。

### BB-03 两端各自编辑同一条记录（真冲突）
- **前置**：两端数据一致。
- **操作**：A 改记录 R 的标题为"A 版" → A 同步 → B 在**未同步**时改 R 的标题为"B 版" → B 同步 → A 同步。
- **期望**：出现**明确的冲突提示**，说明是哪一条记录冲突，并给出可选处理（保留本机 / 采用云端 / 稍后处理）；在用户做出选择之前，**任何一端的 R 内容都不得被自己或对方静默改写**；用户选择后两端一致。
- **隐蔽点**：冲突提示必须是**可操作**的。很容易出现"提示了冲突但页面没有入口"，用户只能反复点同步。
- **反例信号**：静默覆盖（一端变成另一端的内容）；冲突提示出现但无处理入口；两端各自显示不同内容且永远不再收敛。
- **判定手段**：两端界面 + 冲突提示文案 + 用户处理后的两端快照比对。

### BB-04 无操作重复同步
- **前置**：两端已一致。
- **操作**：不做任何编辑，连续触发 4 次同步；其间前后台切换一次、关闭并重开应用一次。
- **期望**：第一次之后全部为"无变化"；两端状态**完全不**改变；不产生新的冲突、不产生新的备份、回收站不变化。
- **隐蔽点**：启动、切前后台、重开应用都可能触发"自动整理/自动接管/自动挑选任务"之类的隐式写入，这类写入在单端看不见，但在双端会与另一端的同步互相打断（表现为偶发的"同步失败/请重试"）。
- **反例信号**：某次同步提示"已同步 1 项"；另一端的同步突然要求核对；备份文件数量无故增加。

## 二、删除与回收站（BB-05 ~ BB-08）

### BB-05 软删除与回收站一致
- **前置**：两端一致，某条记录在两端都可见。
- **操作**：A 删除该记录（进入回收站，不永久删除）→ A 同步 → B 同步 → A 再同步 → B、A 各再同步两轮。
- **期望**：B 看到该记录进入回收站（而不是消失/或被复活成正常记录）；两端回收站内容一致；A 再同步时**不得**再把它当作新改动上传；两端最终无变化。
- **隐蔽点**：这是最容易出错的一组。若接收端把"已删除但仍在回收站"的条目当成"不存在"，它会反过来生成一条"删除"再上传，两端来回删除/复活。
- **反例信号**：B 完全看不到该条目（连回收站都没有）；回收站里出现两条同名；恢复按钮点了没反应；同步反复提示有变化。
- **判定手段**：两端回收站列表 + 快照明文。

### BB-06 永久删除与超期清理不得复活
- **前置**：两端一致。
- **操作**：(a) A 在回收站里把某条记录永久删除 → 同步 → B 同步 → B 打开回收站查看；(b) 另设一条"已删除超过 30 天"的记录，两端同步并触发自动清理。
- **期望**：(a) B 的回收站里该条目**消失**，且后续任何一轮同步都**不得**让它重新出现（含 A 端再次同步）；(b) 超期条目在两端都被清理；**未超期**的回收站条目在两端都保留。
- **隐蔽点**："永久删除"与"回收站删除"在界面上只差一次点击，但跨端语义完全相反。若两者在同步层被同样对待，会出现"删掉了又回来"。要特别验证**删除方自己再同步一轮之后**不会把回收站内容又推出去。
- **反例信号**：永久删除的条目在另一端复活；超期条目在一端清掉、另一端还在；未超期条目被误清。

### BB-07 删除 → 恢复 → 再删除（交错）
- **前置**：两端一致。
- **操作**：A 删除记录 R → A 同步 → B 同步 → B 从回收站恢复 R → B 同步 → A 同步 → A 再次删除 R → A 同步 → B 同步。
- **期望**：每一步之后的最终状态都与"最后执行动作的那一端"一致，且中间步骤在另一端都能被观察到（而不是被跳过）；最终两端一致且无变化。
- **隐蔽点**：这是"删除/反删除"来回拉锯场景。若某一步被同步层判定为"没有变化"，用户会看到"我在 B 恢复了，A 那边还是删掉的"。**每一步之间都必须让另一端完成一次同步**，不能攒着一起做。
- **反例信号**：中间某一步在另一端不可见；最终两端不一致；恢复后的记录内容缺失（只剩标题）。

### BB-08 只读浏览不产生写入
- **前置**：两端一致。
- **操作**：在 B 上只打开回收站页面、记录只读预览、复习页原文预览，**不做任何编辑、不点任何保存/恢复**，停留一会儿后返回；随后两端各同步两轮。
- **期望**：所有只读浏览路径都**不产生**任何上传/下载，两端零变化；回收站条目状态不变。
- **隐蔽点**：只读页面仍然可能触达"草稿/状态"类共享存储，把"浏览"变成一次写入。这类写入在单端完全看不出来，但在双端会制造出"另一端要求核对"的噪音，用户完全无法归因。
- **反例信号**：浏览后同端出现"已同步 1 项"；另一端出现需要核对的提示；被浏览过的记录时间戳/内容被改写。

## 三、计划与日志（BB-09 ~ BB-11）

### BB-09 计划与日志的关联、改名、取消关联
- **前置**：两端一致，已有一条计划 P 和一条日志 L。
- **操作**：A 把 L 关联到 P → A 同步 → B 同步（确认关联）→ A 改 P 的标题 → 同步 → B 改 P 的关联为"不关联" → B 同步 → A 同步。
- **期望**：每次操作后两端对"P 的标题 / P 关联了哪条日志 / L 属于哪个计划"的显示完全一致；L 的正文内容在全程不受影响。
- **隐蔽点**：**"取消关联"和"删除计划"必须是两件事**：取消关联不得让日志内容或计划本体消失；反之删除计划不得连带删掉日志正文。
- **反例信号**：取消关联后日志正文变空；改名后另一端标题未更新；关联后另一端仍显示未关联。

### BB-10 空日志自动回收的边界
- **前置**：两端一致。
- **操作**：分别构造以下四种"看起来空"的日志并与计划关联后同步：
  (a) 只有空段落；(b) 只插入了图片但没有文字；(c) 只有数学公式；(d) 只有一个空表格。
  另构造 (e) 真的空（无任何块）的日志。
- **期望**：(a)–(d) **不得**被回收（内容必须保留，图片/公式/表格都必须还在）；(e) 可被回收，且回收后**两端都不再保留该空日志**，计划仍保留。
- **隐蔽点**：判断"空/非空"的规则最容易只看纯文本。图片、公式、表格在纯文本里都是空字符串，一旦判空只看文字，用户**只有图片或公式的日志会被静默删除**，而且是在两端一起消失。
- **反例信号**：含图片/公式/表格的日志在另一端或下一轮同步后消失；被回收的空日志在另一端复活；计划本体被一起删掉。
- **判定手段**：两端界面 + 快照明文中该记录的块结构。

### BB-11 计划删除/恢复后的关联与统计
- **前置**：两端一致，计划 P 关联日志 L 且有一周历史数据。
- **操作**：A 删除 P（回收站）→ 同步 → B 同步 → A 从回收站恢复 P → 同步 → B 同步 → 两端打开统计页。
- **期望**：删除期间 L 的正文与历史数据不受影响；P 恢复后关联关系恢复、统计口径与删除前一致；两端统计数字相同。
- **隐蔽点**：统计是"派生视图"，最容易在关联失效时把历史数据算漏（表现为"恢复后完成率变了"）。要对比**删除前的截图/数字**。
- **反例信号**：恢复后统计数字与删除前不同；L 的正文或历史丢失；两端统计数字不一致。

## 四、编辑器与草稿（BB-12 ~ BB-14）

### BB-12 快速编辑后立刻离开
- **前置**：两端一致。
- **操作**：A 打开记录 R，输入一段文字后**立刻**返回/切页/切换记录；再重复一次并在返回的瞬间强制结束应用（杀进程）后重开。
- **期望**：重开应用后，R 显示的是刚刚输入的内容（草稿或正式内容都可以，但**内容不得丢失**）；随后同步到 B，B 也能看到该内容。
- **隐蔽点**：输入 → 离开之间存在一个写入排队窗口，正常操作永远看不到问题，只有"立刻返回/立刻杀进程"才暴露。这类丢失在单端表现为"我的文字没了"，在多端表现为"另一端永远是旧的"。
- **反例信号**：重开后文字丢失或回到修改前；B 端永远看不到这次输入；应用提示保存失败但没有保留草稿。

### BB-13 编辑过程中另一端更新同一条记录
- **前置**：两端一致；R 在 A 上打开并处于编辑中。
- **操作**：A 只输入一部分内容（不保存）→ B 修改 R 并同步 → A 触发同步（或切到后台再回来）→ A 尝试保存。
- **期望**：(a) A 的**本机草稿必须保留**（用户已输入的内容不消失）；(b) A 不得**静默**把 B 的修改覆盖掉；(c) 出现明确的、可操作的提示（说明正式内容已更新、本机草稿仍保留）；(d) 用户按提示处理（放弃本机草稿 或 以本机为准继续）后，能正常保存，且两端最终一致。
- **隐蔽点**：只看"有没有覆盖"，会漏掉"草稿是否保住"和"提示之后能不能继续"。三个都要查，尤其是 (d)：很多实现只能"提示"，用户当场卡死。
- **反例信号**：A 保存后 B 的修改消失；A 的输入消失；只能提示、无论如何都保存不了；提示文案是给开发者看的（英文/内部术语）。

### BB-14 只读入口浏览零写入
- **前置**：两端一致。
- **操作**：在复习页打开原文预览、在记录页打开只读视图，滚动、展开、复制文字，**不做任何编辑**；随后两端各同步两轮。
- **期望**：零变化、零上传；正文内容不被改写。
- **隐蔽点**：与 BB-08 同类，但入口不同（复习流程会顺带读写"讲解/待办"类状态），容易在只读流程里顺带触发写入，且触发点极其隐蔽。
- **反例信号**：浏览后出现"已同步 N 项"；另一端提示需要核对。

## 五、中断、恢复与时间（BB-15 ~ BB-18）

### BB-15 同步中断续传
- **前置**：A 端有大量待上传内容（例如 300+ 条记录）。
- **操作**：A 开始同步 → 在中途断网（或强杀应用）→ 恢复网络 → A 再次同步 → B 同步 → 两端各再同步两轮。
- **期望**：所有内容最终到达 B；**不得**出现某个键被反复上传（表现为远端同一键被写很多次、流量异常）；不得出现"同步完成但 B 少了几条"；后续两轮均为零变化。
- **隐蔽点**：中断点是关键。要分别在**刚开始、中途、接近结束**各制造一次中断。最容易漏的是"已经部分写成功、但本机以为整体失败"导致的重传/漏传。
- **反例信号**：B 少了若干条；某一端反复提示"需要核对"且永不结束；远端同一键被反复写。
- **判定手段**：Emulator 控制台（写次数）+ 两端快照比对 + 流量/请求数。

### BB-16 恢复备份与重装后的首同步
- **前置**：A、B 已有较完整数据；A 端有较新的自动备份。
- **操作**：(a) 在 B 上恢复一份**较旧**的备份 → B 同步 → A 同步；(b) 在 B 上清空数据（重装）→ B 同步 → A 同步 → 两端各再同步两轮。
- **期望**：(a) B 恢复后同步，**不得**把备份里的旧内容当作"新编辑"反向覆盖 A 的新内容；冲突/差异必须以用户可理解、可选择的方式呈现；A 端已有内容不得丢失。(b) 重装后的 B 能把 A 的内容完整拉下来；且 B **不得**把自己的空数据上传成"删除"而清空 A。
- **隐蔽点**：恢复旧备份后，本机的"最后同步位置"通常领先于备份内容，这就是最典型的"看似不会冲突、实际会静默覆盖"的入口。(b) 中"空设备首次同步不得删除云端"也是同一类风险。
- **反例信号**：A 的内容被旧备份覆盖；重装后 A 的数据被清空；两端互相覆盖若干轮后停在一个都缺一部分的状态。
- **判定手段**：恢复前的 A 快照（明文）与恢复同步后的 A 状态逐键比对。

### BB-17 双端离线并发后同时上线
- **前置**：两端一致。
- **操作**：两端**同时断网** → A 编辑 X、Y；B 编辑 Y、Z → 两端**同时**恢复网络并**同时**点同步（先后差 1–2 秒）→ 各自再同步两轮。
- **期望**：X、Z 在两端都保留；Y 若内容真的冲突，必须给出冲突提示并保持两端可控（**不得**静默丢弃任一侧的编辑）；最终经用户处理后两端一致。
- **隐蔽点**：**"同时"**是关键。顺序执行永远测不出竞态；必须在真实双端（真机）上快速连点。这也是"看似没问题、实际偶发丢内容"的主因。
- **反例信号**：X 或 Z 之一只在一端存在；Y 被任一端静默覆盖；两端反复提示需要核对；同步结果文案前后不一致（一次说成功一次说失败）。

### BB-18 日界与系统时钟
- **前置**：两端一致；把 A 的系统时间调到 23:58（或用真机等待跨天）。
- **操作**：A 在 23:58 编辑记录并同步 → 跨天到 00:01 → A 继续编辑同一条 → 同步 → B 同步；另构造一条"今天到期"的延迟验证，让两端在跨天前后各同步一次。
- **期望**：跨天的编辑在两端都正确落在**同一个日期归属**下（不得出现同一条记录在两端分属两天、或重复成两条）；到期验证在两端表现一致（不得一端已到期、另一端还没到期，也不得凭空多出一条验证任务）。
- **隐蔽点**："今天"在实现里通常取系统当前日期，跨天瞬间两端会取到不同结果。这类不一致在单端永远看不到，只在双端比对时暴露。
- **反例信号**：同一条记录在两端日期不同；出现重复记录/重复验证任务；到期日在一端被推迟一天。
- **判定手段**：两端界面日期字段 + 快照明文中的日期。

## 六、学习助教与语音（BB-19 ~ BB-22）

### BB-19 评分 → 快速整理的可见性与续跑控制
- **前置**：两端已配置好 AI 供应商；A 端已同步。
- **操作**：(a) A 给一条记录打分 → 观察 A 端整理状态 → A 同步 → B 同步，观察 B 端；(b) 在整理**未完成**时强制结束 A 并重开；(c) 在 A 端点击"继续整理/重试"。
- **期望**：(a) A 端能看到"整理中/已整理待确认/需要补充背景/整理失败"，B 端能看到同一反馈的整理结果（或一致的进行中状态）；(b) 重开后**不得**自动重跑这台设备未完成的整理（避免重复计费与重复写入），但必须给出**可点的继续/重试/开始入口**；(c) 点击后能正常完成。
- **隐蔽点**：(b) 与 (c) 必须成对验收——"不自动重跑"很容易做成"用户再也跑不起来"。这是"省了钱但功能没了"的典型失败。
- **反例信号**：重启后自动重跑（AI 调用数/费用异常增加）；重启后状态永远停在"整理中"且无任何按钮；点了"继续整理"无反应或报错；B 端看不到 A 的整理结果。
- **判定手段**：两端界面状态 + AI 调用次数（供应商后台或本地计数）。

### BB-20 出题/答题过程中另一端完成了任务或改动了被考内容
- **前置**：A 端有一个进行中的练习任务。
- **操作**：(a) A 正在作答 → 在 B 端把该任务标记为已完成并同步 → A 提交答案；(b) A 正在作答 → 在 B 端修改被考内容的正文并同步 → A 提交答案。
- **期望**：A **不得**静默丢掉已输入的答案；必须以可理解的方式说明"该任务/内容已在其他设备变化"，并给出可继续的路径（重做本题 / 保留答案记录 / 稍后处理）；两端最终状态一致、不产生重复计分。
- **隐蔽点**："答案丢失"在这里表现得非常温和——界面只是没反应或回到上一题，用户会以为自己点错了。要专门盯着"输入过的答案是否还在、计分是否重复"。
- **反例信号**：答案消失；提示报错但无法继续；分数被记两次或记零；两端任务状态不一致。

### BB-21 延迟验证到期的跨端表现
- **前置**：两端一致，存在一条已到期的延迟验证与一条未到期的。
- **操作**：A 同步 → B 同步 → A、B 分别进入验证流程并完成一次验证 → 同步 → 两端再各同步两轮。
- **期望**：到期的在两端都可用、未到期的在两端都不可用；完成一次验证后**两端只出现一条**验证记录（不得各生成一条、也不得凭空多出"重做"任务）；两端完成后状态一致且无变化。
- **隐蔽点**：到期判断与"自动排期"是两个都可能产生重复的地方，重复任务会悄悄改变用户的复习计划而很难被发现。
- **反例信号**：两端各有一条验证记录；凭空出现重复任务/同一天两条；未到期的一端可点。

### BB-22 语音回忆会话在清理/恢复后的生命周期
- **前置**：A 端已开始（或暂停）一次语音回忆会话。
- **操作**：(a) 在 A 端执行"恢复备份"或清空数据 → 观察刚才的会话；(b) 清理后重新开始一次新的语音回忆会话。
- **期望**：(a) 被清理掉的会话**不得**在后续操作（暂停、继续、切换页面、重开）中自行复活，也不得凭空出现在导出/备份内容里；(b) 新会话必须能正常开始并正常记录。
- **隐蔽点**：(a) 的"复活"通常发生在旧的后台运行时稍后落盘时，时间上与被清理的时刻隔开，很容易被判成"偶发"。(b) 是最容易被"为了安全起见一律禁止"改坏的入口。
- **反例信号**：清理后旧会话重新出现；导出/备份里含已删除的会话；新会话无法开始或无法记录。

## 执行顺序建议

1. **先 BB-04 / BB-08 / BB-14（零写入类）**：这三组最快，且能立刻暴露"隐式写入"这种会污染后续所有用例的问题。
2. **再 BB-01 / BB-02 / BB-03（基础收敛）**：确认最基本的数据流没问题，再进入删除与计划（BB-05 ~ BB-11）。
3. **然后 BB-12 ~ BB-14（草稿/编辑器）**，再 **BB-15 ~ BB-18（中断/恢复/时间）**——这两段必须在**真机**上做，浏览器模拟不算证据。
4. **最后 BB-19 ~ BB-22（助教/语音）**：涉及 AI 调用费用，用最小的合成数据跑，并把 AI 调用次数单独记录。

## 与自动化测试的分工

- 本清单的 **BB-01 ~ BB-11** 大部分可以用"两个独立数据库 + 可控远端"的合成数据方式自动化，作为每次改动的回归门禁；但**验收结论必须来自真机双端**。
- **BB-12 ~ BB-22** 存在真实时序（导航、杀进程、断网、跨天、AI 延迟），自动化只能覆盖其中"确定性"的片段，剩余部分以本清单为准执行。
- 自动化用例的日期必须相对"当天"生成（例如"到期日 = 今天 + 3 天"），**不得**硬编码具体日期，否则会在某一天自己变红。

## 故意不在本清单内

- 配额/账单/流量字节级的实际测算（本清单只覆盖"是否重复上传"这类可见信号）。
- 附件大文件带宽、移动端后台音频、付费 AI 输出质量。
- 旧客户端与新客户端混用、同一账号多设备以外的账号体系问题。
